Для авторов зависимых пакетов#

В этом документе описаны рекомендуемые приёмы разработки пакетов, зависящих от NumPy.

Версии NumPy и стабильность API/ABI#

NumPy использует стандартную схему версий, соответствующую PEP 440: major.minor.bugfix. Мажорные выпуски крайне редки и, скорее всего, означают нарушение совместимости ABI. Выпуски NumPy 1.xx выходили с 2006 по 2023 год; NumPy 2.0 в начале 2024 года — первый выпуск с изменением ABI. Незначительные нарушения ABI в особых случаях могли происходить несколько раз в минорных выпусках. Минорные версии выходят регулярно, обычно каждые полгода, и содержат новые возможности, объявления об устаревании и удаление ранее устаревшего кода. Корректирующие выпуски выходят ещё чаще и не содержат новых возможностей или объявлений об устаревании.

NumPy, как и сам Python и большинство известных научных проектов Python, не использует семантическое версионирование. Вместо этого изменения API, нарушающие обратную совместимость, должны предваряться предупреждениями об устаревании как минимум в двух выпусках. Подробнее см. NEP 23 — Политика обратной совместимости и объявления возможностей устаревшими.

NumPy предоставляет API Python и C API. К C API можно обращаться напрямую или через такие инструменты, как Cython и f2py. Если ваш пакет использует C API, важно понимать правила совместимости двоичного интерфейса приложений (ABI) NumPy: ABI NumPy совместим с последующими версиями, но не с предыдущими. Это означает, что двоичные файлы, собранные с более старой версией NumPy, продолжают работать с более новыми, а файлы, собранные с более новой версией, не обязательно работают со старыми.

Модули также можно безопасно собирать с NumPy 2.0 или новее в режиме abi3 CPython. Он позволяет собрать модуль для одной минимально поддерживаемой версии Python и сохранить совместимость с более новыми версиями той же серии (например, 3.x). Это может значительно уменьшить число собираемых и распространяемых wheel-пакетов. Дополнительные сведения и примеры см. в документации cibuildwheel.

Тестирование с основной веткой NumPy или предварительными выпусками#

Для крупных активно поддерживаемых пакетов, зависящих от NumPy, мы рекомендуем тестирование с разрабатываемой версией NumPy в CI. Для удобства ночные сборки доступны как wheel по адресу https://anaconda.org/scientific-python-nightly-wheels/. Пример команды установки:

pip install -U --pre --only-binary :all: -i https://pypi.anaconda.org/scientific-python-nightly-wheels/simple numpy

Это помогает обнаружить регрессии NumPy, которые нужно исправить до следующего выпуска. Также рекомендуем превращать предупреждения в ошибки в этом задании CI: все либо как минимум DeprecationWarning и FutureWarning. Так вы заранее узнаете об изменениях NumPy и сможете адаптировать код.

Если вы используете cibuildwheel и хотите проверить собственные пакеты wheel с последней ночной сборкой NumPy, в конфигурации CI может потребоваться что-то подобное:

CIBW_ENVIRONMENT: "PIP_PRE=1 PIP_EXTRA_INDEX_URL=https://pypi.anaconda.org/scientific-python-nightly-wheels/simple"

Зависимость времени сборки#

Примечание

До NumPy 1.25 C API NumPy по умолчанию не предоставлял обратной совместимости. Поэтому при сборке с NumPy версии ниже 1.25 нужно использовать самую старую версию, которую вы планируете поддерживать. Для этого можно воспользоваться oldest-supported-numpy. См. документацию NumPy 1.24.

Если пакет использует C API NumPy напрямую либо через зависящий от него инструмент, например Cython или Pythran, NumPy требуется этому пакету на этапе сборки.

По умолчанию NumPy предоставляет API, обратно совместимый с самой ранней версией NumPy, которая поддерживает самую старую версию Python, поддерживаемую в настоящее время NumPy. Например, NumPy 1.25.0 поддерживает Python 3.9 и выше; а самая ранняя версия NumPy, поддерживающая Python 3.9, была 1.19. Поэтому мы гарантируем, что NumPy 1.25 при использовании настроек по умолчанию предоставит C-API, совместимый с NumPy 1.19. (точная версия установлена ​​во внутренних заголовочных файлах NumPy).

NumPy также обеспечивает прямую совместимость в пределах всех минорных выпусков, но при переходе на мажорный выпуск потребуется перекомпиляция (рекомендации для NumPy 2.0 см. ниже).

Поведение по умолчанию можно настроить, например, добавив:

#define NPY_TARGET_VERSION NPY_1_22_API_VERSION

перед включением любых заголовков NumPy (или эквивалентного флага компилятора -D) в каждый модуль расширения, который требует NumPy C-API. Это в основном полезно, если вам нужно использовать недавно добавленный API за счет несовместимости со старыми версиями.

Если по какой-либо причине вы хотите по умолчанию компилировать для установленной версии NumPy, можно добавить:

#ifndef NPY_TARGET_VERSION
    #define NPY_TARGET_VERSION NPY_API_VERSION
#endif

Это позволяет переопределить значение по умолчанию через -DNPY_TARGET_VERSION. Определение должно быть согласованным в пределах каждого модуля расширения (использование import_array()); оно также применяется к модулю umath.

При компиляции с использованием NumPy добавьте соответствующие ограничения версий в pyproject.toml (см. PEP 517): ваше расширение не будет совместимо с новым основным выпуском NumPy и может быть несовместимо с очень старыми версиями.

Для пакетов conda-forge см. здесь инструкции по объявлению зависимости от numpy при использовании C API.

Зависимость во время выполнения и диапазоны версий#

NumPy и многие основные научные пакеты Python согласовали график прекращения поддержки старых версий Python и NumPy: NEP29. Всем пакетам, зависящим от NumPy, рекомендуем следовать NEP 29.

Для зависимостей времени выполнения задавайте границы версий в pyproject.toml.

Большинству библиотек, которые полагаются на NumPy, не нужно устанавливать верхнюю границу версии: NumPy старается сохранить обратную совместимость.

Тем не менее, если ваш проект (а) гарантированно часто выпускает новые версии, (б) использует значительную часть API NumPy и (в) опасается, что изменения NumPy нарушат его работу, можно задать верхнюю границу <MAJOR.MINOR + N, где N не меньше 3, а MAJOR.MINOR — текущая версия NumPy [*]. Если используется C API NumPy напрямую или через Cython, можно также ограничиться текущей основной версией для защиты от несовместимости ABI. Учтите, что верхняя граница версии NumPy может помешать установке вашей библиотеки вместе с другими, более новыми пакетами.

[*]

Значение N=3 выбрано потому, что при редких изменениях, нарушающих совместимость, NumPy выдаёт предупреждения как минимум на протяжении двух выпусков. Выпуски NumPy выходят примерно раз в полгода, поэтому этот период составляет не менее года; отсюда следующее требование выпускать версии вашего проекта не реже.

Рекомендации для NumPy 2.0#

NumPy 2.0 нарушает совместимость ABI, но позволяет собирать пакеты wheel, работающие и с 2.0, и с выпусками 1.xx. Важно понимать следующее:

  1. Если при сборке wheel-пакетов вы используете NumPy версии 1.xx, эти пакеты не будут работать с NumPy 2.0.

  2. Если пакеты wheel собраны с NumPy 2.x, они будут работать и с NumPy 1.xx.

Стабильность ABI NumPy 2.0 впервые будет гарантирована начиная с первого кандидата в выпуск версии 2.0 (то есть 2.0.0rc1). Для управления зависимостью от NumPy мы рекомендуем следующее:

  1. В основной (разработочной) ветке вашего пакета не добавляйте никаких ограничений.

  2. Если вы используете C API NumPy, например напрямую в C/C++ или через код Cython с NumPy, добавьте требование numpy<2.0 в метаданные зависимостей пакета для выпусков и в ветках выпусков. Сохраняйте его до выхода NumPy 2.0.0rc1, на который сможете ориентироваться. Причина: C ABI NumPy изменится в 2.0, поэтому скомпилированные модули расширения, зависящие от NumPy, перестанут работать; их потребуется перекомпилировать.

  3. Если ваш код использует значительную часть Python API NumPy, также стоит добавить то же требование numpy<2.0 в метаданные, пока вы не убедитесь, что код адаптирован к изменениям в 2.0, то есть пока не проверите его работу с 2.0.0rc1. Обоснование: мы проведём существенную очистку API, удалив многие псевдонимы и устаревшие либо нерекомендуемые объекты (см., например, Руководство по переходу на NumPy 2.0 и NEP 52 — очистка Python API в NumPy 2.0), поэтому, если вы не ограничиваетесь современными рекомендуемыми функциями и объектами, код, вероятно, потребует хотя бы небольших изменений.

  4. Запланируйте выпуск своих пакетов, зависящих от numpy, вскоре после выхода первого кандидата в выпуск NumPy 2.0, предположительно около 1 февраля 2024 года. Причина: к тому моменту можно будет выпустить пакеты, совместимые и с 2.0, и с 1.X, так что ваши пользователи почти или совсем не столкнутся со сбоями; важно, чтобы команда pip install mypackage продолжала работать в день выхода NumPy 2.0.

  5. Как только 2.0.0rc1 станет доступен, вы сможете настроить свои метаданные в pyproject.toml, как описано ниже.

Возможны два случая: вам нужно сохранить совместимость с NumPy 1.xx, поддерживая также 2.0, либо вы можете отказаться от 1.xx в новых выпусках своего пакета и поддерживать только версии >=2.0. Второй вариант проще, но сильнее ограничивает пользователей. В этом случае достаточно добавить numpy>=2.0 или numpy>=2.0.0rc1 в требования для сборки и выполнения. Далее мы рассмотрим несколько более сложный вариант: сохранение совместимости и с 1.xx, и с 2.x.

Пример для пакета, использующего C API NumPy через C, Cython и т. п., с поддержкой NumPy 1.23.5 и новее:

[build-system]
build-backend = ...
requires = [
    # Note for packagers: this constraint is specific to wheels
    # for PyPI; it is also supported to build against 1.xx still.
    # If you do so, please ensure to include a `numpy<2.0`
    # runtime requirement for those binary packages.
    "numpy>=2.0.0rc1",
    ...
]

[project]
dependencies = [
    "numpy>=1.23.5",
]
Комментарии к примеру на русском
  • Для сборщиков пакетов: ограничение относится к пакетам wheel
  • для PyPI; сборка с 1.xx также поддерживается.
  • В таком случае обязательно добавьте требование `numpy<2.0`
  • во время выполнения для этих двоичных пакетов.

Рекомендуем иметь хотя бы одно задание CI, которое собирает и устанавливает wheel-пакет, а затем запускает тесты с самой старой поддерживаемой пакетом версией NumPy. Например:

- name: Build wheel via wheel, then install it
  run: |
    python -m build  # This will pull in numpy 2.0 in an isolated env
    python -m pip install dist/*.whl

- name: Test against oldest supported numpy version
  run: |
    python -m pip install numpy==1.23.5
    # now run test suite
Комментарии к примеру на русском
  • Это установит NumPy 2.0 в изолированное окружение
  • Теперь запускаем набор тестов

Описанное выше работает только после появления NumPy 2.0 на PyPI. Для тестирования с пакетом wheel NumPy 2.0-dev нужно использовать ночную сборку NumPy (см. этот раздел выше) либо собрать NumPy из исходников.
