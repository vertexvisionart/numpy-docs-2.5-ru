Усовершенствованные инструменты отладки #

Если вы дошли до этого раздела, вероятно, вы хотите познакомиться с более сложными инструментами или использовать их. Обычно они не нужны начинающим участникам и для большинства повседневных задач разработки. Их используют реже: например, незадолго до нового выпуска NumPy или после внесения крупного либо особенно сложного изменения.

Некоторые из этих средств используются в тестах непрерывной интеграции NumPy. Если тест завершается неудачно только под средством отладки, эти инструкции должны помочь воспроизвести сбой локально.

Не все эти инструменты используются регулярно, а некоторые доступны лишь в отдельных системах, поэтому возможны различия в поведении, проблемы и особенности работы. Мы будем рады помочь, если возникнут затруднения, и приветствуем улучшения и предложения по этим рабочим процессам.

Поиск ошибок в C с помощью дополнительных инструментов#

Для большей части разработки достаточно обычных инструментов отладки, описанных в разделе «Отладка». Однако некоторые проблемы, например утечки памяти, могут быть особенно неочевидными и трудными для локализации.

Большинству участников не потребуется запускать эти инструменты. Однако вы можете помочь быстрее находить такие проблемы:

  • Тесты должны охватывать все пути выполнения кода, включая обработку ошибок.

  • Старайтесь писать короткие и простые тесты. Если тест очень сложный, подумайте о добавлении ещё одного, более простого. Это полезно, поскольку часто легко определить лишь тест, в котором возникает проблема, а не конкретную его строку.

  • Никогда не используйте np.empty, если данные читаются/используются. Valgrind заметит это и сообщит об ошибке. Если вас не волнуют значения, вместо этого вы можете генерировать случайные значения.

Это поможет нам заметить упущения до выпуска вашего изменения, а вам не придётся беспокоиться об ошибках подсчёта ссылок, которые могут пугать.

Отладочная сборка Python#

Отладочные сборки Python легко установить, например, через системный менеджер пакетов в Linux. Они доступны и на других платформах, хотя, возможно, в менее удобной форме. Если установить отладочную сборку из системного менеджера пакетов сложно, её можно собрать самостоятельно с помощью pyenv. Например, чтобы установить и глобально активировать отладочную сборку Python 3.13.3, выполните:

pyenv install -g 3.13.3
pyenv global 3.13.3

pyenv install собирает Python из исходников, поэтому перед сборкой нужно установить зависимости Python. Инструкции для своей платформы см. в документации pyenv. Для установки зависимостей, необходимых при отладке, можно использовать pip. Если на pypi, нет отладочного пакета wheel, зависимости придётся собрать из исходников, также в отладочном режиме.

В отладочных сборках исполняемый файл Python часто называется pythond вместо python. Чтобы проверить, установлена ли отладочная сборка, выполните, например, pythond -m sysconfig: команда выводит конфигурацию сборки интерпретатора. В отладочной сборке CFLAGS содержит отладочные параметры компилятора, например -g -Og.

Для запуска тестов NumPy или интерактивной оболочки обычно достаточно:

python3.8d runtests.py
# or
python3.8d runtests.py --ipython

Отладочная сборка Python поможет:

  • Найдите ошибки, которые в противном случае могут вызвать случайное поведение. Одним из примеров является случай, когда объект все еще используется после его удаления.

  • Отладочная сборка Python позволяет проверить корректность счётчиков ссылок с помощью дополнительных команд:

    sys.gettotalrefcount()
sys.getallocatedblocks()

  • Python отладочные сборки позволяют упростить отладку с помощью gdb и других отладчиков C.

Используйте вместе с pytest #

Один лишь запуск набора тестов с отладочной сборкой Python не обнаружит много ошибок. Дополнительное преимущество такой сборки — возможность выявлять утечки памяти.

Упростить эту задачу помогает инструмент pytest-leaks, который можно установить с помощью pip. К сожалению, сам pytest может допускать утечки памяти, но в настоящее время обычно удаётся получить хорошие результаты, удалив:

@pytest.fixture(autouse=True)
def add_np(doctest_namespace):
    doctest_namespace['np'] = numpy

@pytest.fixture(autouse=True)
def env_setup(monkeypatch):
    monkeypatch.setenv('PYTHONHASHSEED', '0')

из numpy/conftest.py (это может меняться с новыми версиями pytest-leaks или обновлениями pytest).

Это позволяет удобно запускать весь набор тестов или его часть:

python3.8d runtests.py -t numpy/_core/tests/test_multiarray.py -- -R2:3 -s

где -R2:3 — параметр pytest-leaks (см. его документацию). Параметр -s включает непосредственный вывод и иногда необходим: в некоторых версиях перехваченный вывод ошибочно определялся как утечка.

В некоторых тестах утечки ссылок известны заранее или даже предусмотрены специально. Мы стараемся помечать такие тесты, однако ложные срабатывания всё же возможны.

valgrind#

Valgrind — мощный инструмент поиска определённых проблем доступа к памяти; его следует запускать для сложного кода C. Для обычного использования valgrind обычно достаточно:

PYTHONMALLOC=malloc valgrind python runtests.py

где PYTHONMALLOC=malloc необходим, чтобы избежать ложных срабатываний от самого Python. В зависимости от системы и версии Valgrind вы можете увидеть больше ложных срабатываний. valgrind поддерживает «подавления», чтобы игнорировать некоторые из них, и Python действительно имеет файл подавления (и даже опцию времени компиляции), который может помочь, если вы найдете это необходимым.

Valgrind помогает:

  • Поиск использования неинициализированных переменных и памяти.

  • Обнаружение нарушений доступа к памяти (чтение или запись за пределами выделенной памяти).

  • Находит многие утечки памяти. Но для большинства утечек отладочная сборка Python и pytest-leaks гораздо чувствительнее. Причина в том, что valgrind обнаруживает лишь безусловно потерянную память. Если:

    dtype = np.dtype(np.int64)
arr.astype(dtype=dtype)

    Содержит ошибку подсчёта ссылок для dtype, которую valgrind не обнаруживает, поскольку np.dtype(np.int64) всегда возвращает один и тот же объект. Однако не все типы данных существуют в единственном экземпляре, поэтому при других входных данных возможна утечка памяти. В редких случаях NumPy использует malloc вместо средств выделения памяти Python; такие выделения не видны отладочной сборке Python. Обычно malloc следует избегать, но есть исключения: например, структура PyArray_Dims входит в общедоступный API и не может использовать средства выделения памяти Python.

Хотя обнаружение утечек памяти с помощью Valgrind медленное и менее чувствительное, оно удобно: большинство программ можно запускать под Valgrind без изменений.

Что следует учитывать:

  • Valgrind не поддерживает тип NumPy longdouble, поэтому корректные тесты могут завершаться неудачей или сопровождаться ложными сообщениями об ошибках.

  • Ожидайте некоторых ошибок до и после запуска кода NumPy.

  • Из-за кэшей ошибки, в частности утечки памяти, могут остаться незамеченными либо обнаружиться позже, в не связанном с ними месте.

Важное преимущество valgrind — отсутствие зависимостей помимо самого valgrind, хотя для более информативных трассировок стека желательно использовать отладочные сборки.

Используйте вместе с pytest #

Можно запустить набор тестов под valgrind; этого может быть достаточно, если вас интересуют лишь несколько тестов:

PYTHONMALLOC=malloc valgrind python runtests.py \
 -t numpy/_core/tests/test_multiarray.py -- --continue-on-collection-errors

Обратите внимание на --continue-on-collection-errors, который в настоящее время необходим из-за отсутствия поддержки longdouble, вызывающей сбои (обычно это не требуется, если вы не запустите полный набор тестов).

Для обнаружения утечек памяти также потребуется --show-leak-kinds=definite и, возможно, другие параметры valgrind. Как и при использовании pytest-leaks, некоторые тесты заведомо содержат утечки и вызывают ошибки в valgrind; они могут быть помечены соответствующим образом, но не обязательно.

Мы разработали pytest-valgrind , который:

  • Сообщает об ошибках каждого теста отдельно

  • Позволяет локализовать утечки памяти до отдельных тестов. По умолчанию valgrind проверяет утечки только после завершения программы, что очень неудобно.

Подробнее см. README, где также приведён пример команды для NumPy.

Отладчики C#

При сбоях NumPy или работе над изменениями в его низкоуровневом коде на C или C++ часто удобно запускать Python под отладчиком C, чтобы получить больше информации. Отладчик помогает разобраться в сбое интерпретатора (например, из-за ошибки сегментации), показывая стек вызовов C в месте сбоя. Этот стек часто даёт ценный контекст для понимания причины сбоя. Отладчики C также очень полезны при разработке: они позволяют интерактивно отлаживать реализацию NumPy на C.

Для отладки NumPy разработчики часто используют gdb и lldb. Как правило, gdb удобнее в Linux, а lldb — в macOS. Интерфейсы у них разные, поэтому нужно освоить выбранный отладчик. Для перехода с gdb на lldb полезна таблица соответствия команд: она показывает, как выполнять распространённые действия в обоих отладчиках.

Сборка с отладочными символами#

Инструмент spin для организации разработки имеет встроенную поддержку gdb и lldb через команды spin gdb и spin lldb.

Примечание

Сборка с -Dbuildtype=debug имеет несколько важных особенностей:

  • Проверки assert включены: этот тип сборки не определяет макрос NDEBUG, поэтому все проверки assert на уровне C остаются активными. Это помогает при отладке точно определить место возникновения неожиданного состояния.

  • Может потребоваться переопределение флагов компилятора: некоторые наборы инструментов, особенно из conda-forge, по умолчанию устанавливают флаги оптимизации, например -O2. Они могут переопределять настройки типа сборки debug. Для полноценной отладочной сборки в такой среде может понадобиться вручную отменить или переопределить этот флаг.

Подробности по обоим вопросам см. в руководстве meson-python по отладочным сборкам.

Для обоих отладчиков рекомендуется собирать NumPy с профилем Meson debug или debugoptimized. Для выбора debug передайте параметр через spin build:

spin build -- -Dbuildtype=debug

чтобы использовать debugoptimized, вместо этого нужно передать -Dbuildtype=debugoptimized.

Можно передать дополнительные аргументы в meson setup помимо buildtype, используя тот же синтаксис позиционных аргументов для spin build.

Запуск тестового сценария#

Пусть тестовый скрипт test.py находится в папке test рядом с каталогом исходного кода NumPy. Запустить его со сборкой NumPy, созданной через spin, можно следующей командой:

spin gdb ../test/test.py

Это запустит gdb. Если нужен только стек вызовов при аварийном завершении, введите «r» и нажмите Enter. Тестовый скрипт запустится; если произойдёт сбой, введите «bt», чтобы получить стек вызовов. Для lldb действия аналогичны: замените spin gdb на spin lldb.

Также можно устанавливать точки останова и применять другие, более сложные методы. Подробности см. в документации отладчика.

Одна из типичных трудностей с точками останова в NumPy: некоторые участки кода многократно выполняются уже при импорте модуля numpy. Поэтому бывает непросто или утомительно найти первый «настоящий» вызов после завершения импорта и полной инициализации numpy.

Один из обходных путей заключается в использовании такого сценария:

import os
import signal

import numpy as np

PID = os.getpid()

def do_nothing(*args):
    pass

signal.signal(signal.SIGUSR1, do_nothing)

os.kill(PID, signal.SIGUSR1)

# the code to run under a debugger follows

Используйте вместе с pytest #

Тесты pytest также можно запускать под отладчиком. Это требует некоторых ручных действий, поскольку spin пока не автоматизирует процесс. Сначала выполните spin build, чтобы получить полностью собранную копию NumPy под управлением spin. Затем для запуска тестов под lldb выполните примерно следующее:

spin lldb $(which python) $(which pytest) build-install/usr/lib/python3.13/site-packages/numpy/_core/tests/test_multiarray.py

После ввода «r» и нажатия Enter эта команда запустит тесты из test_multiarray.py под отладчиком lldb. Приведённая команда взята из сеанса Python 3.13 на Mac. При использовании другой версии Python или другой операционной системы структура каталогов внутри build-install может немного отличаться.

Точки останова можно устанавливать, как описано выше. Здесь также возникает проблема их частого срабатывания при импорте NumPy. Выделите проверяемые действия в тестовый скрипт, чтобы применить описанный выше обходной способ с os.kill.

Обратите внимание на использование $(which python) для обеспечения того, чтобы отладчик получал путь к исполняемому файлу Python. Если вы используете pyenv, вам может потребоваться заменить which python на pyenv which python, поскольку pyenv полагается на скрипты shim, о которых which не знает.

Санитайзеры компилятора#

Наборы санитайзеров компилятора, поставляемые с GCC и LLVM, позволяют обнаруживать многие распространённые ошибки программирования во время выполнения. При сборке санитайзеры добавляют в код приложения инструменты для дополнительных проверок при выполнении. Обычно их запускают в ходе обычного тестирования. Если проверка санитайзера выявляет проблему, тест завершается ошибкой или аварийно, а санитайзер выдаёт отчёт о характере проблемы.

Санитайзеры можно использовать и с обычной сборкой CPython, но лучше создать окружение на основе Python, собранного из исходного кода с инструментированием санитайзером, затем им собрать NumPy и запустить тесты. Если весь стек Python инструментирован с одной и той же библиотекой времени выполнения санитайзера, можно выявлять проблемы, возникающие между его частями. Например, это позволяет обнаружить утечки памяти NumPy из-за неверного обращения с памятью, выделенной в CPython.

Сборка Python с инструментированием санитайзерами#

Подробнее о сборке Python из исходного кода см. соответствующий раздел руководства разработчика Python. Чтобы включить AddressSanitizer, при сборке передайте --with-address-sanitizer скрипту configure.

Можно также использовать pyenv для автоматической сборки Python и быстрого включения или отключения его установок через командную строку, как при работе с виртуальными средами. С помощью pyenv можно установить сборку Python 3.13 с инструментированием ASAN следующим образом:

CONFIGURE_OPTS="--with-address-sanitizer" pyenv install 3.13

Для работы с ThreadSanitizer можно быстрее воспользоваться cpython_sanity образами Docker, избежав сборки Python из исходного кода. Однако отладка внутри контейнера Docker может быть неудобна.

Используйте вместе с spin #

Независимо от способа сборки Python, получив инструментированную сборку, можно установить зависимости NumPy для разработки и тестирования и собрать NumPy с AddressSanitizer. Например, чтобы собрать NumPy с профилем debug и AddressSanitizer, передайте meson дополнительные параметры сборки следующим образом:

spin build -- -Dbuildtype=debug -Db_sanitize=address

После завершения сборки вы можете использовать другие команды spin, такие как spin test и spin gdb, как и в любой другой сборке Python.

Особые соображения #

Некоторые тесты NumPy намеренно приводят к тому, что malloc возвращает NULL. Некоторые санитайзеры компилятора при стандартной настройке считают это ошибкой. Проверку можно отключить, передав санитайзеру параметр allocator_may_return_null=1. Например, для AddressSanitizer:

ASAN_OPTIONS=allocator_may_return_null=1 spin test

Вы можете увидеть сообщения об утечках памяти из интерпретатора Python, особенно в macOS. Если такие отчёты бесполезны, отключите обнаружение утечек, указав detect_leaks=0 в ASAN_OPTIONS. Несколько параметров можно передать списком с разделителем «:», например:

ASAN_OPTIONS=allocator_may_return_null=1:halt_on_error=1:detect_leaks=1 spin test

Особенно полезен параметр halt_on_error: при обнаружении ошибки он немедленно аварийно завершает процесс Python и выводит отчёт, включая трассировку стека.

Можно также изучить конфигурацию рабочего процесса GitHub Actions compiler_sanitizers.yml. В ней описано несколько заданий CI, запускаемых в рамках тестов NumPy с инструментами обнаружения ошибок ThreadSanitizer, AddressSanitizer и UndefinedBehaviorSanitizer.
