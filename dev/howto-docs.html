Как участвовать в работе над документацией NumPy#

Это руководство поможет вам решить, что внести и как отправить его в официальную документацию NumPy.

Встречи команды документации#

Сообщество NumPy твёрдо намерено улучшать документацию. Мы регулярно проводим встречи по документации в Zoom; даты объявляются в списке рассылки numpy-discussion, приглашаются все желающие. Обращайтесь, если есть вопросы или нужна помощь с первыми шагами: мы рады помочь. Протоколы встреч ведутся на hackmd.io и хранятся в репозитории NumPy Archive.

Что потребуется#

Подробности изложены в документации NumPy. Справочник API генерируется непосредственно из строк документации в коде при сборке документации. Хотя справочные описания почти всех доступных пользователям функций и классов уже есть, для некоторых не хватает примеров использования.

Нам не хватает документации более широкого охвата: учебных и практических руководств, объяснений. Сообщать о недостатках — ещё один способ помочь. Мы рассмотрим оба направления.

Внесение исправлений#

Мы рады сообщениям об ошибках документации и хотим их исправлять. Однако ради решения наиболее важных проблем некоторые сообщения приходится откладывать или оставлять без внимания. Ниже — ошибки, которыми стоит заняться в первую очередь.

Наивысший приоритет имеют технические неточности: пропущенный параметр в строке документации, неверное описание функции, параметра или метода и т. п. Другие структурные дефекты, например неработающие ссылки, тоже приоритетны. Такие ошибки легко подтвердить и исправить. Если умеете, отправьте pull request (PR) с исправлением; иначе создайте issue.

Опечатки и орфографические ошибки имеют более низкий приоритет. Мы рады сообщениям о них, но не всегда можем быстро их исправить. Для них также можно создавать запросы на слияние или задачи.

Очевидные ошибки формулировки, например пропуск частицы «не», относятся к опечаткам. Но другие переформулировки, даже грамматические, требуют оценки по существу, поэтому требования к ним выше. Для начала предложите исправление в виде задачи в системе отслеживания проблем.

У некоторых функций и объектов, определённых в модулях расширения на C, например numpy.ndarray.transpose и numpy.array, строки документации задаются отдельно в _add_newdocs.py.

Добавление новых страниц #

Трудности, с которыми вы сталкиваетесь при чтении нашей документации, лучше всего показывают, что нужно исправить.

Написав недостающую документацию, вы внесёте прямой вклад в развитие открытого проекта. Но даже сообщение о том, чего не хватает, уже полезно. Если хотите написать документ, обсудите замысел в списке рассылки, чтобы получить идеи и отзывы. Чтобы сообщить о пробеле, создайте issue. Пример приведён в этом обсуждении.

Если вы ищете тему для работы, официальный план развития документации оформлен как предложение по улучшению NumPy (NEP): NEP 44 — Реструктуризация документации NumPy. В нём указаны разделы, требующие доработки, и перечислены желаемые дополнения, в том числе блокноты Jupyter.

Система подготовки документации#

Есть приёмы написания полезной документации; четыре основных подхода охватывают почти всё, поскольку есть четыре категории документов: tutorial, how-to guide, explanation и reference. Это разделение предложил Daniele Procida в своей системе Diátaxis. Начиная или предлагая документ, заранее определите его тип.

Учебные материалы NumPy#

Помимо документации в дереве исходного кода NumPy, можно предложить материалы в формате Jupyter Notebook для страницы Учебные материалы NumPy. Этот набор руководств и учебных материалов проекта NumPy предназначен как для самостоятельного изучения, так и для преподавания. Материалы разрабатываются в отдельном репозитории GitHub numpy-tutorials. Там можно изучить существующие блокноты, предложить новые темы в задачах или отправить собственные руководства через pull request.

Подробнее об участии в проекте#

Не беспокойтесь, если английский для вас не родной или вы можете подготовить только черновик. Разработка открытого ПО — совместная работа сообщества. Сделайте всё, что можете, а мы поможем устранить недостатки.

Изображения и реальные данные делают текст интереснее и убедительнее, но убедитесь, что их лицензии допускают использование и что материалы доступны. Даже приблизительный замысел иллюстрации другие участники смогут доработать.

Пока NumPy принимает только форматы данных, используемые и другими научными библиотеками Python, такими как pandas, SciPy и Matplotlib. Мы разрабатываем пакет для поддержки большего числа форматов; свяжитесь с нами для получения подробностей.

Документация NumPy хранится в дереве исходного кода. Чтобы добавить документ, скачайте дерево, соберите его и отправьте pull request. Если GitHub и pull request вам незнакомы, см. Руководство участника.

Мы используем язык разметки reStructuredText (rST), более развитый, чем Markdown. Sphinx, которым многие проекты Python собирают документацию и создают ссылки между её разделами, преобразует rST в HTML и другие форматы. Подробнее о rST см. Краткое руководство по reStructuredText или Введение в reStructuredText.

Косвенный вклад#

Если вы найдёте сторонние материалы, которые могли бы дополнить документацию NumPy, сообщите нам об этом, создав issue.

Помогать NumPy можно и вне этого проекта: написать руководство в своём блоге, создать видео на YouTube или ответить на вопросы в Stack Overflow и на других сайтах — это тоже вклад.

Стиль документации #

Документация пользователя#

  • При написании руководства пользователя мы в целом следуем руководству Google по стилю документации для разработчиков.

  • Стиль NumPy регулирует случаи, когда:

    • У Google нет инструкций, или

    • Мы предпочитаем не использовать стиль Google.

    Наши текущие правила:

    • В английском тексте мы используем множественное число index в форме indices, а не indexes, следуя примеру numpy.indices.

    • Для единообразия мы также используем форму множественного числа matrix («матрица») — matrices («матрицы»).

  • Грамматические вопросы, недостаточно подробно рассмотренные в правилах NumPy или Google, разрешаются согласно разделу «Grammar and Usage» последнего издания Chicago Manual of Style.

  • Просим сообщать о случаях, которые стоит добавить в правила стиля NumPy.

Строки документации#

При использовании Sphinx с соглашениями NumPy подключайте расширение numpydoc для корректной обработки строк документации. Например, Sphinx извлечёт раздел Parameters и преобразует его в список полей. numpydoc также предотвращает ошибки reStructuredText, которые обычный Sphinx выдаёт, встречая неожиданные для строк документации соглашения NumPy, например заголовки разделов (-------------).

Он доступен по адресу:

  • numpydoc на PyPI

  • numpydoc на GitHub

Обратите внимание, что для документации внутри NumPy нет необходимости выполнять import numpy as np в начале примера.

Используйте numpydoc и его стандарт форматирования, показанный в соответствующем примере.

Документирование кода C/C++ #

NumPy использует Doxygen для разбора специально оформленных блоков комментариев C/C++. Он создаёт XML-файлы, которые Breathe преобразует в RST для Sphinx.

Процесс документирования состоит из трёх шагов:

1. Написание блоков комментариев#

Несмотря на то, что до сих пор не существует стиля комментирования, Javadoc более предпочтителен, чем другие, из-за сходства с существующими блоками комментариев без индекса.

Примечание

См. «Документирование кода».

Так выглядит стиль Javadoc:

Здесь приводятся подробности. Текст может занимать несколько строк.

Параметры:

  • num — комментарий к параметру num.

  • str — оставьте комментарий ко второму параметру.

Возвращаемые значения:

оставьте комментарий для возвращаемого значения.

Для однострочного комментария можно использовать три косые черты. Например:

/**
 *  Template to represent limbo numbers.
 *
 *  Specializations for integer types that are part of nowhere.
 *  It doesn't support with any real types.
 *
 *  @param Tp Type of the integer. Required to be an integer type.
 *  @param N  Number of elements.
*/
template<typename Tp, std::size_t N>
class DoxyLimbo {
 public:
    /// Default constructor. Initialize nothing.
    DoxyLimbo();
    /// Set Default behavior for copy the limbo.
    DoxyLimbo(const DoxyLimbo<Tp, N> &l);
    /// Returns the raw data for the limbo.
    const Tp *data();
 protected:
    Tp p_data[N]; ///< Example for inline comment.
};

Вот как это отображается:

template<typename Tp, std::size_t N>
class DoxyLimbo#

Шаблон для представления чисел limbo.

Специализации для целочисленных типов из «ниоткуда». Не поддерживает ни один реально существующий тип.

Параметр Tp:

Целочисленный тип. Обязательно должен быть целочисленным.

Параметр N:

Количество элементов.

Задаёт стандартное поведение при копировании limbo.

Распространённые теги Doxygen:#

Примечание

Другие теги и команды см. на https://www.doxygen.nl/manual/commands.html

@brief

Начинает абзац с кратким описанием. По умолчанию первое предложение блока документации автоматически считается кратким описанием, поскольку в настройках Doxygen включён параметр JAVADOC_AUTOBRIEF.

@details

Точно так же, как @brief начинает краткое описание, @details начинает подробное описание. Вы также можете начать новый абзац (пустую строку), тогда команда @details не понадобится.

@param

Начинает описание параметра функции с именем <parameter-name>, за которым следует текст описания. Наличие параметра проверяется: предупреждение выдаётся, если для него (или любого другого параметра) отсутствует документация либо документированный параметр отсутствует в объявлении или определении функции.

@return

Начинает описание возвращаемого значения функции. Несколько соседних команд @return будут объединены в один абзац. Описание @return заканчивается, когда встречается пустая строка или какая-либо другая команда секционирования.

@code/@endcode

Запускает/заканчивает блок кода. К блоку кода относятся иначе, чем к обычному тексту. Он интерпретируется как исходный код.

@rst/@endrst

Начинает/заканчивает блок разметки reST.

Примеры #

Взгляните на следующий пример :

/**
 * A comment block contains reST markup.
 * @rst
 * .. note::
 *
 *   Thanks to Breathe_, we were able to bring it to Doxygen_
 *
 * Some code example::
 *
 *   int example(int x) {
 *       return x * 2;
 *   }
 * @endrst
 */
void doxy_reST_example(void);

Вот как это отображается:

void doxy_reST_example(void)#

Блок комментариев содержит разметку reST.

Пример кода:

int example(int x) {
    return x * 2;
}

Примечание

Благодаря Breathe мы смогли перенести этот подход и в Doxygen

2. Передача данных Doxygen#

Не все файлы заголовков собираются автоматически.Вы должны добавить желаемые пути заголовка C/C++ в файлы подконфигурации Doxygen.

Файлы подконфигурации имеют установленное имя .doxyfile; обычно они расположены рядом с каталогами документируемых заголовков. Если вблизи нужных заголовков, в пределах двух уровней каталогов, такого файла нет, создайте новый.

Во вложенных конфигурационных файлах можно использовать любые параметры Doxygen из его настроек конфигурации, но нельзя переопределять или повторно инициализировать их значения: следует использовать только оператор добавления «+=». Например:

# to specify certain headers
INPUT += @CUR_DIR/header1.h \
         @CUR_DIR/header2.h
# to add all headers in certain path
INPUT += @CUR_DIR/to/headers
# to define certain macros
PREDEFINED += C_MACRO(X)=X
# to enable certain branches
PREDEFINED += NPY_HAVE_FEATURE \
              NPY_HAVE_FEATURE2
Комментарии к примеру на русском
  • Для указания отдельных заголовков
  • Для добавления всех заголовков из указанного каталога
  • Для определения нужных макросов
  • Для включения нужных ветвей

Примечание

@CUR_DIR — шаблонная константа, возвращающая путь к текущему каталогу файла подконфигурации.

3. Директивы по включению #

Breathe предоставляет широкий спектр пользовательских директив, позволяющих конвертировать документы, созданные Doxygen , в файлы reST.

Примечание

Подробнее см. «Директивы и переменные конфигурации».

Общие директивы: #

doxygenfunction

Директива формирует вывод для одной функции. Её имя должно быть уникальным в проекте.

.. doxygenfunction:: <function name>
    :outline:
    :no-link:

Посмотрите пример, чтобы увидеть это в действии.

doxygenclass

Эта директива создаёт соответствующий вывод для одного класса. Она принимает стандартные параметры project, path, outline и no-link, а также members, protected-members, private-members, undoc-members, membergroups и members-only:

.. doxygenclass:: <class name>
   :members: [...]
   :protected-members:
   :private-members:
   :undoc-members:
   :membergroups: ...
   :members-only:
   :outline:
   :no-link:

Подробности и примеры использования см. в документации doxygenclass.

doxygennamespace

Эта директива создаёт вывод для содержимого пространства имён. Она принимает стандартные параметры project, path, outline и no-link, а также content-only, members, protected-members, private-members и undoc-members. Для вложенного пространства имён нужно указать полное имя, например foo::bar для пространства bar внутри foo.

.. doxygennamespace:: <namespace>
   :content-only:
   :outline:
   :members:
   :protected-members:
   :private-members:
   :undoc-members:
   :no-link:

Подробности и пример работы см. в документации doxygennamespace.

doxygengroup

Эта директива формирует вывод содержимого группы Doxygen. Объявить такую группу можно специальной разметкой Doxygen в комментариях исходного кода; см. документацию по группировке.

Принимает стандартные параметры project, path, outline и no-link, а также content-only, members, protected-members, private-members и undoc-members.

.. doxygengroup:: <group name>
   :content-only:
   :outline:
   :members:
   :protected-members:
   :private-members:
   :undoc-members:
   :no-link:
   :inner:

Подробнее и с примерами см. документацию doxygengroup.

Устаревшая директива#

Если функция, модуль или API находятся в режиме legacy, то есть сохраняются для обратной совместимости, но не рекомендуются для нового кода, можно использовать директиву .. legacy::.

По умолчанию, если использовать устаревшую директиву без аргументов, она сгенерирует следующий вывод:

Прежние возможности

Этот подмодуль относится к прежнему API и больше не будет обновляться. Он также может быть удалён в будущих версиях NumPy.

Настоятельно рекомендуется добавить собственное сообщение, например указать новый API взамен старого:

.. legacy::

   For more details, see :ref:`distutils-status-migration`.
