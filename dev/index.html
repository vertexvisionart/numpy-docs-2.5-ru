Участие в разработке NumPy#

Не пишете код? Это не проблема! Работа над NumPy многогранна, и нам нужна помощь во многих областях. Ниже перечислены занятия, с которыми вы можете помочь. Все они важны, поэтому список упорядочен по алфавиту:

  • Сопровождение и разработка кода

  • Координация сообщества

  • DevOps

  • Разработка учебных материалов и поясняющей документации

  • Сбор средств

  • Маркетинг

  • Управление проектом

  • Перевод контента

  • Проектирование и разработка веб-сайтов

  • Написание технической документации

Мы понимаем, что у всех разный уровень опыта. Кроме того, NumPy — давно сложившийся проект, поэтому трудно представить идеального «начинающего участника». Именно поэтому мы не отмечаем задачи меткой «good-first-issue». Вместо неё вы найдёте задачи с меткой «Sprintable». Они могут относиться к следующим категориям:

  • Легко исправить под руководством опытного участника (идеально для работы на спринте).

  • Возможность научиться новому для тех, кто готов разобраться глубже, даже вне спринта.

Кроме того, в зависимости от вашего опыта одни задачи с меткой «Sprintable» могут оказаться лёгкими, а другие — более сложными.

Далее в документе рассматривается работа над кодом и документацией NumPy. Описания других видов деятельности и ролей сейчас обновляются. Если они вас интересуют, свяжитесь с нами через список рассылки numpy-discussion или GitHub: создайте обсуждение проблемы либо оставьте комментарий к подходящему сообщению. Это предпочтительные каналы общения: открытый проект открыт по своей природе. Но если сначала вам удобнее обсудить вопрос в менее публичной обстановке, можно воспользоваться Slack; подробности см. на numpy.org/contribute.

Краткое описание процесса разработки#

Ниже приведён краткий обзор; ссылки полного оглавления расположены далее:

  1. Если вы участвуете впервые:

    • Перейдите в numpy/numpy и нажмите кнопку «fork», чтобы создать собственную копию проекта.

    • Клонируйте проект на локальный компьютер:

      git clone --recurse-submodules https://github.com/your-username/numpy.git

    • Смените каталог:

      cd numpy

    • Добавить репозиторий upstream:

      git remote add upstream https://github.com/numpy/numpy.git

    • Теперь git remote -v покажет два удаленных репозитория, названных:

      • upstream, который относится к репозиторию numpy

      • origin, указывающий на ваш личный форк

    • Получите последние изменения из апстрима, включая теги:

      git checkout main
git pull upstream main --tags

    • Инициализируйте подмодули numpy:

      git submodule update --init

  2. Подготовьте своё изменение:

    • Создайте ветвь для функции, над которой вы хотите работать. Поскольку имя ветви появится в сообщении слияния, используйте разумное имя, такое как «linspace-speedups»:

      git checkout -b linspace-speedups

    • По мере работы создавайте локальные коммиты (git add и git commit). Пишите правильно оформленные сообщения коммитов, добавляйте тесты, которые не проходят до изменения и проходят после него, запускайте все тесты локально. Обязательно документируйте любое изменение поведения в строках документации, соблюдая стандарт NumPy.

  3. Чтобы представить свой вклад:

    • Отправьте изменения в свой форк на GitHub:

      git push origin linspace-speedups

    • Откройте GitHub. Рядом с новой веткой появится зелёная кнопка Pull Request. Убедитесь, что заголовок и описание ясны, кратки и понятны без дополнительных пояснений. Затем нажмите кнопку, чтобы отправить запрос.

    • Если ваш коммит добавляет новую возможность или меняет поведение, объясните изменения в списке рассылки. Для исправления ошибок, обновления документации и подобных изменений это обычно не требуется. Однако если реакции нет, можно попросить о рецензировании.

  4. Процесс рецензирования:

    • Рецензенты — другие разработчики и заинтересованные участники сообщества — оставят в вашем запросе на включение изменений (Pull Request, PR) комментарии к отдельным строкам и/или общие замечания, чтобы помочь улучшить реализацию, документацию и стиль. Код каждого разработчика проекта проходит проверку. Мы воспринимаем её как дружеское обсуждение, в котором все учатся и которое повышает общее качество кода. Поэтому, пожалуйста, не позволяйте проверке отбить у вас желание участвовать: её цель — улучшить проект, а не критиковать вас. Мы очень благодарны за время, которое вы уделяете проекту! Подробнее см. рекомендации для рецензентов.

    • Чтобы обновить PR, внесите изменения в локальный репозиторий, создайте коммит, запустите тесты и только после их успешного прохождения отправьте изменения в свой форк. После отправки в ту же ветку PR обновится автоматически. Если вы не знаете, как исправить сбои тестов, можно всё равно отправить изменения и попросить помощи в комментарии к PR.

    • После каждого обновления PR запускаются службы непрерывной интеграции (CI): они собирают код, выполняют модульные тесты, измеряют покрытие и проверяют стиль кода вашей ветки. Перед слиянием PR проверки CI должны пройти успешно. При сбое причину можно узнать, нажав значок “failed” (красный крест) и изучив журнал сборки и тестов. Чтобы не расходовать ресурсы напрасно, проверяйте свою работу локально перед фиксацией изменений.

    • Перед слиянием PR должен быть одобрен хотя бы одним участником основной команды. Одобрение означает, что этот участник внимательно проверил изменения и PR готов к слиянию.

  5. Документирование изменений

    Если изменение влияет на поведение, видимое пользователю, помимо обновления строки документации функции и возможного описания в общей документации может потребоваться запись в примечаниях к выпуску. Для этого создайте небольшой файл с кратким описанием и поместите его в doc/release/upcoming_changes. Формат и правила именования файлов описаны в doc/release/upcoming_changes/README.rst.

    Если изменение предусматривает объявление возможности устаревшей, сначала обсудите его на GitHub или в списке рассылки. После достижения согласия выполните необходимые изменения согласно политике устаревания NEP 23.

  6. Перекрёстные ссылки на сообщения об ошибках

    Если PR связан с задачей или сообщением об ошибке, добавьте в комментарий GitHub текст xref gh-xxxx, где xxxx — номер задачи. Если PR решает её, замените xref на closes, fixes или другой вариант, поддерживаемый GitHub.

    В исходном коде обязательно предваряйте любую проблему или PR-ссылку с помощью gh-xxxx.

Для более подробного обсуждения читайте дальше и переходите по ссылкам внизу этой страницы.

Руководящие принципы #

  • Весь код должен быть покрыт тестами (подробнее см. покрытие тестами ниже).

  • Весь код должен быть документирован.

  • Ни одно изменение не принимается без проверки и одобрения участника основной команды. Если на ваш pull request не ответили в течение недели, вежливо напомните о нём в самом PR или в списке рассылки.

  • Не добавляйте уведомления об авторских правах в исходный код, не обсудив предварительно, нужны ли они. Как правило, весь код, который вы вносите в проект, распространяется под его лицензией.

Стилистические рекомендации #

  • Настройте редактор для соблюдения PEP 8: удаление пробелов в конце строк, отсутствие табуляции и т. п. Проверяйте код с помощью ruff.

  • Используйте типы данных NumPy вместо строк (np.uint8 вместо "uint8").

  • Соблюдайте следующие соглашения об импорте:

    import numpy as np

  • Рекомендации по коду на C см. в NEP 45.

Покрытие тестами#

Запросы на включение изменений (PR), затрагивающие код, должны добавлять новые тесты или менять существующие так, чтобы до исправления они завершались неудачно, а после него проходили. Перед отправкой PR следует запустить тесты.

Для локального запуска набора тестов NumPy требуются некоторые дополнительные пакеты, такие как pytest и hypothesis. Дополнительные зависимости тестирования перечислены в requirements/test_requirements.txt в каталоге верхнего уровня и могут быть легко установлены с помощью:

$ python -m pip install -r requirements/test_requirements.txt

В идеале тесты модуля должны охватывать весь его код, то есть покрытие операторов должно составлять 100%.

Чтобы измерить покрытие кода тестами, выполните:

$ spin test --coverage

Будет создан отчёт в формате html в каталоге build/coverage. Его можно открыть в браузере, например так:

$ firefox build/coverage/index.html

Сборка документации#

Чтобы создать HTML-документацию, используйте:

spin docs

Вы также можете запустить make из каталога doc. make help перечисляет все цели.

Необходимые зависимости и другие требования перечислены в разделе Сборка документации API NumPy и справочника.
