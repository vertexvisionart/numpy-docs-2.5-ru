Поддерживаемые платформы и версии #

NEP 29 определяет минимальный набор поддерживаемых версий Python. Обычно поддержку отдельной версии сохраняют немного дольше, чтобы не создавать трудностей другим проектам; решение принимает ответственный за выпуск.

  • macOS

    Для каждой версии Python мы стремимся поддерживать те же версии macOS, что Python.org и cibuildwheel. Мы собираем двоичные wheel-пакеты для macOS, совместимые с распространёнными вариантами установки Python: с python.org, python-build-standalone (такие установки выполняет uv), системным Python, conda-forge, Homebrew и MacPorts.

  • Windows

    Мы собираем 32- и 64-битные wheel-пакеты для Windows. Поддерживаются Windows 7, 8 и 10. При сборке NumPy используются наиболее удобные компиляторы: по состоянию на август 2025 года это MSVC для x86/x86-64 и Clang-cl для arm64, а также cibuildwheel и GitHub Actions.

  • Linux

    Мы собираем и публикуем на PyPI wheel-пакеты manylinux и musllinux для платформ x86-64 и aarch64. Пакеты для 32-битных платформ сейчас не предоставляются. Мы стремимся поддерживать самые старые версии, поддержка которых ещё не завершена, и обновляем их примерно синхронно с cibuildwheel. Подробнее см. pypa/manylinux и эту таблицу совместимости дистрибутивов.

  • BSD / Solaris / AIX

    Готовые двоичные wheel-пакеты на PyPI не предоставляются, однако ожидается, что сборка из исходного кода на этих платформах работает нормально.

Инструменты сборки#

Для сборки пакетов wheel мы используем следующие наборы инструментов:

  • Linux: мы используем компиляторы по умолчанию в образах Docker manylinux/musllinux, которые обычно представляют собой относительно недавнюю версию GCC.

  • macOS: используются компиляторы Apple Clang и версия XCode, установленные в образе среды выполнения GitHub Actions.

  • Windows: для x86 и x86-64 мы используем набор инструментов MSVC и Visual Studio по умолчанию, установленный в соответствующем образе среды выполнения GitHub Actions. В прошлом иногда приходилось использовать более старый набор инструментов, чтобы статическая библиотека libnpymath не вызывала проблем в SciPy. Если нужно узнать точные номера версий, изучите код numpy/numpy-release и журналы CI.

Минимальные версии компиляторов для сборки из исходного кода указаны в файле meson.build верхнего уровня.

OpenBLAS #

Большинство пакетов wheel скомпонованы с версией OpenBLAS из репозитория openblas-libs. Разделяемая библиотека (или DLL) включена в wheel и переименована, чтобы избежать конфликтов имён с другими библиотеками OpenBLAS, которые могут находиться в файловой системе.

Сборка документации#

Мы больше не собираем файлы pdf. Требования для сборки документации html те же, что и для обычной разработки. Подробнее см. README репозитория numpy/doc и пошаговые инструкции в doc/RELEASE_WALKTHROUGH.rst.

Публикация на PyPI#

Создание выпуска на PyPI и загрузка wheel-пакетов и исходного дистрибутива sdist автоматизированы в CI и используют доверенную публикацию PyPI. Подробности см. в README репозитория numpy/numpy-release и пошаговых инструкциях doc/RELEASE_WALKTHROUGH.rst.

Создание списков авторов / PR #

Чтобы скрипты могли обращаться к репозиторию NumPy на GitHub, понадобится персональный токен доступа: https://help.github.com/articles/creating-a-personal-access-token-for-the-command-line/. С ним список авторов и запросов на изменения можно сформировать командой spin changelog. Могут потребоваться дополнительные пакеты, например gitpython и pygithub.

Что входит в выпуск#

На PyPI мы публикуем пакеты wheel для ряда платформ, описанных выше, и исходный дистрибутив sdist.

В GitHub Releases мы публикуем тот же sdist (автоматически создаваемые GitHub архивы исходного кода неполны), а также примечания к выпуску и журнал изменений.

Процесс выпуска#

Согласовать график выпуска #

Обычный график функционального выпуска предусматривает два кандидата в релиз и окончательный выпуск. Сроки лучше сначала обсудить в списке рассылки, чтобы участники успели добавить свои коммиты. После определения даты создайте ветку maintenance/x.y.z, добавьте в main пустые примечания к следующему выпуску и обновите вехи (Milestones) в трекере задач.

Проверка устаревших возможностей#

Перед созданием ветки выпуска нужно проверить, что весь устаревший код, подлежащий удалению, удалён. Для всех новых объявлений об устаревании строка документации или предупреждение должны указывать версию будущего удаления.

Проверить номер версии C API #

Версию C API нужно отслеживать в трех местах.

  • numpy/_core/meson.build

  • numpy/_core/code_generators/cversions.txt

  • numpy/_core/include/numpy/numpyconfig.h

Процесс состоит из трёх шагов.

  1. Если API изменился, увеличьте C_API_VERSION в numpy/core/meson.build. API считается неизменным только тогда, когда любой код, скомпилированный с текущим API, обратно совместим с последней выпущенной версией NumPy. Изменения структур C или дополнения к открытому интерфейсу делают новый API несовместимым с предыдущей версией.

  2. Если C_API_VERSION на первом этапе изменился или изменился хэш API, файл cversions.txt необходимо обновить. Чтобы проверить хеш, запустите скрипт numpy/_core/cversions.py и запишите выведенный хеш API. Если этот хэш не соответствует последнему хешу в numpy/_core/code_generators/cversions.txt, хэш изменился. Используя соответствующий C_API_VERSION и хэш, добавьте новую запись в cversions.txt. Если версия API не менялась, но хэш отличается, вам нужно будет закомментировать предыдущую запись для этой версии API. Например, в NumPy 1.9 были добавлены аннотации, меняющие хеш, но API остался таким же, как и в 1.8. Хэш служит для проверки изменений API, но он не является окончательным.

    Если шаги 1 и 2 выполнены правильно, при сборке выпуска не должно появляться предупреждение «API mismatch detect at the beginning of the build».

  3. В numpy/_core/include/numpy/numpyconfig.h нужно добавить макрос NPY_X_Y_API_VERSION, где X и Y — мажорный и минорный номера выпуска. Значение следует увеличивать по сравнению с предыдущей версией только при объявлении устаревшими функций или макросов в заголовочных файлах.

Номер версии C ABI в numpy/_core/meson.build следует менять только при выпуске новой основной версии.

Проверьте примечания к выпуску#

Создайте примечания к выпуску с помощью towncrier и зафиксируйте изменения коммитом. При этом все фрагменты из doc/release/upcoming_changes будут удалены и появится doc/release/<version>-note.rst:

towncrier build --version "<version>"
git commit -m"Create release note"

Убедитесь, что примечания к выпуску обновлены.

Добавьте в примечания к выпуску раздел «Основные изменения». Упомяните некоторые из следующих пунктов:

  • основные новые возможности

  • устаревшие и удалённые возможности

  • поддерживаемые версии Python

  • для SciPy, поддерживаемые версии NumPy

  • Перспективы на ближайшее будущее

Перед выпуском #

Добавление и прекращение поддержки версий Python#

При добавлении или прекращении поддержки версий Python нужно не только изменить минимальную версию в pyproject.toml, но и отредактировать несколько файлов конфигурации и CI. Внесите изменения обычным PR в main и при необходимости перенесите их в ветки выпусков. Сейчас мы выпускаем wheel-пакеты для новых версий Python после первого кандидата в релиз Python, как только новую версию начинают поддерживать manylinux и cibuildwheel.

Перенос pull request в ветку сопровождения#

Изменения, назначенные этому выпуску, необходимо перенести в ветку maintenance/2.4.x.

Обновление контрольных этапов выпуска 2.4.0#

Просмотрите задачи и запросы на включение изменений, отнесённые к этапу 2.4.0, и перенесите их на более позднюю версию либо снимите привязку к этапу. Возможно, потребуется создать новый этап.

Проверьте репозиторий numpy-release#

Проверьте версию cibuildwheel в .github/workflows/wheels.yml и версии openblas в openblas_requirements.txt.

Создание PR для выпуска#

В PR для подготовки выпуска обычно нужно обновить или создать четыре документа:

  • Журнал изменений

  • Примечания к выпуску

  • Файл .mailmap

  • Файл pyproject.toml

Оформите эти изменения обычным pull request в ветку сопровождения. В него можно включить и другие небольшие исправления. Сообщение коммита может выглядеть так:

REL: Prepare for the NumPy 2.4.0 release

- Create 2.4.0-changelog.rst.
- Update 2.4.0-notes.rst.
- Update .mailmap.
- Update pyproject.toml

Задайте версию выпуска#

Проверьте файл pyproject.toml и установите версию релиза и обновите классификатор, если это необходимо:

$ gvim pyproject.toml

Проверьте файл doc/source/release.rst #

убедитесь, что примечания к выпуску добавлены в файл release.rst:

$ gvim doc/source/release.rst

Создайте журнал изменений #

Журнал изменений создаётся инструментом spin changelog, который собирает принятые запросы на изменения и форматирует их для выпуска:

$ spin changelog $GITHUB v2.3.0..maintenance/2.4.x > doc/changelog/2.4.0-changelog.rst

где GITHUB содержит ваш токен доступа GitHub. Текст нужно проверить на нестандартные имена участников. Также стоит заменить ссылки, если они есть в заголовках PR, моноширинным текстом: ссылки плохо переносятся в Markdown. Для исправления нестандартных имён нужно обновить файл .mailmap, что требует немало работы. Лучше заранее сделать несколько пробных запусков и обратиться к соответствующим участникам через issue на GitHub, чтобы получить нужные сведения.

Завершите подготовку примечаний к выпуску#

Если в doc/release/upcoming_changes/ есть фрагменты примечаний к выпуску, запустите spin notes: команда включит их в файл doc/source/release/notes-towncrier.rst и удалит исходные фрагменты:

$ spin notes
$ gvim doc/source/release/notes-towncrier.rst doc/source/release/2.4.0-notes.rst

После включения содержимого notes-towncrier в примечания к выпуску директиву .. include:: notes-towncrier.rst можно удалить. Примечания всегда требуют правки: нужно написать введение и выделить существенные изменения. Для корректирующих выпусков можно также добавить текст changelog; для первого выпуска он слишком длинный. Образец оформления см. в предыдущих примечаниях к выпускам.

Проверка сборок wheel#

После включения запроса с подготовкой выпуска откройте репозиторий numpy-release в браузере и вручную запустите рабочий процесс для ветки maintenance/2.4.x кнопкой Run workflow в разделе actions. Убедитесь, что адресат загрузки none выбран в раскрывающемся списке environment. Сборка пакетов wheel занимает около часа, но иногда GitHub работает очень медленно. Если отдельные сборки не удались по посторонним причинам, их можно повторить в интерфейсе GitHub Actions через re-run failed. После сборки проверьте результаты: число артефактов, ожидаемые имена пакетов wheel и т. д. Если всё в порядке, продолжайте выпуск.

Пошаговое руководство по выпуску#

В примерах ниже upstream означает основной репозиторий GitHub, а origin — его форк в вашей учётной записи. Если вы лишь клонировали репозиторий локально без создания форка, команды может потребоваться изменить. Также можно отредактировать .git/config и добавить upstream, если его ещё нет.

1. Пометьте коммит выпуска тегом#

Переключитесь на ветку выпуска, убедитесь, что она актуальна, и очистите репозиторий:

$ git checkout maintenance/2.4.x
$ git pull upstream maintenance/2.4.x
$ git submodule update
$ git clean -xdfq

Проверка корректности:

$ python3 -m spin test -m full

Создайте тег выпуска и отправьте его в удалённый репозиторий. Для этого необходимы права записи в репозиторий numpy:

$ git tag -a -s v2.4.0 -m"NumPy 2.4.0 release"
$ git push upstream v2.4.0

Если вам нужно удалить тег из-за ошибки:

$ git tag -d v2.4.0
$ git push --delete upstream v2.4.0

2. Сборка пакетов wheel и sdist#

Откройте репозиторий numpy-release в браузере и вручную запустите рабочий процесс ветки maintenance/2.4.x кнопкой Run workflow в actions. Убедитесь, что цель загрузки pypi выбрана в раскрывающемся списке environment. Сборка пакетов wheel занимает около часа, но иногда GitHub работает очень медленно. Если отдельные сборки завершились ошибкой по посторонним причинам, повторите их в интерфейсе GitHub Actions командой re-run failed. После сборки проверьте результаты: число артефактов, имена пакетов wheel и т. д. Если всё правильно, запустите загрузку.

3. Загрузка файлов в GitHub Releases#

Перейдите в numpy/numpy. Там должен быть тег v2.4.0; нажмите на него, затем на кнопку редактирования и измените заголовок на «v2.4.0 (<date>)». Файлы можно добавить двумя способами: через редактируемое текстовое поле или загрузкой двоичных файлов. Текстовое поле использует Markdown, поэтому преобразуйте примечания к выпуску из rst в md:

$ python tools/write_release.py 2.4.0

будет создан редактируемый файл release/README.md. Проверьте, правильно ли выглядит результат. Возможно, потребуется убрать лишние переносы строк и заменить некоторые ссылки моноширинным текстом. Затем скопируйте содержимое в буфер обмена и вставьте в текстовое поле. Для правильного отображения может понадобиться несколько попыток. Затем

  • Скачайте исходный дистрибутив sdist (numpy-2.4.0.tar.gz) с PyPI и загрузите его на GitHub как двоичный файл. Сделать это через pip нельзя.

  • Загрузите release/README.rst в виде двоичного файла.

  • Загрузите doc/changelog/2.4.0-changelog.rst в виде двоичного файла.

  • Установите флажок предварительного выпуска, если это предварительный выпуск.

  • Нажмите кнопку Publish release внизу.

Примечание

Убедитесь, что все три файла загружены и присутствуют, а текст выпуска заполнен полностью. Выпуски настроены как неизменяемые, поэтому впоследствии ошибки уже нельзя будет легко исправить.

4. Загрузите документацию на numpy.org (пропустите для предварительных выпусков)#

Примечание

Для публикации обновления вам понадобится токен личного доступа GitHub.

Этот шаг нужен только для окончательных выпусков; его можно пропустить для предварительных выпусков и большинства исправляющих выпусков. make merge-doc клонирует репозиторий numpy/doc в doc/build/merge и обновляет в нём документацию:

$ git clean -xdfq
$ git co v2.4.0
$ rm -rf doc/build  # want version to be current
$ python -m spin docs merge-doc --build
$ pushd doc/build/merge
Комментарии к примеру на русском
  • Нужна текущая версия

Если серия релиза новая, вам нужно будет добавить новый раздел на первую страницу doc/build/merge/index.html сразу после комментария «вставить здесь»:

$ gvim index.html +/'insert here'

Также обновите JSON-файл переключателя версий: добавьте новый выпуск и обновите версии, помеченные (stable) и preferred:

$ gvim _static/versions.json

Затем запустите update.py для обновления версии в _static:

$ python3 update.py

Новую документацию можно проверить в браузере, чтобы убедиться в работоспособности ссылок. Раскрывающийся список версий при этом не изменится: он получает данные из numpy.org:

$ firefox index.html  # or google-chrome, etc.
Комментарии к примеру на русском
  • Или google-chrome и т. п.

Обновите стабильную ссылку и обновите:

$ ln -sfn 2.4 stable
$ ls -l  # check the link
Комментарии к примеру на русском
  • Проверяем ссылку

Как только все покажется удовлетворительным, обновите, зафиксируйте и загрузите изменения:

$ git commit -a -m"Add documentation for v2.4.0"
$ git push git@github.com:numpy/doc
$ popd

5. Вернуть ветку сопровождения в состояние разработки (пропустить для предварительных выпусков)#

Создайте примечания к следующему выпуску и задайте в них версию. Это будет почти пустая заготовка:

$ git checkout -b begin-2.4.1 maintenance/2.4.x
$ cp doc/source/release/template.rst doc/source/release/2.4.1-notes.rst
$ gvim doc/source/release/2.4.1-notes.rst
$ git add doc/source/release/2.4.1-notes.rst

Добавить ссылку на новые примечания к выпуску:

$ gvim doc/source/release.rst

Обновление version в pyproject.toml :

$ gvim pyproject.toml

Создайте коммит с результатом, отредактируйте его сообщение, укажите включённые в него файлы и добавьте строку [skip cirrus] [skip actions], затем отправьте изменения:

$ git commit -a -m"MAINT: Prepare 2.4.x for further development"
$ git rebase -i HEAD^
$ git push origin HEAD

Откройте GitHub и создайте запрос на включение изменений (PR). Он должен быть быстро принят.

6. Объявить релиз на numpy.org (пропустить для предварительных выпусков) #

Предполагается, что вы создали форк numpy/numpy.org:

$ cd ../numpy.org
$ git checkout main
$ git pull upstream main
$ git checkout -b announce-numpy-2.4.0
$ gvim content/en/news.md

  • Для каждого выпуска перейдите в нижнюю часть страницы и добавьте ссылку отдельной строкой. Используйте предыдущие ссылки как образец.

  • Для выпуска *.0 в цикле:

    • Добавьте новый раздел вверху с кратким описанием новых функций и укажите на него ссылку на новости.

    • Измените поля newsHeader и date в начале news.md

    • Также измените buttonText в строке 14 файла content/en/config.yaml

создайте коммит и отправьте изменения:

$ git commit -a -m"announce the NumPy 2.4.0 release"
$ git push origin HEAD

Зайдите на GitHub и сделайте PR.

7. Объявление в списках рассылки#

О выпуске следует объявить в списках рассылки numpy-discussion и python-announce-list. За основу возьмите предыдущие объявления. Списки участников и PR совпадают со списками, подготовленными выше для примечаний к выпуску. При одновременной отправке в оба списка укажите python-announce-list в поле скрытой копии (BCC), чтобы ответы не попадали в этот список.

8. Обновление main после выпуска (кроме предварительных выпусков)#

Переключитесь на ветку main и перенесите в неё изменения документации. Если процедуры изменились или улучшились, стоит обновить и эти заметки:

$ git checkout -b post-2.4.0-release-update main
$ git checkout maintenance/2.4.x doc/source/release/2.4.0-notes.rst
$ git checkout maintenance/2.4.x doc/changelog/2.4.0-changelog.rst
$ git checkout maintenance/2.4.x .mailmap  # only if updated for release.
$ gvim doc/source/release.rst  # Add link to new notes
$ git status  # check status before commit
$ git commit -a -m"MAINT: Update main after 2.4.0 release."
$ git push origin HEAD
Комментарии к примеру на русском
  • Только если обновлено для выпуска.
  • Добавляем ссылку на новые примечания
  • Проверяем состояние перед коммитом

Зайдите на GitHub и сделайте PR.

Пошаговый пример работы с веткой#

В руководстве пошагово показано создание ветки NumPy 2.3.x в Linux. Команды можно копировать в командную строку, но номера 2.3 и 2.4 следует заменить нужными версиями. Перед созданием ветки желательно максимально актуализировать .mailmap; это может занять несколько недель.

Этот документ следует читать вместе с общим руководством по подготовке выпуска.

Работа с ветками#

Создайте ветку#

Это требуется только при создании новой ветки сопровождения. Начало нового цикла разработки в основной ветке следует отметить аннотированным тегом. Это делается так:

$ git checkout main
$ git pull upstream main
$ git commit --allow-empty -m'REL: Begin NumPy 2.4.0 development'
$ git push upstream HEAD

Если отправка не удалась из-за объединения новых PR, выполните следующие действия:

$ git pull --rebase upstream

и повторите отправку. После успешной отправки создайте тег:

$ git tag -a -s v2.4.0.dev0 -m'Begin NumPy 2.4.0 development'
$ git push upstream v2.4.0.dev0

затем создайте новую ветку и отправьте её в удалённый репозиторий:

$ git branch maintenance/2.3.x HEAD^
$ git push upstream maintenance/2.3.x

Подготовьте ветку main к дальнейшей разработке#

Создайте ветку для PR, подготавливающего main к дальнейшей разработке:

$ git checkout -b 'prepare-main-for-2.4.0-development' v2.4.0.dev0

Удалите фрагменты примечаний к выпуску:

$ git rm doc/release/upcoming_changes/[0-9]*.*.rst

Создайте заготовку примечаний к новому выпуску и добавьте её в указатель:

$ cp doc/source/release/template.rst doc/source/release/2.4.0-notes.rst
$ gvim doc/source/release/2.4.0-notes.rst  # put the correct version
$ git add doc/source/release/2.4.0-notes.rst
$ gvim doc/source/release.rst  # add new notes to notes index
$ git add doc/source/release.rst
Комментарии к примеру на русском
  • Укажите правильную версию
  • Добавляем новые примечания в указатель

Обновите cversions.txt, чтобы добавить текущий выпуск. На этом раннем этапе не должно быть нового хэша, просто добавьте комментарий после предыдущей практики:

$ gvim numpy/_core/code_generators/cversions.txt
$ git add numpy/_core/code_generators/cversions.txt

Проверьте результат, создайте коммит и отправьте его в удалённый репозиторий:

$ git status  # check work
$ git commit -m'REL: Prepare main for NumPy 2.4.0 development'
$ git push origin HEAD
Комментарии к примеру на русском
  • Проверяем результат

Теперь сделайте запрос на включение.
