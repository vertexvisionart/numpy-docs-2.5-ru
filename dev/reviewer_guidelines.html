Рекомендации для рецензентов#

Проверка открытых запросов на изменения (PR) помогает развивать проект. Мы приглашаем и внешних участников: это хороший способ познакомиться с кодовой базой.

Кто может быть рецензентом? #

Рецензировать изменения могут и люди вне команды NumPy. Мы рады участию экспертов в отдельных областях, например linalg или fft, и сопровождающих других проектов. Для рецензирования необязательно быть сопровождающим NumPy — членом команды с правом слияния PR.

Если мы ещё не знакомы, представьтесь в списке рассылки или Slack, прежде чем рецензировать запросы на включение изменений.

Правила общения#

  • Любой запрос на включение изменений — удачный или неудачный — это проявление щедрости. Начните с положительного комментария: так автор почувствует, что его вклад ценят, и ему будет легче воспринять ваши дальнейшие замечания. Возможно, и вам от этого станет приятнее.

  • По возможности начните с основных вопросов, чтобы автор видел, что его работу поняли. Не спешите сразу разбирать код построчно или начинать с мелких, хотя и повторяющихся, замечаний.

  • Вы представляете проект. NumPy уже определился, каким проектом хочет быть: открытым, чутким, приветливым, дружелюбным и терпеливым. Будьте доброжелательны к участникам.

  • Не стремитесь к идеалу в ущерб хорошему результату, особенно в документации. Если вы делаете множество мелких замечаний или придираетесь к стилю и грамматике, рассмотрите слияние PR после устранения всех существенных проблем. Затем либо отправьте отдельный коммит напрямую, если вы сопровождающий, либо сами откройте дополнительный PR.

  • Если вам нужна помощь с ответами при проверке кода, посмотрите стандартные ответы для рецензирования.

Контрольный список для рецензента#

  • Понятно ли предполагаемое поведение при любых условиях? Вот на что следует обратить внимание:

    • Что происходит с неожиданными входами, такими как пустые массивы или значения nan / inf?

    • Проверены ли аргументы оси или формы на int или tuples?

    • Проверяются ли необычные dtypes, если функция их поддерживает?

  • Следует ли улучшить имена переменных для обеспечения ясности или согласованности?

  • Нужно ли добавить комментарии или, наоборот, удалить бесполезные и избыточные?

  • Соответствует ли документация рекомендациям NumPy? Правильно ли оформлены строки документации?

  • Соответствует ли код рекомендациям NumPy по стилю?

  • Если вы сопровождаете проект и назначение ветки не очевидно из описания PR, добавьте краткое объяснение в сообщение коммита слияния. Если при этом закрывается задача, добавьте также «Closes gh-123», где 123 — её номер.

  • Изменения кода должен проверить и одобрить хотя бы один сопровождающий проекта, то есть участник с правом записи коммитов. Если вы первым проверили PR и одобряете изменения, отметьте это с помощью инструмента GitHub одобрения при рецензировании (approve review). Простой PR, например с очевидно корректным исправлением ошибки, можно слить сразу. Более сложный PR или изменение общедоступного API следует оставить открытым хотя бы на пару дней, чтобы другие сопровождающие тоже успели его проверить.

  • Если вы повторно проверяете уже одобренный PR, используйте тот же подход, что и для нового: сосредоточьтесь на существенных вопросах и не ограничивайтесь мелкими придирками. Если у вас есть права на коммит и вы считаете дальнейшую проверку ненужной, выполните слияние PR.

Для сопровождающих проекта#

  • Перед слиянием PR убедитесь, что все автоматические тесты CI проходят, а документация собирается без ошибок.

  • При конфликтах слияния попросите автора PR перенести ветку на main с помощью rebase.

  • Для PR, которые добавляют новые функции или в некотором роде сложны, подождите, по крайней мере, день или два, прежде чем объединить его. Таким образом, другие получают возможность комментировать до того, как код войдет. Рассмотрите возможность добавления его в заметки к выпуску.

  • Принимая изменения, участник с правом коммита отвечает за их соответствие правилам процесса разработки NumPy. Также необходимо убедиться, что новые возможности и нарушения обратной совместимости обсуждались в списке рассылки numpy-discussion.

  • Допустимо объединять коммиты или приводить в порядок сообщения коммитов PR, если они слишком запутаны. При этом сохраняйте имя исходного автора и проверяйте соответствие сообщений правилам NumPy.

  • Если вы хотите отклонить PR и причины очевидны, можно просто закрыть его с объяснением. В противном случае лучше сначала объяснить, почему вы считаете изменение неподходящим для NumPy, и дать второму разработчику с правом внесения изменений возможность высказаться или закрыть PR.

  • Если автор PR не отвечает на замечания в течение 6 месяцев, переведите PR в неактивную категорию и добавьте метку «inactive». После этого сопровождающий проекта может закрыть PR. О желании завершить работу над PR можно сообщить комментарием в любой момент, не дожидаясь истечения 6 месяцев.

  • Сопровождающим рекомендуется самостоятельно дорабатывать PR, если перед слиянием нужны лишь небольшие изменения, например исправления стиля кода или грамматических ошибок. Если работа над PR остановилась, сопровождающие могут вносить и более крупные изменения. Помните, что PR — совместная работа автора и рецензентов; иногда прямой push — лучший способ её завершить.

Изменения API#

Как уже упоминалось, большинство публичных изменений API должны обсуждаться заранее и часто с более широкой аудиторией (в списке рассылки или даже через NEP).

При изменении общедоступного C API учитывайте его обратную совместимость: любое дополнение должно быть совместимо по ABI с предыдущими версиями. Если это не так, необходимо добавить защитную проверку.

Например, структура PyUnicodeScalarObject содержит следующие поля:

#if NPY_FEATURE_VERSION >= NPY_1_20_API_VERSION
    char *buffer_fmt;
#endif
Комментарии к примеру на русском
  • Если NPY_FEATURE_VERSION >= NPY_1_20_API_VERSION

Это связано с тем, что поле buffer_fmt добавили в конец структуры в NumPy 1.20; все предшествующие поля сохранили совместимость ABI. Аналогично, любая функция, добавляемая в таблицу API в numpy/_core/code_generators/numpy_api.py, должна иметь аннотацию MinVersion. Например:

'PyDataMem_SetHandler':                 (304, MinVersion("1.22")),

Возможности, реализованные только в заголовочных файлах, например новый макрос, обычно не требуют защиты условной компиляцией.

Рабочий процесс GitHub #

При проверке запросов на изменения используйте подходящие средства GitHub для отслеживания рабочего процесса:

  • Завершив проверку, при необходимости попросите автора внести изменения: установите статус проверки «Changes requested» («Запрошены изменения»). На GitHub для этого откройте страницу pull request, вкладку Files changed и нажмите Review changes в правом верхнем углу.

  • Если текущее состояние вас устраивает, отметьте pull request как Approved (так же, как выбирается Changes requested). Сопровождающие могут вместо этого выполнить слияние pull request, если считают его готовым.

Может оказаться полезным иметь копию кода запроса на включение на своем компьютере, чтобы можно было поиграть с ним локально. Для этого можно использовать GitHub CLI , нажав кнопку Open with в правом верхнем углу страницы PR.

Если окружение для разработки уже настроено, теперь можно собрать код и запустить тесты.

Стандартные ответы при рецензировании#

Некоторые из этих ответов удобно сохранить в сохранённых ответах GitHub для рецензирования:

Вопрос по использованию
You are asking a usage question. The issue tracker is for bugs and new features.
I'm going to close this issue, feel free to ask for help via our [help channels](https://numpy.org/gethelp/).
Вы можете внести изменения в документацию
Please feel free to offer a pull request updating the documentation if you feel it could be improved.
Самодостаточный пример, воспроизводящий ошибку
Please provide a [self-contained example code](https://stackoverflow.com/help/mcve), including imports and data (if possible), so that other contributors can just run it and reproduce your issue.
Ideally your example code should be minimal.
Версии программного обеспечения
To help diagnose your issue, please paste the output of:
```
python -c 'import numpy; print(numpy.version.version)'
```
Thanks.
Блоки кода
Readability can be greatly improved if you [format](https://help.github.com/articles/creating-and-highlighting-code-blocks/) your code snippets and complete error messages appropriately.
You can edit your issue descriptions and comments at any time to improve readability.
This helps maintainers a lot. Thanks!
Ссылки на код
For clarity's sake, you can link to code like [this](https://help.github.com/articles/creating-a-permanent-link-to-a-code-snippet/).
Более понятные описание и заголовок
Please make the title of the PR more descriptive.
The title will become the commit message when this is merged.
You should state what issue (or PR) it fixes/resolves in the description using the syntax described [here](https://docs.github.com/en/github/managing-your-work-on-github/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword).
Комментарии к примеру на русском
  • linking-a-pull-request-to-an-issue-using-a-keyword).
Нужен регрессионный тест
Please add a [non-regression test](https://en.wikipedia.org/wiki/Non-regression_testing) that would fail at main but pass in this PR.
Не меняйте то, что не относится к задаче
Please do not change unrelated lines. It makes your contribution harder to review and may introduce merge conflicts to other pull requests.
