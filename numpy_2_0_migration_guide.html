Руководство по переходу на NumPy 2.0#

Этот документ объясняет, как обновить код для работы с NumPy 2.0. В нём рассматриваются изменения Python API и C API NumPy.

Примечание

NumPy 2.0 также нарушает двоичную совместимость. Если вы распространяете двоичные сборки пакета Python, зависящего от C API NumPy, см. рекомендации для NumPy 2.0.

Плагин Ruff#

Многие изменения из примечаний к выпуску 2.0 и этого руководства по миграции можно автоматически внести в зависимый код специальным правилом Ruff — NPY201.

Вам следует установить ruff>=0.4.8 и добавить правило NPY201 в ваш pyproject.toml:

[tool.ruff.lint]
select = ["NPY201"]

Вы также можете применить правило NumPy 2.0 непосредственно из командной строки:

$ ruff check path/to/code/ --select NPY201

Изменения повышения типов данных в NumPy#

В NumPy 2.0 изменено повышение типов — выбор общего типа при объединении данных разных типов — в соответствии с NEP 50. Подробности см. в этом NEP: в нём есть таблица примеров изменений и раздел об обратной совместимости.

Самое существенное изменение, влияющее на обратную совместимость: точность скаляров теперь сохраняется последовательно. Вот два примера:

  • np.float32(3) + 3. теперь возвращает float32, когда он ранее возвращал float64.

  • np.array([3], dtype=np.float32) + np.float64(3) теперь возвращает массив float64: повышенная точность скаляра не игнорируется.

При работе со скалярами с плавающей запятой это может снизить точность результата. Для целых чисел возможны ошибки или переполнения.

Для решения этой проблемы можно явно привести тип. Часто удобно также преобразовать значения в скаляры Python с помощью int(), float() или numpy_scalar.item().

Чтобы выявить изменения, можно включить предупреждения об изменившемся поведении. Используйте warnings.simplefilter, чтобы превратить предупреждение в ошибку и получить трассировку стека:

np._set_promotion_state("weak_and_warn")

что полезно при тестировании. К сожалению, такой запуск может выявить множество изменений, несущественных на практике.

Целочисленный тип по умолчанию в Windows#

Целое число по умолчанию, используемое NumPy, теперь является 64-битным во всех 64-битных системах (и 32-битным в 32-битной системе). По историческим причинам, связанным с Python 2, оно ранее было эквивалентно типу C long. Целое число по умолчанию теперь эквивалентно np.intp .

Большинство пользователей не затронет это изменение. Некоторые операции потребуют больше памяти, другие могут стать быстрее. Если возникают проблемы при вызове библиотеки на компилируемом языке, может помочь явное приведение к long, например arr = arr.astype("long", copy=False).

Библиотеки на C, Cython и подобных языках, взаимодействующие со скомпилированным кодом, могут потребовать обновления для обработки пользовательских данных, если на стороне C используется long или эквивалентный тип. Можно использовать intp и приводить входные данные либо поддерживать одновременно long и intp для лучшей совместимости с NumPy 1.x. При создании целочисленного массива на C или Cython новый макрос NPY_DEFAULT_INT принимает значение NPY_LONG или NPY_INTP в зависимости от версии NumPy.

Это изменение не затрагивает API NumPy для генерации случайных чисел.

Изменения C API#

Некоторые определения удалены или заменены как устаревшие либо неподдающиеся сопровождению. Некоторые новые определения API имеют разные значения во время выполнения в NumPy 2.0 и NumPy 1.x. Часть из них определена в numpy/_core/include/numpy/npy_2_compat.h, например NPY_DEFAULT_INT. Этот файл можно целиком или частично включить в свой проект, чтобы определения были доступны при компиляции с NumPy 1.x.

При необходимости с помощью PyArray_RUNTIME_VERSION >= NPY_2_0_API_VERSION можно явно реализовать разное поведение для NumPy 1.x и 2.0. (Заголовочный файл совместимости определяет его так, чтобы такое использование было возможно.)

Пожалуйста, дайте нам знать, если вам нужны дополнительные обходные пути здесь.

Изменена структура PyArray_Descr#

Одно из наиболее существенных изменений C-API — структура PyArray_Descr стала более непрозрачной. Это позволяет добавлять флаги и поддерживать размеры элементов, не ограниченные диапазоном int, а в будущем — улучшать структурированные типы данных, не обременяя новые типы их полями.

Код, использующий только номер типа и другие начальные поля, не затрагивается. Предполагается, что большая часть кода обращается преимущественно к полю ->elsize. Если dtype или дескриптор принадлежит массиву, например arr->descr->elsize, такое обращение лучше заменить на PyArray_ITEMSIZE(arr).

Если это невозможно, требуются новые функции доступа:

  • PyDataType_ELSIZE и PyDataType_SET_ELSIZE (обратите внимание, что в результате получается npy_intp, а не int).

  • PyDataType_ALIGNMENT

  • PyDataType_FIELDS, PyDataType_NAMES, PyDataType_SUBARRAY

  • PyDataType_C_METADATA

Для кода Cython следует использовать Cython 3: тогда это изменение не потребует правок. При компиляции только для NumPy 2 доступ к полям структуры elsize и alignment сохраняется.

Для компиляции и с 1.x, и с 2.x при использовании этих новых функций доступа, к сожалению, нужно либо определить их локально макросом, например:

#if NPY_ABI_VERSION < 0x02000000
  #define PyDataType_ELSIZE(descr) ((descr)->elsize)
#endif
Комментарии к примеру на русском
  • Если NPY_ABI_VERSION < 0x02000000

либо добавить npy2_compat.h в свой код и явно подключать этот файл при компиляции с NumPy 1.x (поскольку это новый API). При работе с NumPy 2 подключение файла ни на что не влияет.

Если вам нужна помощь или имеющихся функций недостаточно, создайте задачу в репозитории NumPy.

Пользовательские DType: существующие пользовательские типы должны определяться через PyArray_DescrProto с небольшими изменениями кода. См. примечание к PyArray_RegisterDataType.

Функциональность перенесена в заголовочные файлы, требующие import_array()#

Если раньше вы подключали только ndarraytypes.h, некоторые возможности теперь могут оказаться недоступными: потребуется подключить ndarrayobject.h или аналогичный заголовок. Он также нужен при включении npy_2_compat.h в исходный код вашего проекта, чтобы новые определения были доступны при компиляции с NumPy 1.x.

Функциональность, которая ранее не требовала импорта, включает в себя:

  • Функции для доступа к флагам dtype: PyDataType_FLAGCHK, PyDataType_REFCHK и связанным с ними NPY_BEGIN_THREADS_DESCR.

  • PyArray_GETITEM и PyArray_SETITEM.

Предупреждение

Для доступа ко всему API NumPy необходимо использовать механизм import_array() при работе с заголовком npy_2_compat.h. Скорее всего, ваш модуль расширения уже вызывает его. Если нет, мы добавили PyArray_ImportNumPyAPI() как предпочтительный способ импортировать API NumPy. Повторные вызовы этой функции обходятся дёшево, поэтому её можно вызывать в любом месте, где она нужна, если вы не хотите выполнять инициализацию при импорте модуля.

Увеличенное максимальное количество измерений #

Максимальное количество измерений (и аргументов) было увеличено до 64. Это влияет на макросы NPY_MAXDIMS и NPY_MAXARGS. Может быть хорошо пересмотреть их использование, и мы обычно рекомендуем вам не использовать эти макросы (особенно NPY_MAXARGS), чтобы будущая версия NumPy могла снять это ограничение на количество измерений.

NPY_MAXDIMS также использовался в C API для обозначения axis=None, в том числе в PyArray_AxisConverter. Теперь эта функция возвращает для оси -2147483648 — минимальное целочисленное значение. Другие функции могут выдавать ошибку AxisError: axis 64 is out of bounds for array of dimension; в этом случае нужно передавать NPY_RAVEL_AXIS вместо NPY_MAXDIMS. NPY_RAVEL_AXIS определён в заголовочном файле npy_2_compat.h и зависит от версии NumPy во время выполнения: он равен 32 в NumPy 1.x и -2147483648 в NumPy 2.x.

Комплексные типы — изменения базового типа#

Базовые типы C для всех комплексных типов заменены встроенными типами C99. Их расположение в памяти осталось таким же, как у типов NumPy 1.x, но API немного отличается: прямой доступ к полям, например c.real или c.imag, больше невозможен.

Для получения вещественной и мнимой частей комплексного числа рекомендуется использовать функции npy_creal и npy_cimag и их варианты для float и long double: они работают как с NumPy 1.x, так и с NumPy 2.x. Для установки вещественной и мнимой частей добавлены функции npy_csetreal и npy_csetimag, а также макросы совместимости NPY_CSETREAL и NPY_CSETIMAG и соответствующие варианты для float и long double.

В C++ базовый тип остаётся структурой (всё сказанное выше по-прежнему применимо).

Это влияет на Cython. Рекомендуется использовать его собственные определения типов cfloat_t, cdouble_t, clongdouble_t вместо типов NumPy, например npy_cfloat, если только вы не взаимодействуете с кодом C, использующим типы NumPy. При использовании собственных определений типов Cython можно по-прежнему обращаться к атрибутам c.real и c.imag, но операторы изменения на месте, например c.imag += 1, в режиме C++ больше не поддерживаются.

Поскольку NumPy 2 теперь подключает complex.h, в коде с переменной по имени I может возникать ошибка вида

Для использования имени I теперь требуется #undef I.

Примечание

В NumPy 2.0.1 временно присутствовало #undef I для пользователей, которые ещё не подключали complex.h.

Изменения пространств имён#

В NumPy 2.0 некоторые функции, модули и константы перемещены или удалены, чтобы сделать пространство имён NumPy удобнее: убрать ненужные и устаревшие средства и уточнить, какие части NumPy считаются внутренними. Рекомендации по переходу приведены в таблицах ниже. В большинстве случаев достаточно использовать предложенную альтернативу, совместимую с предыдущими версиями.

Подробнее см. NEP 52 — Упорядочение Python API в NumPy 2.0.

Пространство имён numpy.lib#

Большинство функций np.lib есть и в основном пространстве имён, которое является их основным местом. Чтобы доступ к общедоступным функциям был однозначным, np.lib теперь почти пусто и содержит лишь несколько специализированных подмодулей, классов и функций:

  • подмодули array_utils, format, introspect, mixins, npyio, scimath и stride_tricks,

  • классы Arrayterator и NumpyVersion,

  • Функции add_docstring и add_newdoc

  • tracemalloc_domain постоянная.

Если вы получаете AttributeError при доступе к атрибуту из np.lib, вам следует попытаться получить доступ к нему из основного пространства имен np. Если элемент также отсутствует в основном пространстве имен, вы используете закрытый член. Вам следует либо использовать существующий API, либо, если это невозможно, обратиться к нам с просьбой восстановить удаленную запись.

Пространство имён numpy.core#

Пространство имён np.core теперь официально внутреннее и переименовано в np._core. Не следует напрямую обращаться к членам _core: используйте для нужного атрибута основное пространство имён. Структура модуля _core в будущем может меняться без уведомления, в отличие от публичных модулей, соблюдающих установленный период устаревания. Если нужного элемента нет и в основном пространстве имён, используйте существующий API, а если это невозможно, обратитесь к нам с просьбой восстановить удалённый элемент.

Методы ndarray и скаляров#

Несколько методов из скалярных классов np.ndarray и np.generic были удалены. В таблице ниже представлены замены удаленных элементов:

Пространство имён numpy.strings#

Создано новое пространство имён numpy.strings, в котором большинство строковых операций реализовано как универсальные функции. Прежнее пространство имён numpy.char по-прежнему доступно и по возможности использует новые универсальные функции для повышения производительности. В дальнейшем рекомендуется использовать функции strings. Пространство имён char может быть объявлено устаревшим в будущем.

Другие изменения #

Примечание о файлах pickle#

NumPy 2.0 поддерживает загрузку файлов pickle, созданных в NumPy 1.26, и наоборот. В NumPy 1.25 и более ранних версиях загрузка файла pickle, созданного в NumPy 2.0, вызывает исключение.

Адаптация к изменениям именованного аргумента copy#

Изменения поведения именованного параметра copy в asarray, array и ndarray.__array__ могут потребовать следующих изменений:

  • Код, использующий np.array(..., copy=False), в большинстве случаев можно изменить на np.asarray(...). В более старом коде np.array обычно использовался именно так, потому что он имел меньше накладных расходов, чем стандартное поведение копирования при необходимости np.asarray. Это уже не так, и np.asarray является предпочтительной функцией.

  • Если код должен явно передавать None/False в значении «копировать при необходимости» с совместимостью с NumPy 1.x и 2.x, пример реализации см. в scipy#20172.

  • В сигнатуру любого метода __array__ объекта, подобного массиву и не принадлежащего NumPy, нужно добавить именованные параметры dtype=None и copy=None. Это будет работать и со старыми версиями NumPy, хотя они никогда не передают аргумент copy. Если эти параметры добавлены в сигнатуру __array__, то для:

    • copy=True и любое значение dtype всегда возвращают новую копию.

    • copy=None — создать копию, если это необходимо (например, из-за dtype),

    • copy=False: создание копии запрещено. Если копия нужна для получения массива NumPy или соблюдения dtype, следует вызвать исключение ValueError.

Написание кода, зависящего от версии NumPy#

Явное ветвление по версии numpy требуется редко: обычно код можно переписать так, чтобы он одновременно работал с 1.x и 2.0. Если это всё же необходимо, рекомендуем следующий шаблон с numpy.lib.NumpyVersion:

# example with AxisError, which is no longer available in
# the main namespace in 2.0, and not available in the
# `exceptions` namespace in <1.25.0 (example uses <2.0.0b1
# for illustrative purposes):
if np.lib.NumpyVersion(np.__version__) >= '2.0.0b1':
    from numpy.exceptions import AxisError
else:
    from numpy import AxisError

  • Пример с AxisError: в версии 2.0 он больше недоступен
  • в основном пространстве имён, а до 1.25.0 недоступен в
  • пространстве имён `exceptions`. В примере используется <2.0.0b1
  • в иллюстративных целях:

Этот шаблон будет корректно работать, в том числе с кандидатами на выпуск NumPy, что важно в период выпуска 2.0.0.
