Параллельное генерирование случайных чисел #

Существует четыре основных стратегии, которые могут быть использованы для создания повторяемых псевдослучайных чисел в нескольких процессах (локальных или распределенных).

Создание дочерних последовательностей SeedSequence#

NumPy позволяет создавать новые, с очень высокой вероятностью независимые экземпляры BitGenerator и Generator с помощью их метода spawn(). Это создание дочерних экземпляров реализуется объектом SeedSequence, который используется для инициализации потока случайных чисел генератора битов.

SeedSequence реализует алгоритм, который обрабатывает предоставленное пользователем начальное значение seed — обычно целое число некоторого размера — и преобразует его в начальное состояние BitGenerator. Для преобразования исходных значений низкого качества в начальные состояния высокого качества используются методы хеширования, обеспечивающие такой результат по крайней мере с очень высокой вероятностью.

Например, состояние MT19937 состоит из 624 целых uint32. Простейшая инициализация 32-разрядным числом могла бы записать его в последний элемент, оставив остальные нулевыми. Для MT19937 это допустимое, но плохое состояние: алгоритм вихря Мерсенна плохо работает при слишком большом числе нулей. Аналогично, два соседних 32-разрядных начальных значения, например 12345 и 12346, дали бы очень похожие потоки.

SeedSequence избегает этих проблем, используя последовательности целочисленных хешей с хорошим лавинным эффектом: изменение любого входного бита примерно с вероятностью 50% меняет любой выходной бит. Два очень близких начальных значения с высокой вероятностью создают сильно различающиеся начальные состояния. Кроме того, можно передавать целые числа произвольного размера или их списки. SeedSequence перемешивает все переданные биты и создаёт столько битов, сколько требуется использующему её BitGenerator для инициализации.

В совокупности эти свойства позволяют безопасно сочетать обычное начальное значение, заданное пользователем, с простыми возрастающими счётчиками и получать состояния BitGenerator, с очень высокой вероятностью независимые друг от друга. Это можно оформить в API, которым легко пользоваться правильно и трудно ошибочно. Хотя SeedSequence пытается решить многие проблемы малых пользовательских начальных значений, мы по-прежнему рекомендуем генерировать начальные значения со 128 битами энтропии через secrets.randbits, чтобы избежать оставшихся смещений, обусловленных выбором чисел человеком.

from numpy.random import SeedSequence, default_rng

ss = SeedSequence(12345)

# Spawn off 10 child SeedSequences to pass to child processes.
child_seeds = ss.spawn(10)
streams = [default_rng(s) for s in child_seeds]
Комментарии к примеру на русском
  • Создаём 10 дочерних SeedSequence для передачи дочерним процессам.

Напрямую использовать SeedSequence необязательно. Потоки streams выше можно создать непосредственно из родительского генератора через spawn:

parent_rng = default_rng(12345)
streams = parent_rng.spawn(10)

Дочерние объекты тоже могут порождать свои дочерние объекты и так далее. У каждого дочернего объекта есть SeedSequence, в котором положение объекта в дереве порождения смешивается с заданным пользователем начальным значением. Это создаёт независимые с очень высокой вероятностью потоки.

grandchildren = streams[0].spawn(4)

Эта возможность позволяет локально решать, когда и как разделять потоки случайных чисел, без координации между процессами. Не нужно заранее резервировать участки последовательности для предотвращения перекрытия или запрашивать потоки у общего глобального сервиса. Такая схема «древовидного хеширования» не уникальна для NumPy, но пока мало распространена. Всё более гибкие средства распараллеливания Python хорошо сочетаются с этим подходом.

В этой схеме можно оценить верхнюю границу вероятности коллизии, зная число создаваемых потоков. SeedSequence по умолчанию хеширует входные данные — начальное значение и путь в дереве порождения — в 128-битный пул. Пессимистическая оценка вероятности коллизии в этом пуле ([1]) составляет примерно \(n^2*2^{-128}\), где n — число порождённых потоков. Даже если программа использует целый миллион потоков, то есть около \(2^{20}\), вероятность совпадения хотя бы одной пары составляет примерно \(2^{-88}\): такой вероятностью можно уверенно пренебречь ([2]).

[1]

Алгоритм тщательно спроектирован так, чтобы исключить несколько возможных причин совпадения состояний. Например, при одном уровне порождения дочерних генераторов все состояния гарантированно уникальны. Однако проще грубо оценить наивную верхнюю границу вероятности и учитывать, что на деле вероятность ещё ниже.

[2]

В этом расчёте количеством чисел, получаемых из каждого потока, в основном можно пренебречь. В разделе Переход с PCG64 на PCG64DXSM приведены технические подробности о PCG64. У остальных предоставляемых генераторов есть дополнительная защита от перекрытия, если пулы SeedSequence отличаются хотя бы одним битом. У PCG64DXSM есть \(2^{127}\) отдельных циклов, определяемых начальным значением, помимо позиции в каждом цикле длины \(2^{128}\). Для перекрытия нужно попасть в один и тот же или близкий цикл и выбрать близкую позицию внутри него. Philox имеет полностью независимые циклы, определяемые начальным значением. SFC64 включает 64-битный счётчик, поэтому каждое уникальное начальное значение отстоит от любого другого как минимум на \(2^{64}\) итераций. Наконец, у MT19937 просто невообразимо большой период. Поэтому сбой проявился бы через внутреннюю коллизию SeedSequence.

Последовательность целочисленных начальных значений генератора#

Как обсуждалось в предыдущем разделе, SeedSequence принимает не только целое начальное значение, но и последовательность неотрицательных целых чисел произвольной длины. Проявив некоторую осторожность, эту возможность можно использовать для создания специальных схем получения надёжных параллельных потоков псевдослучайных чисел, с гарантиями, сопоставимыми с созданием дочерних генераторов.

Например, часто рабочему процессу передают одно целое число — исходное начальное значение генератора для всего вычисления, а также целочисленный идентификатор исполнителя (или более подробный идентификатор: задания, пакета и т. п.). Если эти идентификаторы уникальны и формируются детерминированно, можно получить воспроизводимые параллельные потоки псевдослучайных чисел, объединив идентификатор и исходное начальное значение в список.

# default_rng() and each of the BitGenerators use SeedSequence underneath, so
# they all accept sequences of integers as seeds the same way.
from numpy.random import default_rng

def worker(root_seed, worker_id):
    rng = default_rng([worker_id, root_seed])
    # Do work ...

root_seed = 0x8c3c010cb4754c905776bdac5ee7501
results = [worker(root_seed, worker_id) for worker_id in range(10)]
Комментарии к примеру на русском
  • default_rng() и все BitGenerator используют SeedSequence, поэтому
  • одинаковым образом принимают последовательности целых чисел как начальные значения.
  • Выполняем работу…

Этот подход может заменить ряд применявшихся ранее небезопасных стратегий, в которых исходное начальное значение и идентификатор объединяют в одно целочисленное начальное значение. Например, пользователи часто прибавляют идентификатор рабочего процесса к исходному начальному значению, особенно в коде со старым RandomState.

# UNSAFE! Do not do this!
worker_seed = root_seed + worker_id
rng = np.random.RandomState(worker_seed)
Комментарии к примеру на русском
  • НЕБЕЗОПАСНО! Так делать нельзя!

В одном запуске такой параллельной программы у каждого рабочего процесса действительно будет отдельный поток случайных чисел. Однако при повторных запусках с другими начальными значениями наборы начальных значений рабочих процессов могут пересекаться. По опыту автора, корневое начальное значение при повторном запуске часто просто увеличивают на 1 или 2. Если значения для рабочих процессов также выводятся небольшими приращениями их идентификаторов, часть процессов даст одинаковые результаты, внося смещение в общую совокупность результатов.

Если объединить идентификатор рабочего процесса и исходное начальное значение (root seed) в список целых чисел, этот риск исчезает. Даже упрощённые способы задания начального состояния при этом остаются достаточно безопасными.

Эта схема требует уникальных дополнительных идентификаторов, создаваемых детерминированно. Для этого может понадобиться координация рабочих процессов. Переменные идентификаторы рекомендуется размещать перед неизменным корневым seed. spawn добавляет целые числа после seed пользователя. Поэтому, если вы сочетаете этот специально подобранный механизм с созданием дочерних последовательностей либо передаёте объекты библиотеке, которая может их создавать, немного безопаснее ставить идентификаторы рабочих процессов в начало, а не в конец, чтобы избежать совпадений.

# Good.
worker_seed = [worker_id, root_seed]

# Less good. It will *work*, but it's less flexible.
worker_seed = [root_seed, worker_id]
Комментарии к примеру на русском
  • Верно.
  • Менее удачный вариант. Он *работает*, но менее гибок.

С учётом этих оговорок гарантии защиты от коллизий примерно такие же, как при порождении дочерних генераторов, рассмотренном в предыдущем разделе. Алгоритмические механизмы одинаковы.

Независимые потоки случайных чисел#

Philox — генератор случайных чисел на основе счётчика. Он получает значения, шифруя возрастающий счётчик с помощью слабых криптографических примитивов. Начальное значение определяет ключ шифрования. Разные ключи создают разные независимые потоки. Philox позволяет обойти алгоритм инициализации и напрямую задать 128-битный ключ. Даже похожие, но различающиеся ключи создают независимые потоки.

import secrets
from numpy.random import Philox

# 128-bit number as a seed
root_seed = secrets.getrandbits(128)
streams = [Philox(key=root_seed + stream_id) for stream_id in range(10)]
Комментарии к примеру на русском
  • 128-битное число как начальное значение

Эта схема требует, чтобы вы избегали повторного использования идентификаторов потоков. Это может потребовать координации между параллельными процессами.

Скачкообразный переход состояния BitGenerator#

jumped продвигает состояние BitGenerator так, как если бы было сгенерировано большое число случайных значений, и возвращает новый экземпляр с этим состоянием. Число таких значений зависит от BitGenerator и лежит в диапазоне от \(2^{64}\) до \(2^{128}\). Кроме того, число условно сгенерированных значений зависит от разрядности случайного числа, выдаваемого конкретным BitGenerator по умолчанию. Ниже перечислены BitGenerator с поддержкой jumped, их периоды, размеры скачков и разрядность выдаваемых по умолчанию беззнаковых случайных чисел.

Величина перехода составляет \((\phi-1)*2^{128}\), где \(\phi\) — золотое сечение. По мере переходов с циклическим обходом периода фактические расстояния между соседними потоками постепенно становятся меньше величины перехода. Однако такое использование золотого сечения — классический способ построения последовательности с малой дискрепантностью, оптимально распределяющей состояния по периоду. За всю жизнь вы не успеете выполнить столько переходов, чтобы расстояния сократились достаточно для перекрытия потоков.

jumped может использоваться для создания длинных блоков, которые должны быть достаточно длинными, чтобы не перекрываться.

import secrets
from numpy.random import PCG64

seed = secrets.getrandbits(128)
blocked_rng = []
rng = PCG64(seed)
for i in range(10):
    blocked_rng.append(rng.jumped(i))

При использовании jumped нужно быть осторожным, чтобы не перейти к уже использованному потоку. В приведенном выше примере позже нельзя будет использовать blocked_rng[0].jumped(), поскольку он будет перекрываться с blocked_rng[1]. Как и в случае с независимыми потоками, если основной процесс хочет отделить еще 10 потоков путем перехода, то ему нужно начать с range(10, 20), иначе он воссоздаст те же самые потоки. С другой стороны, если вы тщательно сконструируете потоки, то у вас гарантированно будут потоки, которые не перекрываются.
