Рекомендации по тестированию#

Введение#

До выпуска 1.15 NumPy использовал систему тестирования nose; теперь используется pytest. Старая система сохраняется для поддержки зависимых проектов, которые ею пользуются, но все тесты самого NumPy должны использовать pytest.

Наша цель — обеспечить каждый модуль и пакет NumPy полным набором модульных тестов. Они должны проверять всю функциональность каждой процедуры и её устойчивость к ошибочным или неожиданным входным аргументам. Хорошо продуманные тесты с хорошим покрытием значительно облегчают рефакторинг. При обнаружении новой ошибки следует написать тест для конкретного случая и добавить его в набор тестов, чтобы ошибка не могла незаметно появиться снова.

Примечание

SciPy использует средства тестирования из numpy.testing, поэтому все приведённые ниже примеры NumPy применимы и к SciPy

Тестирование NumPy #

NumPy можно протестировать разными способами, выбирайте любой, который вам удобен.

Запуск тестов из Python#

Установленный NumPy можно проверить через numpy.test. Например, для запуска полного набора тестов NumPy используйте:

>>> import numpy
>>> numpy.test(label='slow')

Метод test может принимать два или более аргумента. Первый, label, — строка, указывающая, что тестировать; второй, verbose, — целое число, задающее подробность вывода. Подробнее см. строку документации numpy.test. По умолчанию label равен ‘fast’: запускаются стандартные тесты. Значение ‘full’ запускает весь набор, включая медленные тесты. Если verbose не больше 1, выводятся только информационные сообщения о выполняемых тестах; при большем значении также выдаются предупреждения об отсутствующих тестах. Чтобы запустить все тесты и узнать, какие модули ими не покрыты:

>>> numpy.test(label='full', verbose=2)  # or numpy.test('full', 2)
Комментарии к примеру на русском
  • Или numpy.test('full', 2)

Наконец, если вы заинтересованы только в тестировании подмножества NumPy, например, модуля _core, используйте следующее:

>>> numpy._core.test()

Запуск тестов из командной строки#

Если вы собираете NumPy для работы над самим NumPy, используйте утилиту spin.

Чтобы запустить полный набор тестов NumPy:

$ spin test -m full

Тестирование подмножества NumPy :

$ spin test -t numpy/_core/tests

Подробнее о тестировании см. Тестирование сборок

Запуск тестов в нескольких потоках#

Для нагрузочной проверки потокобезопасности NumPy набор тестов можно запустить через pytest-run-parallel. Установка pytest-run-parallel:

$ pip install pytest-run-parallel

Чтобы запустить набор тестов в нескольких потоках:

$ spin test -p auto # have pytest-run-parallel detect the number of available cores
$ spin test -p 4 # run each test under 4 threads
$ spin test -p auto -- --skip-thread-unsafe=true # run ONLY tests that are thread-safe
Комментарии к примеру на русском
  • Пусть pytest-run-parallel определит число доступных ядер
  • Запускаем каждый тест в 4 потоках
  • Запускаем ТОЛЬКО потокобезопасные тесты

Новые тесты стоит проверять под pytest-run-parallel, поскольку этот пакет используется в заданиях CI. Советы по написанию потокобезопасных тестов приведены здесь.

Примечание

Лучше запускать pytest-run-parallel со сборкой Python без GIL версии 3.14 или новее. При использовании обычной сборки Python нужно установить переменные окружения PYTHON_CONTEXT_AWARE_WARNINGS и PYTHON_THREAD_INHERIT_CONTEXT в 1.

Запуск doctest-тестов#

Документация NumPy содержит примеры кода, «доктесты». Чтобы проверить корректность примеров, установите пакет scipy-doctest:

$ pip install scipy-doctest

И запустите одну из них:

$ spin check-docs -v
$ spin check-docs numpy/linalg
$ spin check-docs -- -k 'det and not slogdet'

При использовании spin test тесты doctest не запускаются.

Другие методы проведения тестов #

Запуск тестов с использованием ваших любимых IDE, таких как vscode или pycharm

Написание собственных тестов#

Если вы пишете код для включения в NumPy, добавляйте тесты по мере разработки. Для каждого модуля Python, модуля расширения или подпакета в каталоге NumPy должен быть соответствующий файл test_<name>.py. Pytest ищет в этих файлах тестовые методы с именами test* и тестовые классы с именами Test*.

Предположим, у вас есть модуль NumPy numpy/xxx/yyy.py, содержащий функцию zzz(). Чтобы протестировать эту функцию, вы должны создать тестовый модуль под названием test_yyy.py. Если вам нужно протестировать только один аспект zzz, вы можете просто добавить тестовую функцию:

def test_zzz():
    assert zzz() == 'Hello from zzz'

Чаще всего нам нужно группировать несколько тестов вместе, поэтому мы создаем тестовый класс:

# import xxx symbols
from numpy.xxx.yyy import zzz
import pytest

class TestZzz:
    def test_simple(self):
        assert zzz() == 'Hello from zzz'

    def test_invalid_parameter(self):
        with pytest.raises(ValueError, match='.*some matching regex.*'):
            ...
Комментарии к примеру на русском
  • Импортируем символы xxx

В этих тестовых методах оператор assert или специализированная функция проверки позволяет проверить некоторое предположение. Если проверка не проходит, тест завершается неудачно. Распространённые функции проверки:

  • numpy.testing.assert_equal для проверки точного поэлементного равенства массива результатов и эталона,

  • numpy.testing.assert_allclose — для проверки приближённого поэлементного равенства массива результатов и эталона, то есть с заданными относительным и абсолютным допусками; и

  • numpy.testing.assert_array_less для поэлементной проверки строгого неравенства между массивом результата и эталонным массивом.

По умолчанию эти проверочные функции сравнивают только числовые значения массивов. Чтобы дополнительно проверить dtype и форму, используйте strict=True.

Для собственных проверок используйте инструкцию Python assert. pytest внутренне переписывает инструкции assert, чтобы при сбое выдавать информативные сообщения, поэтому они предпочтительнее устаревшего варианта numpy.testing.assert_. Обычные инструкции assert игнорируются при запуске Python в оптимизированном режиме с -O, но при выполнении тестов через pytest это не проблема.

Аналогично, функции pytest pytest.raises и pytest.warns следует предпочитать их широко используемым устаревшим аналогам numpy.testing.assert_raises и numpy.testing.assert_warns. Эти версии также принимают параметр match, который следует всегда использовать для точного сопоставления с ожидаемым предупреждением или ошибкой.

Функции и методы test_ не должны иметь строки документации: они затрудняют определение теста по выводу набора тестов, запущенного с verbose=2 или аналогичной настройкой подробности. Описывайте назначение теста обычными комментариями (#), чтобы читателю, незнакомому с кодом, было проще его понять.

Кроме того, значительная часть NumPy — исторический код, изначально написанный без модульных тестов, поэтому некоторые модули всё ещё не имеют тестов. Вы можете выбрать любой из них и написать для него тесты.

Использование кода C в тестах#

NumPy предоставляет обширный C API. Для его тестирования используются модули расширения на C, которые работают только с официальным C API, как будто ничего не знают о внутреннем устройстве NumPy. Примеры — тесты пользовательского типа rational в _rational_tests и механизма ufunc в _umath_tests, входящие в двоичный дистрибутив. Начиная с версии 1.21 можно также писать в тестах фрагменты кода C: они локально компилируются в модули расширения и загружаются в Python.

numpy.testing.extbuild.build_and_import_extension(modname, functions, *, prologue='', build_dir=None, include_dirs=None, more_init='')#

Собирает и импортирует модуль расширения C modname из списка фрагментов функций functions.

Параметры:
functionsсписок фрагментов

Каждый фрагмент — последовательность из func_name, соглашения о вызове и фрагмента кода.

prologueстрока

Код, размещаемый перед остальным кодом, обычно дополнительные макросы #include или #define.

build_dirpathlib.Path

Каталог сборки модуля, обычно временный

include_dirsсписок

Дополнительные каталоги поиска заголовочных файлов при компиляции

more_initстрока

Код, включаемый в функцию инициализации модуля PyMODINIT_FUNC

Возвращаемые значения:
out: модуль

Модуль будет загружен и готов к использованию.

Примеры

>>> functions = [("test_bytes", "METH_O", """
    if ( !PyBytesCheck(args)) {
        Py_RETURN_FALSE;
    }
    Py_RETURN_TRUE;
""")]
>>> mod = build_and_import_extension("testme", functions)
>>> assert not mod.test_bytes('abc')
>>> assert mod.test_bytes(b'abc')

Метки тестов#

Немаркированные тесты, подобные приведенным выше, выполняются при запуске numpy.test() по умолчанию. Если вы хотите пометить свой тест как медленный и, следовательно, зарезервированный для полного запуска numpy.test(label='full'), вы можете пометить его с помощью pytest.mark.slow:

import pytest

@pytest.mark.slow
def test_big(self):
    print('Big, slow test')

Аналогично для методов:

class test_zzz:
    @pytest.mark.slow
    def test_simple(self):
        assert_(zzz() == 'Hello from zzz')

Методы подготовки и завершения тестов#

Раньше NumPy использовала механизм setup и teardown в стиле xunit, предоставляемый pytest. Теперь рекомендуется явно вызывать методы подготовки и завершения из тех тестов, которым они нужны:

class TestMe:
    def setup(self):
        print('doing setup')
        return 1

    def teardown(self):
        print('doing teardown')

    def test_xyz(self):
        x = self.setup()
        assert x == 1
        self.teardown()

Этот подход безопасен при работе с потоками и позволяет запускать тесты через pytest-run-parallel. Использование подготовительных фикстур pytest, например методов настройки xunit, обычно не является потокобезопасным и, вероятно, приведёт к сбоям проверки потокобезопасности.

pytest поддерживает более универсальные фикстуры с разными областями действия, которые можно автоматически подключать через специальные аргументы. Например, аргумент с именем tmp_path используется в тестах для создания временных каталогов. Однако фикстуры следует применять умеренно.

Параметрические тесты #

Одна очень приятная особенность pytest — это простота тестирования различных значений параметров с помощью декоратора pytest.mark.parametrize. Например, предположим, что вы хотите протестировать linalg.solve для всех комбинаций трех размеров массива и двух типов данных:

@pytest.mark.parametrize('dimensionality', [3, 10, 25])
@pytest.mark.parametrize('dtype', [np.float32, np.float64])
def test_solve(dimensionality, dtype):
    np.random.seed(842523)
    A = np.random.random(size=(dimensionality, dimensionality)).astype(dtype)
    b = np.random.random(size=dimensionality).astype(dtype)
    x = np.linalg.solve(A, b)
    eps = np.finfo(dtype).eps
    assert_allclose(A @ x, b, rtol=eps*1e2, atol=0)
    assert x.dtype == np.dtype(dtype)

Doctest#

Doctest позволяет удобно документировать поведение функции и одновременно проверять его. В строку документации функции можно включить пример интерактивного сеанса Python, а система тестирования выполнит этот пример и сравнит фактический вывод с ожидаемым.

Тесты из документации (doctests) можно запустить, добавив аргумент doctests к вызову test(). Например, чтобы запустить все тесты, включая doctests, для numpy.lib:

>>> import numpy as np
>>> np.lib.test(doctests=True)

Примеры doctest выполняются так, словно запущен новый интерпретатор Python, выполнивший import numpy as np. Для тестов подпакета NumPy этот подпакет уже импортирован. Например, для теста в numpy/linalg/tests/ пространство имён создаётся так, будто from numpy import linalg уже выполнено.

tests/#

Вместо того, чтобы хранить код и тесты в одном каталоге, мы помещаем все тесты для данного подпакета в подкаталог tests/. Для нашего примера, если он еще не существует, вам нужно будет создать каталог tests/ в numpy/xxx/. Так что путь для test_yyy.py - это numpy/xxx/tests/test_yyy.py.

После написания numpy/xxx/tests/test_yyy.py можно запустить тесты, перейдя в каталог tests/ и набрав:

python test_yyy.py

Или, если вы добавите numpy/xxx/tests/ в путь Python, вы можете запускать тесты в интерпретаторе в интерактивном режиме следующим образом:

>>> import test_yyy
>>> test_yyy.test()

__init__.py и setup.py #

Однако обычно добавление каталога tests/ в путь Python нежелательно. Вместо этого было бы лучше вызвать тест прямо из модуля xxx. Для этого просто поместите следующие строки в конец файла __init__.py вашего пакета:

...
def test(level=1, verbosity=1):
    from numpy.testing import Tester
    return Tester().test(level, verbosity)

Вам также нужно будет добавить каталог тестов в разделе конфигурации вашего setup.py:

...
def configuration(parent_package='', top_path=None):
    ...
    config.add_subpackage('tests')
    return config
...

Теперь вы можете сделать следующее, чтобы проверить свой модуль:

>>> import numpy
>>> numpy.xxx.test()

Также при вызове всего набора тестов NumPy будут найдены и запущены ваши тесты:

>>> import numpy
>>> numpy.test()
# your tests are included and run automatically!
Комментарии к примеру на русском
  • Ваши тесты автоматически включаются в набор и запускаются!

Советы и хитрости #

Известные сбои и пропуск тестов #

Иногда нужно пропустить тест или пометить его как ожидаемо неуспешный: например, если тесты пишутся до реализации проверяемого кода или тест не проходит только на определённой архитектуре.

Чтобы пропустить тест, просто используйте skipif:

import pytest

@pytest.mark.skipif(SkipMyTest, reason="Skipping this test because...")
def test_something(foo):
    ...

Тест помечается как пропущенный, если SkipMyTest имеет ненулевое значение, а сообщение в подробном выводе теста является вторым аргументом, переданным skipif. Аналогичным образом тест можно пометить как известный сбой, используя xfail:

import pytest

@pytest.mark.xfail(MyTestFails, reason="This test is known to fail because...")
def test_something_else(foo):
    ...

Разумеется, тест можно безусловно пропустить или пометить как ожидаемо неуспешный, используя skip или xfail без аргументов соответственно.

В конце запуска тестов выводится общее число пропущенных тестов и тестов с ожидаемой неудачей. Пропущенные отмечаются как 'S' (или 'SKIPPED' при verbose > 1), а тесты с ожидаемой неудачей — как 'x' (или 'XFAIL' при verbose > 1).

Тесты на случайных данных#

Тесты со случайными данными полезны, но сбои должны выявлять новые ошибки или регрессии. Тест, который обычно проходит, но иногда падает без изменений кода, бесполезен. Сделайте случайные данные воспроизводимыми, задав seed перед генерацией. С помощью rng = numpy.random.RandomState(some_number) задайте начальное значение локальному экземпляру numpy.random.RandomState.

Можно также использовать Hypothesis для генерации произвольных данных. Hypothesis сам управляет начальными значениями генераторов случайных чисел Python и NumPy и предоставляет краткий и мощный способ описания данных, в том числе hypothesis.extra.numpy, например для набора форм, совместимых при трансляции массивов.

По сравнению с обычной случайной генерацией преимущества включают воспроизведение сбоев и обмен примерами без фиксированного начального значения, получение минимальных примеров для каждого сбоя и более эффективные способы обнаружения ошибок.

Написание потокобезопасных тестов #

Написание потокобезопасных тестов может потребовать проб и ошибок. В целом следует придерживаться приведённых выше рекомендаций, особенно касающихся методов подготовки тестов и задания начального состояния генератора случайных данных. Явная подготовка и использование локального генератора случайных чисел обеспечивают потокобезопасность. Ниже даны советы по другим распространённым проблемам, с которыми можно столкнуться.

Использование pytest.mark.parametrize может иногда вызывать проблемы с потокобезопасностью. Чтобы это исправить, вы можете использовать copy():

@pytest.mark.parametrize('dimensionality', [3, 10, 25])
@pytest.mark.parametrize('dtype', [np.float32, np.float64])
def test_solve(dimensionality, dtype):
    dimen = dimensionality.copy()
    d = dtype.copy()
    # use these copied variables instead
    ...
Комментарии к примеру на русском
  • Вместо исходных переменных используем эти копии

Если вы тестируете операцию, которая по своей природе не является потокобезопасной, пометьте тест с помощью pytest.mark.thread_unsafe: тогда он будет выполняться в одном потоке и не приведёт к сбоям тестирования из-за параллельного выполнения.

@pytest.mark.thread_unsafe(reason="reason this test is thread-unsafe")
def test_thread_unsafe():
  ...

Примеры того, что следует помечать как небезопасное при работе из нескольких потоков:

  • Использование sys.stdout и sys.stderr

  • Изменение глобальных данных, например строк документации, модулей, сборщиков мусора и т. д.

  • Тесты, требующие много памяти, поскольку могут вызвать сбои.

Некоторые фикстуры pytest также небезопасны при параллельном использовании потоками, например monkeypatch и capsys. Однако pytest-run-parallel автоматически помечает их как небезопасные, если вы их используете. Другие фикстуры, например tmp_path, были исправлены для безопасной работы с потоками.

Документация для numpy.test #

numpy.test(label='fast', verbose=1, extra_argv=None, doctests=False, coverage=False, durations=-1, tests=None)#

Средство запуска тестов pytest.

Тестовая функция обычно добавляется в __init__.py пакета следующим образом:

from numpy._pytesttester import PytestTester
test = PytestTester(__name__).test
del PytestTester

Вызов этой тестовой функции находит и запускает все тесты модуля и всех его подмодулей.

Параметры:
module_nameимя модуля

Имя проверяемого модуля.

Атрибуты:
module_namestr

Полный путь к пакету для тестирования.
