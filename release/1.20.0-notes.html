Примечания к выпуску NumPy 1.20.0#

Это крупнейший на данный момент выпуск NumPy: в него вошло около 684 запросов на изменения от 184 участников. Подробности приведены в списке основных изменений ниже. Выпуск поддерживает Python 3.7–3.9; поддержка Python 3.6 прекращена. Основные изменения:

  • Аннотации для функций NumPy. Работа продолжается; ожидаются улучшения с учётом отзывов пользователей.

  • Более широкое использование SIMD для ускорения ufunc. Проделана большая работа по внедрению универсальных функций, упрощающих использование современных возможностей на разных аппаратных платформах. Эта работа продолжается.

  • Предварительные изменения в реализации dtype и приведении типов, которые упрощают добавление новых типов данных. Работа продолжается, но уже сделанного достаточно для экспериментов и сбора отзывов.

  • Масштабные улучшения документации: принято около 185 pull request. Эта работа продолжается в рамках более крупного проекта по улучшению представления NumPy в интернете и повышению его полезности для новых пользователей.

  • Дальнейшая очистка кода в связи с прекращением поддержки Python 2.7. Она улучшает читаемость кода и устраняет технический долг.

  • Предварительная поддержка нового Cython 3.0.

Новые функции #

В классе random.Generator появилась функция permuted.#

Новая функция отличается от shuffle и permutation тем, что переставляет подмассивы, выбираемые вдоль оси, вместо независимой перестановки одномерных срезов этой оси для каждого сочетания остальных индексов. Например, теперь можно переставлять целиком строки или столбцы двумерного массива.

(gh-15121)

sliding_window_view создаёт представление скользящего окна для массивов NumPy#

numpy.lib.stride_tricks.sliding_window_view создаёт представления массивов NumPy с доступом через скользящее окно. Это упрощает некоторые алгоритмы, например вычисление скользящего среднего.

(gh-17394)

numpy.broadcast_shapes — новая функция, доступная пользователям#

broadcast_shapes возвращает общую форму, полученную трансляцией (согласованием форм) заданных кортежей размеров.

>>> np.broadcast_shapes((1, 2), (3, 1))
(3, 2)

>>> np.broadcast_shapes(2, (3, 1))
(3, 2)

>>> np.broadcast_shapes((6, 7), (5, 6, 1), (7,), (5, 1, 7))
(5, 6, 7)

Устаревающие возможности#

Использование псевдонимов встроенных типов, таких как np.int, устарело. #

Долгое время np.int был псевдонимом встроенного int. Это неоднократно вызывало путаницу у новичков, и существовало в основном по историческим причинам.

Эти псевдонимы объявлены устаревшими. В таблице ниже приведён их полный список и точное значение каждого. Замена имён из первого столбца соответствующими значениями второго сохраняет поведение и устраняет предупреждение об устаревании.

В третьей колонке перечислены альтернативные имена NumPy, которые иногда могут быть предпочтительными. Дополнительную информацию см. также Типы данных .

Для подавляющего большинства случаев рекомендация проста: для типов bool, object, str и unicode обычное имя короче и понятнее и служит хорошей заменой. Для float и complex можно использовать float64 и complex128, если нужно явно указать точность.

Для np.int прямая замена на np.int_ или int тоже подходит и не меняет поведение, но разрядность по-прежнему зависит от компьютера и операционной системы. Если вы хотите явно выбрать тип и пересмотреть его использование, есть следующие варианты:

  • np.int64 или np.int32, чтобы точно указать точность. Это гарантирует, что результаты не будут зависеть от компьютера или операционной системы.

  • np.int_ или int (по умолчанию), но имейте в виду, что это зависит от компьютера и операционной системы.

  • Типы C: np.cint (int), np.int_ (long), np.longlong.

  • np.intp является 32-битным на 32-битных машинах и 64-битным на 64-битных машинах. Это может быть лучший тип для индексации.

При использовании с np.dtype(...) или dtype=... замена на соответствующее имя NumPy, как описано выше, не влияет на результат. При использовании в качестве скаляра с:

np.float(123)

его изменение может незначительно изменить результат. В этом случае версия Python float(123) или int(12.) обычно предпочтительнее, хотя версия NumPy может быть полезна для обеспечения согласованности с массивами NumPy (например, NumPy ведет себя по-другому для таких операций, как деление на ноль).

(gh-14882)

Передача shape=None функциям с обязательным аргументом shape объявлена устаревшей#

Ранее это было эквивалентно передаче shape=(). Предупреждение об устаревшем использовании выдаёт PyArray_IntpConverter в C API. Если ваш API должен поддерживать передачу None, проверьте None до вызова преобразователя, чтобы различать None и ().

(gh-15886)

Ошибки индексации выдаются даже при пустом результате#

В будущем NumPy будет вызывать IndexError, если целочисленный индексный массив содержит значения за границами допустимого диапазона, даже если длина неиндексируемого измерения равна 0. Сейчас в таком случае выдаётся DeprecationWarning. Это возможно, если исходный массив пуст или используется пустой срез:

arr1 = np.zeros((5, 0))
arr1[[20]]
arr2 = np.zeros((5, 5))
arr2[[20], :0]

Ранее непустой индекс [20] не проверялся на корректность. Теперь он проверяется, и некорректное значение вызывает предупреждение об устаревании, которое в будущем станет ошибкой. Это относится и к присваиванию.

(gh-15900)

Неточные совпадения значений mode и searchside объявлены устаревшими#

Раньше неточные совпадения значений mode и searchside, в том числе без учёта регистра, допускались; теперь они вызывают DeprecationWarning. Ниже приведены примеры использования, которые теперь объявлены устаревшими и вызывают DeprecationWarning:

import numpy as np
arr = np.array([[3, 6, 6], [4, 5, 1]])
# mode: inexact match
np.ravel_multi_index(arr, (7, 6), mode="clap")  # should be "clip"
# searchside: inexact match
np.searchsorted(arr[0], 4, side='random')  # should be "right"
Комментарии к примеру на русском
  • mode: неточное совпадение
  • Должно быть clip
  • searchside: неточное совпадение
  • Должно быть right

(gh-16056)

Модуль numpy.dual устарел. Вместо импорта функций из numpy.dual импортируйте их непосредственно из NumPy или SciPy.

Объекты ArrayLike без __len__ и __getitem__#

Объекты, реализующие один из протоколов __array__, __array_interface__ или __array_struct__, но не являющиеся последовательностями (что обычно определяется наличием __len__ и __getitem__), в будущем будут иначе обрабатываться при преобразовании в массив.

При вложении в последовательности, например np.array([array_like]), эти объекты обрабатывались как один объект Python, а не как массив. В будущем их поведение будет идентично следующему:

np.array([np.array(array_like)])

Это изменение должно затронуть только случаи, когда np.array(array_like) не является нульмерным. Способ устранения предупреждения зависит от объекта:

  • Некоторые объекты, подобные массивам, могут рассчитывать на новое поведение; пользователи могут игнорировать предупреждение. Объект может явно выбрать новое поведение, предоставив протокол последовательности.

  • Например, shapely позволит преобразовать в массив, используя line.coords, а не np.asarray(line). Пользователи могут обойти это предупреждение или использовать новое соглашение, когда оно станет доступным.

К сожалению, новое поведение доступно только при вызове np.array(array_like).

Если вы хотите, чтобы старое поведение осталось неизменным, создайте массив объектов, а затем заполните его явно, например:

arr = np.empty(3, dtype=object)
arr[:] = [array_like1, array_like2, array_like3]

Так NumPy поймёт, что не нужно обходить содержимое объекта, подобного массиву, а следует использовать его как обычный объект.

(gh-17973)

Будущие изменения#

Массивы не могут использовать dtype подмассивов#

Создание массивов и приведение типов через np.array(arr, dtype) и arr.astype(dtype) будет использовать другую логику, если dtype — тип подмассива, например np.dtype("(2)i,").

Для такого dtype справедливо следующее поведение:

res = np.array(arr, dtype)

res.dtype is not dtype
res.dtype is dtype.base
res.shape == arr.shape + dtype.shape

Но res заполняется по следующему правилу:

res = np.empty(arr.shape + dtype.shape, dtype=dtype.base)
res[...] = arr

что использует некорректную трансляцию массивов и часто приводит к ошибке. В дальнейшем каждый элемент будет приводиться отдельно, давая тот же результат, что и:

res = np.array(arr, dtype=np.dtype(["f", dtype]))["f"]

Которые обычно могут быть использованы для выбора нового поведения.

Это изменение не влияет на np.array(list, dtype="(2)i,"), если только list не содержит хотя бы один массив. В частности, поведение не меняется для списка кортежей.

(gh-17596)

  • Период устаревания np.sctypeNA и np.typeNA завершён: оба имени удалены из общедоступного API. Используйте np.typeDict.

    (gh-16554)

Примечания о совместимости#

isinstance(dtype, np.dtype), а не type(dtype) is not np.dtype #

Объекты dtype NumPy больше не являются непосредственными экземплярами np.dtype. Проверка type(dtype) is np.dtype теперь всегда возвращает False; код необходимо изменить, используя правильную проверку isinstance(dtype, np.dtype).

Изменение затрагивает также макрос C PyArray_DescrCheck при компиляции с версией NumPy, предшествующей 1.16.6. Если код использует этот макрос и должен компилироваться с более ранней NumPy, макрос необходимо заменить; см. раздел Изменения C API.

Приведение типов same_kind в concatenate при axis=None#

Ранее при вызове concatenate с axis=None развёрнутые в одномерные массивы приводились по правилу unsafe. При любом другом выборе оси использовалось правило «same kind». Это различие в поведении по умолчанию объявлено устаревшим: вместо него будет применяться «same kind». Новый именованный аргумент casting позволяет сохранить прежнее поведение.

(gh-16134)

Скаляры NumPy приводятся к типу массива при присваивании его элементам#

При создании массивов и присваивании им значений скаляры NumPy теперь во всех соответствующих случаях приводятся к типам так же, как массивы NumPy. В частности, меняется поведение некоторых случаев, прежде вызывавших ошибку:

np.array([np.float64(np.nan)], dtype=np.int64)

выполнится успешно, но вернёт неопределённый результат, обычно наименьшее возможное целое число. Это также влияет на присваивания:

arr[0] = np.float64(np.nan)

Пока NumPy сохраняет это поведение для:

np.array(np.float64(np.nan), dtype=np.int64)

Вышеперечисленные изменения не влияют на скаляры Python:

np.array([float("NaN")], dtype=np.int64)

остаётся без изменений: np.nan — это float Python, а не NumPy. В отличие от целых со знаком, беззнаковые целые не сохраняют этот особый случай, поскольку всегда вели себя скорее как приведение типов. Следующий код больше не вызывает ошибку:

np.array([np.float64(np.nan)], dtype=np.uint64)

Чтобы избежать проблем обратной совместимости, пока сохраняется возможность присваивать скаляры datetime64 строкам слишком малой длины. Поэтому np.asarray(np.datetime64("2020-10-10"), dtype="S5") теперь выполняется успешно, хотя раньше завершалось ошибкой. В дальнейшем это поведение может быть объявлено устаревшим либо небезопасное приведение будет разрешено в общем случае, чтобы присваивания массивов и скаляров вели себя одинаково.

Изменения приведения к массиву при смешивании строк и других типов#

При смешивании строк с другими типами, например:

np.array(["string", np.float64(3.)], dtype="S")

Результаты изменятся, и в некоторых случаях строковый тип будет иметь большую длину. В частности, если dtype="S" не задан, любое числовое значение создаст строковый результат длины, достаточной для всех возможных числовых значений, например «S32» для чисел с плавающей запятой. При преобразовании нестроковых данных в строки всегда следует задавать dtype="S".

Если задан dtype="S", результаты будут в основном такими же, как раньше, но скаляры NumPy, в отличие от float Python вроде 1.0, по-прежнему будут обеспечивать одинаковую длину строк:

np.array([np.float64(3.)], dtype="S")  # gives "S32"
np.array([3.0], dtype="S")  # gives "S3"
Комментарии к примеру на русском
  • Даёт "S32"
  • Даёт "S3"

Ранее первая версия давала такой же результат, как и вторая.

Переработка преобразования входных объектов в массивы#

Внутренняя реализация преобразования объектов в массивы переработана. Как правило, это не должно затронуть пользователей. В исключительно редких случаях, когда объекты, подобные массивам, вложены друг в друга:

np.array([array_like1])

Теперь все будет более согласовано с:

np.array([np.array(array_like1)])

Это может неочевидным образом изменить результаты для некоторых некорректно определённых объектов, подобных массивам. Например, это касается объектов, которые при этом не являются последовательностями с согласованной формой. В NumPy 1.20 для объектов, подобных массивам, которые не являются последовательностями, выдаётся предупреждение (само поведение пока сохраняется; см. раздел об устаревших возможностях). Если объект также является последовательностью (определяет __getitem__ и __len__), NumPy теперь использует только результат, предоставленный через __array__, __array_interface__ или __array_struct__. Это приведёт к различиям, если (вложенная) последовательность задаёт другую форму.

    • --disable-optimization явно отключает все новые оптимизации. Также определяется макрос компилятора C с именем NPY_DISABLE_OPTIMIZATION, который можно использовать для условной компиляции SIMD-кода.

  • Расширенный диспетчер процессорных реализаций

    Гибкий диспетчер процессорных реализаций для разных архитектур, построенный на Python/NumPy distutils. Поддерживает все распространённые компиляторы и широкий набор возможностей процессоров.

    Новый диспетчер требует расширения *.dispatch.c для исходных файлов на C с поддержкой диспетчеризации. Такие файлы можно компилировать несколько раз: каждый вариант ориентирован на определённые возможности процессора и использует свои определения #define и флаги, влияющие на выполняемые ветви кода.

  • Новый автоматически создаваемый заголовочный файл C ``core/src/common/_cpu_dispatch.h``

    Этот заголовочный файл создаётся модулем distutils ccompiler_opt и содержит все директивы #define и заголовки наборов инструкций, настроенных с помощью аргументов командной строки «–cpu-baseline» и «–cpu-dispatch».

  • Новый заголовок C ``core/src/common/npy_cpu_dispatch.h``

    Заголовок содержит все средства, необходимые для диспетчеризации CPU. Он также связывает новую инфраструктуру с определением возможностей процессора NumPy во время выполнения.

  • Добавление новых атрибутов в модуль NumPy umath на уровне Python

    • __cpu_baseline__ — список с минимальным набором требуемых оптимизаций, поддерживаемых компилятором и платформой согласно значениям аргумента командной строки «–cpu-baseline».

    • __cpu_dispatch__ — список дополнительных оптимизаций, выбираемых диспетчером во время выполнения и поддерживаемых компилятором и платформой согласно значениям аргумента командной строки «–cpu-dispatch».

  • Вывод поддерживаемых возможностей CPU при запуске PytestTester

np.linspace для целых чисел теперь использует округление вниз#

При использовании dtype int в numpy.linspace значения с плавающей точкой раньше округлялись в сторону нуля. Теперь используется numpy.floor с округлением в сторону -inf. Это меняет результат для отрицательных значений. Например, раньше следующий код давал:

>>> np.linspace(-3, 1, 8, dtype=int)
array([-3, -2, -1, -1,  0,  0,  0,  1])

И теперь приводит к:

>>> np.linspace(-3, 1, 8, dtype=int)
array([-3, -3, -2, -2, -1, -1,  0,  1])

Прежний результат все же можно получить при:

>>> np.linspace(-3, 1, 8).astype(int)
array([-3, -2, -1, -1,  0,  0,  0,  1])
