Примечания к выпуску NumPy 1.21.0#

Основные изменения NumPy 1.21.0:

  • продолжение работы над SIMD с охватом большего числа функций и платформ,

  • начальная работа над новой инфраструктурой dtype и приведением типов,

  • пакеты wheel universal2 для Python 3.8 и Python 3.9 на Mac,

  • улучшенная документация,

  • улучшенные аннотации,

  • Новый битгенератор PCG64DXSM для случайных чисел.

Кроме того, выпуск, как обычно, содержит множество исправлений ошибок и других улучшений.

Этот выпуск поддерживает Python 3.7–3.9. Официальная поддержка Python 3.10 будет добавлена после его выхода.

Предупреждение

Существуют нерешенные проблемы компиляции NumPy 1.20.0 с gcc-11.1.

  • Оптимизация уровня -O3 приводит ко многим неверным предупреждениям при выполнении тестов.

  • На некотором оборудовании NumPy зависает в бесконечном цикле.

Новые функции #

Добавлена PCG64DXSM BitGenerator#

У PCG64 BitGenerator при массово-параллельном использовании обнаружены статистические слабости, не замеченные при первом выпуске в NumPy 1.17. Большинство пользователей никогда с ними не столкнётся и может продолжать использовать PCG64. Мы добавили PCG64DXSM BitGenerator, который в будущих выпусках станет стандартной реализацией BitGenerator для default_rng. PCG64DXSM устраняет статистическую слабость, сохраняя производительность и возможности PCG64.

Подробнее см. Переход с PCG64 на PCG64DXSM.

Устаревающие возможности#

Атрибут .dtype должен вернуть dtype #

Теперь выдаётся DeprecationWarning, если атрибут .dtype объекта, переданного в np.dtype либо как аргумент dtype=obj, не является dtype. NumPy перестанет пытаться рекурсивно преобразовывать результат .dtype.

(gh-13578)

Неточные совпадения значений numpy.convolve и numpy.correlate объявлены устаревшими#

convolve и correlate теперь выдают предупреждение при неточном совпадении аргумента mode, в том числе отличающемся регистром. Передавайте полные строки "same", "valid", "full" вместо "s", "v", "f" в аргумент mode.

(gh-17492)

np.typeDict официально объявлен устаревшим. #

np.typeDict — псевдоним np.sctypeDict, объявленный устаревшим более 14 лет назад (6689502). Теперь при каждом обращении к np.typeDict выдаётся предупреждение об устаревании.

(gh-17586)

При создании объектов, подобных массивам, будут вызываться исключения#

Раньше исключения, возникавшие при доступе к специальным атрибутам __array__ или __array_interface__, обычно игнорировались. Теперь для любого исключения, кроме AttributeError, выдаётся предупреждение. Чтобы устранить его, измените соответствующий тип так, чтобы он вызывал AttributeError.

( gh-19001 )

Четыре метода объекта ndarray.ctypes объявлены устаревшими: это недокументированные детали реализации соответствующих свойств.

Речь идет о следующих методах:

  • _ctypes.get_strides (вместо этого используйте _ctypes.strides)

  • _ctypes.get_as_parameter (вместо этого используйте _ctypes._as_parameter_)

Примечания о совместимости#

Изменения типов исключений в универсальных функциях#

В некоторых случаях при неверных входных данных универсальные функции теперь могут выдавать другие ошибки. Основное изменение — замена RuntimeError на более подходящее TypeError. Если один вызов содержит несколько ошибок, NumPy теперь может сообщить о другой из них.

( gh-15271 )

Проверка аргументов __array_ufunc__#

NumPy теперь частично проверяет аргументы до вызова __array_ufunc__. Ранее при ожидаемой диспетчеризации могли передаваться недопустимые аргументы, например неизвестный именованный аргумент.

( gh-15271 )

__array_ufunc__ и дополнительные позиционные аргументы#

Ранее у всех позиционных аргументов проверялась поддержка __array_ufunc__. Для reduce, accumulate и reduceat все аргументы могут передаваться позиционно, поэтому любой из них мог получить вызов __array_ufunc__ для обработки универсальной функции. Чтобы поведение не зависело от позиционной или именованной передачи, NumPy теперь выбирает реализацию только по входному и выходному массивам. Например, массив where никогда не участвует в диспетчеризации свёртки вида np.add.reduce.

( gh-15271 )

Проверка входных значений в Generator.uniform #

Выполняется проверка high - low >= 0 в np.random.Generator.uniform. Вызывается ValueError при low > high. Раньше границы в неправильном порядке принимались и незаметно менялись местами, поэтому при low > high значение генерировалось как high + (low - high) * random().

(gh-17921)

/usr/include удалён из стандартных путей поиска заголовочных файлов#

При сборке пакета с помощью numpy.distutils стандартный список путей поиска заголовочных файлов больше не включает /usr/include. Обычно этот путь добавляет компилятор, а его жёсткое задание может вызвать проблемы. Если это изменение приводит к проблеме, создайте сообщение об ошибке. Обходное решение описано в PR 18658.

( gh-18658 )

Изменения в сравнении с dtype=... #

В дальнейшем аргументы dtype= (или signature) универсальных функций сравнения (equal, less и т. д.) будут задавать желаемый тип выходных данных. Это означает следующее:

np.equal(2, 3, dtype=object)

выдаст FutureWarning о том, что в будущем будет возвращаться массив object; сейчас это происходит для:

np.equal(None, None, dtype=object)

Из-за того, что np.array(None) уже является объектным массивом. (Это также происходит для некоторых других типов).

Поскольку операции сравнения обычно возвращают только логические массивы, указание любого другого dtype в будущем всегда будет вызывать ошибку, а сейчас вызывает DeprecationWarning.

(gh-18718)

Изменения аргументов dtype и signature универсальных функций#

Аргументы универсальных функций dtype и signature, которые также применимы к свёрткам, например np.add.reduce (реализации np.sum), теперь вызывают предупреждение, если переданный dtype не является «базовым» типом данных.

NumPy почти всегда игнорировал метаданные, порядок байтов и единицы времени в этих входных данных. Теперь он всегда игнорирует эти сведения, а при изменении порядка байтов или единиц времени вызывает ошибку. Ниже приведены наиболее важные примеры изменений, вызывающих ошибку. В некоторых случаях сохранённые сведения раньше не игнорировались; теперь во всех таких случаях возникает ошибка:

# Previously ignored the byte-order (affect if non-native)
np.add(3, 5, dtype=">i32")

# The biggest impact is for timedelta or datetimes:
arr = np.arange(10, dtype="m8[s]")
# The examples always ignored the time unit "ns":
np.add(arr, arr, dtype="m8[ns]")
np.maximum.reduce(arr, dtype="m8[ns]")

# The following previously did use "ns" (as opposed to `arr.dtype`)
np.add(3, 5, dtype="m8[ns]")  # Now return generic time units
np.maximum(arr, arr, dtype="m8[ns]")  # Now returns "s" (from `arr`)
Комментарии к примеру на русском
  • Раньше порядок байтов игнорировался; это важно для немашинного порядка
  • Сильнее всего это влияет на timedelta и datetime:
  • Эти примеры всегда игнорировали единицу времени ns:
  • Следующий вариант раньше использовал ns, в отличие от `arr.dtype`
  • Теперь возвращают неопределённые единицы времени
  • Теперь возвращает s из `arr`

То же самое относится и к функциям, таким как np.sum, которые используют их внутри. Это изменение необходимо для достижения согласованной обработки в NumPy.

Если вы столкнулись с такими ошибками, в большинстве случаев передавайте, например, dtype=np.timedelta64: это явно обозначает общий тип timedelta64 без указания единиц измерения и порядка байтов. Если тип результата нужно задать точно, можно привести входные данные к нужному типу либо передать выходной массив через out=.

В будущем NumPy может разрешить здесь задание точного выходного dtype; перед этим будет введено предупреждение FutureWarning.

(gh-18718)

Ufunc signature=... и dtype= обобщение и casting #

Из-за изменений повышения типов при np.ufunc(1.0, 1.0, signature=...) или np.ufunc(1.0, 1.0, dtype=...) в версии 1.21 может выбираться другой цикл, чем в 1.20. Ранее при signature проверка приведения входных типов ослаблялась, что могло небезопасно понижать точность входных данных, особенно в сочетании с casting="unsafe".

Приведение типов теперь гарантированно безопасно. Если сигнатура задана лишь частично, например signature=("float64", None, None), подходящий цикл может не найтись, что вызовет ошибку. В таком случае для принудительного приведения входов нужно задать полную сигнатуру. При использовании dtype="float64" или задании только выходов, например signature=(None, None, "float64"), поведение не меняется. Мы ожидаем, что изменение затронет очень немногих пользователей.

Кроме того, смысл dtype="float64" немного изменён: теперь он строго задаёт DType только выходных, а не входных данных. Поэтому он всегда эквивалентен следующему:

signature=(None, None, "float64")

(Если ufunc имеет два входа и один выход.) Поскольку это может привести к тому, что в некоторых случаях цикл не будет найден, NumPy обычно также будет искать цикл:

signature=("float64", "float64", "float64")

если первый поиск не удался. В будущем это поведение можно будет настроить для достижения ожидаемых результатов для более сложных функций. (Для некоторых универсальных функций, таких как np.ldexp, входы могут иметь разные DTypes.)

(gh-18880)

Distutils принудительно использует строгую модель с плавающей запятой в clang #

NumPy distutils теперь всегда добавляет флаг компилятора -ffp-exception-behavior=strict при сборке с Clang. По умолчанию Clang использует нестрогий режим, позволяющий генерировать код, который некорректно устанавливает предупреждения и ошибки вычислений с плавающей точкой.

( gh-19049 )

Изменения C API#

Использование ufunc->type_resolver и «кортежа типов»#

Перед вызовом функций разрешения типов NumPy теперь нормализует аргумент «кортеж типов». Этот механизм устарел, и по возможности NumPy его не использует. Вызывать ufunc->type_resolver или PyUFunc_DefaultTypeResolver настоятельно не рекомендуется; теперь такие вызовы требуют нормализованного кортежа типов. Это не мешает предоставлять собственную функцию разрешения типов: в большинстве случаев она продолжит работать. Если у вас есть нестандартная необходимость вызывать такую функцию напрямую, сообщите разработчикам NumPy, чтобы найти решение.

(gh-18718)

Новые возможности #

Добавлен плагин mypy для платформозависимой разрядности numpy.number#

Теперь доступен плагин mypy, автоматически определяющий зависящую от платформы точность некоторых подклассов number, в том числе int_, intp и longlong. Полный перечень затронутых классов приведён в документации по скалярным типам.

Обратите внимание, что хотя использование плагина является полностью необязательным, без него точность вышеупомянутых классов будет выведена как Any.

Чтобы включить плагин, добавьте его в файл конфигурации mypy:

[mypy]
plugins = numpy.typing.mypy_plugin

(gh-17843)

Управление подклассами numpy.number расширенной точности с помощью плагина mypy#

Плагин mypy, добавленный в numpy/numpy#17843, расширен: теперь он удаляет аннотации типов расширенной точности, недоступных на данной платформе. Например, удаляется float128, если этот тип недоступен.

Без плагина mypy будет считать, что все типы расширенной точности доступны на всех платформах.

Чтобы включить плагин, добавьте его в файл конфигурации mypy:

[mypy]
plugins = numpy.typing.mypy_plugin

( gh-18322 )

Новый аргумент min_digits для печати значений float #

Новый аргумент min_digits добавлен в функции вывода чисел с плавающей точкой Dragon4 format_float_positional и format_float_scientific. При unique=True он гарантирует вывод как минимум заданного числа цифр, даже если дополнительные цифры не нужны для однозначного представления значения. Он дополняет аргумент precision, задающий максимальное число цифр. В режиме фиксированной точности unique=False этот аргумент не действует: число цифр задаётся precision.

f2py теперь распознаёт блоки абстрактных интерфейсов Fortran#

f2py теперь может анализировать абстрактные блоки интерфейса.

(gh-18695)

Настройка BLAS и LAPACK через переменные окружения#

Автоматическое обнаружение установленных библиотек BLAS и LAPACK можно отключить с помощью переменных окружения NPY_BLAS_LIBS и NPY_LAPACK_LIBS. Флаги компоновки из этих переменных будут использованы напрямую, а языком будет считаться F77. Это особенно полезно при автоматической сборке, когда точно известно, какие BLAS и LAPACK установлены. Например, так можно заменять реализацию во время выполнения через компоновку с библиотеками-заглушками.

Если задана переменная NPY_CBLAS_LIBS (необязательная в дополнение к NPY_BLAS_LIBS), она также используется: определяется HAVE_CBLAS, а её содержимое добавляется к флагам компоновки.

Для ndarray добавлен псевдоним, поддерживающий обращение через квадратные скобки во время выполнения#

Добавлен numpy.typing.NDArray — псевдоним np.ndarray[Any, np.dtype[~Scalar]], поддерживающий параметризацию в квадратных скобках во время выполнения. Его можно использовать для аннотации массивов с заданным dtype и неопределённой формой. 1

1 По состоянию на версию 1.21 NumPy не поддерживает аннотации форм массивов; ожидается, что в будущем это изменится (см. PEP 646).

Примеры#

>>> import numpy as np
>>> import numpy.typing as npt

>>> print(npt.NDArray)
numpy.ndarray[typing.Any, numpy.dtype[~ScalarType]]

>>> print(npt.NDArray[np.float64])
numpy.ndarray[typing.Any, numpy.dtype[numpy.float64]]

>>> NDArrayInt = npt.NDArray[np.int_]
>>> a: NDArrayInt = np.arange(10)

>>> def func(a: npt.ArrayLike) -> npt.NDArray[Any]:
...     return np.array(a)

Улучшения#

Произвольная опция period для numpy.unwrap #

Интервал развёртки фазы больше не ограничен значением 2 * pi. Это особенно полезно для фаз в градусах, но можно использовать и другие интервалы.

>>> phase_deg = np.mod(np.linspace(0,720,19), 360) - 180
>>> phase_deg
array([-180., -140., -100.,  -60.,  -20.,   20.,   60.,  100.,  140.,
       -180., -140., -100.,  -60.,  -20.,   20.,   60.,  100.,  140.,
       -180.])

>>> unwrap(phase_deg, period=360)
array([-180., -140., -100.,  -60.,  -20.,   20.,   60.,  100.,  140.,
        180.,  220.,  260.,  300.,  340.,  380.,  420.,  460.,  500.,
        540.])

(gh-16987)

np.unique теперь возвращает единственное значение NaN#

Когда np.unique работал на массиве с несколькими записями NaN, его возврат включал NaN для каждой записи, которая была NaN в исходном массиве. Теперь это улучшено так, что возвращенный массив содержит только один NaN в качестве последнего элемента.

Для комплексных массивов все значения NaN также считаются эквивалентными независимо от того, находится ли NaN в вещественной или мнимой части. Для возвращаемого массива выбирается наименьший из этих элементов в лексикографическом порядке. Определение лексикографического порядка для комплексных массивов см. в np.sort.

(gh-18070)

Повышена производительность Generator.rayleigh и Generator.geometric#

В Generator повышена скорость генерации случайных величин с распределениями Рэлея и геометрическим. Оба способа основаны на преобразовании экспоненциальных случайных величин. Медленный метод обратной функции распределения, использующий логарифм, заменён генератором экспоненциальных случайных величин на основе алгоритма «зиккурат».

Это изменение нарушает совместимость потока случайных значений, генерируемых для любого из этих распределений.

(gh-18666)

Улучшены аннотации-заглушки#

Уточнены все временные аннотации типов, ранее заданные как typing.Any. Где уместно, они заменены явными определениями функций, классами или другими объектами.

Ускорено целочисленное деление массивов NumPy#

Целочисленное деление массивов NumPy теперь использует libdivide при постоянном делителе. Это вместе с другими небольшими оптимизациями значительно ускоряет вычисления. Изменения используются оператором // и np.floor_divide.

Улучшение производительности np.save и np.load для небольших массивов #

np.save теперь работает намного быстрее для небольших массивов.

np.load также быстрее для небольших массивов, но только при сериализации с версией >= (3, 0).

В обоих случаях удалены проверки, относящиеся только к Python 2, но сохранена совместимость с массивами, которые могли быть созданы в Python 2.

Класс результата numpy.piecewise теперь совпадает с классом входа#

Если экземпляры подклассов ndarray подаются на вход piecewise, они передаются функциям в таком виде. Теперь результат также принадлежит тому же подклассу.

(gh-18110)

Включение Accelerate Framework#

В macOS 11.3 должны быть решены несколько проблем, с которыми NumPy сталкивался при использовании BLAS и LAPACK из Accelerate Framework. Это изменение позволяет использовать Accelerate Framework в macOS. Если обнаружатся другие проблемы, отправьте сообщение об ошибке Accelerate через инструмент обратной связи для разработчиков (https://developer.apple.com/bug-reporting/). Мы намерены оперативно решать проблемы и продолжать поддержку и обновление наших библиотек BLAS и LAPACK.
