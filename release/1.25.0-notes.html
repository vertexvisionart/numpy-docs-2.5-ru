Историческая справка: страница описывает NumPy 1.25.0. Слова «сейчас», «раньше» и «будет» относятся ко времени этого выпуска; описанное поведение может отличаться от NumPy 2.5.

Примечания к выпуску NumPy 1.25.0#

NumPy 1.25.0 продолжает работу над обработкой и повышением dtype, ускорением выполнения и ясностью документации. Также проведена подготовка к будущему выпуску NumPy 2.0.0: многие возможности объявлены устаревшими, а для ранее устаревших завершились переходные периоды. Основные изменения:

  • Добавлена поддержка MUSL: теперь доступны wheel-пакеты для MUSL.

  • Поддерживает компилятор Fujitsu C/C++.

  • Объектные массивы теперь поддерживаются в einsum

  • Поддержка матричного умножения на месте (@=).

Мы выпустим NumPy 1.26 после выхода Python 3.12. Это необходимо, поскольку из Python 3.12 удалён distutils и для дальнейших сборок мы переходим на Meson. Следующим основным выпуском будет NumPy 2.0.0. Мы планируем сохранить в серии 2.0 поддержку зависимых проектов, собранных с более ранними версиями NumPy.

Версии Python, поддерживаемые в этом выпуске, составляют 3.9-3.11.

Устаревающие возможности#

  • np.core.MachAr объявлен устаревшим. Это внутренний API. В целом имена, определённые в np.core, следует считать внутренними.

    ( gh-22638 )

  • np.finfo(None) объявлен устаревшим.

    (gh-23011)

  • np.round_ устарел. Вместо этого используйте np.round.

    (gh-23302)

  • np.product устарел. Вместо этого используйте np.prod.

    (gh-23314)

  • np.cumproduct устарел. Вместо этого используйте np.cumprod.

    (gh-23314)

  • np.sometrue устарел. Вместо этого используйте np.any.

    (gh-23314)

  • np.alltrue устарел. Вместо этого используйте np.all.

    (gh-23314)

  • Только нульмерные массивы рассматриваются как скаляры. Раньше NumPy считал скалярами все массивы размера 1, например np.array([3.14]). В дальнейшем это будет распространяться только на массивы с ndim, равным 0, например np.array(3.14). Следующие выражения будут выдавать предупреждение об устаревшем поведении:

    a = np.array([3.14])
float(a)  # better: a[0] to get the numpy.float or a.item()

b = np.array([[3.14]])
c = numpy.random.rand(10)
c[0] = b  # better: c[0] = b[0, 0]
    Комментарии к примеру на русском
    • Лучше: a[0] для получения numpy.float или a.item()
    • Лучше: c[0] = b[0, 0]

    (gh-10615)

  • np.find_common_type объявлена устаревшей. Вместо numpy.find_common_type теперь следует использовать numpy.result_type или numpy.promote_types. Большинство пользователей оставляют второй аргумент scalar_types функции find_common_type равным []; в этом случае np.result_type и np.promote_types быстрее и надёжнее. Если scalar_types не используется, главное отличие заключается в том, что новые функции намеренно преобразуют порядок байтов в родной для платформы. Кроме того, find_common_type возвращает dtype object вместо ошибки повышения типов. Это приводит к различиям при нечисловых входных данных, в том числе timedelta/datetime, для которых текущие правила повышения типов NumPy иногда дают неожиданные результаты.

    Если аргумент scalar_types не равен [], ситуация сложнее. В большинстве случаев вызов np.result_type со значениями Python 0, 0.0 или 0j даёт тот же результат, что и использование int, float или complex в scalar_types.

    Если scalar_types уже сформирован, правильная замена — np.result_type; ей можно передавать скалярные значения, например np.float32(0.0). Передача значений, отличных от 0, может включить поведение, учитывающее конкретное значение; np.find_common_type никогда его не использовал, а NEP 50 может изменить его в будущем. Основное возможное изменение поведения возникает, когда типы массивов — целые со знаком, а типы скаляров — без знака.

    Если вы не знаете, чем заменить использование scalar_types, или допускаете появление нечисловых типов данных, создайте обращение в системе отслеживания проблем NumPy и попросите о помощи.

    ( gh-22539 )

Окончательно удалённые устаревшие возможности#

  • np.core.machar и np.finfo.machar были удалены.

    ( gh-22638 )

  • +arr теперь вызывает ошибку, если dtype не является числовым и унарный плюс для него не определён.

    ( gh-22998 )

  • В функции семейства объединения массивов (stack, vstack, hstack, dstack и column_stack) теперь нужно передавать последовательность.

    ( gh-23019 )

  • np.clip теперь по умолчанию использует приведение по правилу same-kind. Переход к небезопасному приведению был объявлен устаревшим в NumPy 1.17.

    ( gh-23403 )

  • np.clip теперь переносит в результат значения np.nan, переданные в качестве min или max. Раньше скалярное значение NaN обычно игнорировалось; такое поведение было объявлено устаревшим в NumPy 1.17.

    ( gh-23403 )

  • Субмодуль np.dual был удален.

    (gh-23480)

  • Для объектов, определяющих один из протоколов массивов, NumPy теперь всегда игнорирует поведение последовательности. Отказ от прежнего поведения начат в NumPy 1.20.

    ( gh-23660 )

  • Завершён переход, о котором предупреждал редко встречавшийся FutureWarning при приведении к типу подмассива в astype или функциях создания массивов, таких как asarray. Теперь поведение всегда такое, как если бы тип подмассива был обёрнут в одно поле (раньше это служило обходным решением). (FutureWarning выдавался начиная с NumPy 1.20.)

    (gh-23666)

  • Изменения, о которых предупреждалось для == и !=, вступили в силу. Операторы == и != для массивов теперь всегда:

    • вызывать ошибки, возникающие при сравнении, например из-за несовместимых форм массивов (np.array([1, 2]) == np.array([1, 2, 3])).

    • возвращать массив, целиком состоящий из True или False, если значения принципиально несопоставимы, например имеют разные типы данных. Пример: np.array(["a"]) == np.array([1]).

      Это соответствует поведению Python: возвращать False и True при сравнении несовместимых типов, как в "a" == 1 и "a" != 1. Долгое время такие сравнения выдавали DeprecationWarning или FutureWarning.

    ( gh-22707 )

  • Поддержка nose удалена. NumPy перешёл на pytest в 2018 году, а nose не поддерживается уже много лет. Поддержка nose сохранялась в NumPy ради зависимых проектов, которые ещё не перешли на pytest или другой инструмент тестирования. В Python 3.12 nose без дополнительных исправлений вызывает ошибку. Пора переходить на современные средства.

    Удалённые декораторы:

    • вызывает

    • медленный

    • setastest

    • skipif

    • knownfailif

    • устарело

    • параметризировать

    • _needs_refcount

    Не путайте их с похожими средствами pytest, например pytest.mark.slow, pytest.mark.skipif, pytest.mark.parametrize.

    Удалённые функции:

    • Tester

    • import_nose

    • run_module_suite

    (gh-23041)

  • Слой совместимости numpy.testing.utils удалён. Импорт из numpy.testing.utils был объявлен устаревшим в 2019 году; теперь этот слой удалён. Все объекты следует импортировать непосредственно из numpy.testing.

    (gh-23060)

  • Переменная окружения для отключения диспетчеризации удалена. Поддержка NUMPY_EXPERIMENTAL_ARRAY_FUNCTION прекращена; эта переменная отключала диспетчеризацию через __array_function__.

    ( gh-23376 )

  • Удалена поддержка y= в качестве псевдонима out=. Функции fix, isposinf и isneginf позволяли использовать y= как устаревший псевдоним out=. Теперь это не поддерживается.

    ( gh-23376 )

Примечания о совместимости#

  • Метод busday_count теперь корректно обрабатывает случаи, когда begindates позже enddates. Ранее дата enddates включалась в подсчёт, хотя в документации указано, что она всегда исключается.

    ( gh-23229 )

  • При сравнении datetime и timedelta через np.equal или np.not_equal NumPy ранее допускал сравнение с casting="unsafe". Теперь эта операция завершается ошибкой. Принудительное задание dtype результата аргументом dtype может позволить её выполнить, но это не рекомендуется.

    ( gh-22707 )

  • При загрузке данных из файлового объекта с помощью np.load указатель чтения может находиться в конце файла, например после многократных вызовов np.load для чтения нескольких массивов. Раньше NumPy в таком случае вызывал ValueError при allow_pickle=False и OSError при allow_pickle=True. Теперь в обоих случаях вызывается EOFError.

    (gh-23105)

np.pad с mode=wrap дополняет массив точными повторениями исходных данных#

Код для прежних версий pad с mode="wrap" теперь будет давать другие результаты, если размер дополнения превышает размер исходного массива.

np.pad с mode=wrap теперь всегда заполняет добавляемую область точными повторами исходных данных, даже если размер дополнения превышает размер исходного массива.

(gh-22575)

Удалены типы Cython long_t и ulong_t#

long_t и ulong_t были псевдонимами для longlong_t и ulonglong_t и сбивали с толку (остаток от Python 2). Это изменение может привести к ошибкам:

'long_t' is not a type identifier
'ulong_t' is not a type identifier

Рекомендуется использовать типы с явно заданной разрядностью, например cnp.int64_t, либо cnp.intp_t: он имеет разрядность 32 бита на 32-разрядных системах и 64 бита на 64-разрядных, что лучше всего согласуется с индексированием. Если нужен тип C long, используйте просто long или npy_long. Тип cnp.int_t также соответствует long (целочисленному типу NumPy по умолчанию). Однако long имеет разрядность 32 бита в 64-разрядной Windows, и мы можем захотеть изменить это даже в NumPy. (Если вас интересует этот вопрос, обращайтесь к разработчикам NumPy.)

(gh-22637)

Изменены сообщение и тип ошибки при некорректном аргументе axes универсальной функции ufunc#

Изменились сообщение об ошибке и тип исключения при передаче неверного значения axes в ufunc(..., axes=[...])`. Теперь сообщение точнее описывает проблему, а при несоответствии значения возбуждается AxisError. Для недопустимых типов входных данных по-прежнему возбуждается TypeError.

(gh-22675)

Объекты, подобные массивам и определяющие __array_ufunc__, теперь могут переопределять универсальные функции при использовании в качестве where#

Если именованный аргумент where функции numpy.ufunc относится к подклассу numpy.ndarray или имеет совместимый по поведению тип, определяющий numpy.class.__array_ufunc__, он может переопределять поведение ufunc тем же способом, что и входные и выходные аргументы. Для корректной работы реализация where.__array_ufunc__ должна извлечь из аргумента where базовое представление данных, прежде чем передать его в стандартную реализацию ufunc или, для подклассов numpy.ndarray, вызвать super().__array_ufunc__.

(gh-23240)

Компиляция с использованием C API NumPy теперь по умолчанию обеспечивает обратную совместимость#

Теперь NumPy по умолчанию предоставляет обратно совместимое подмножество C API, поэтому использовать oldest-supported-numpy больше не требуется. Библиотеки могут переопределить минимальную версию совместимости по умолчанию следующим образом:

#define NPY_TARGET_VERSION NPY_1_22_API_VERSION

перед подключением NumPy либо передав эквивалентный параметр -D компилятору. В NumPy 1.25 значение по умолчанию — NPY_1_19_API_VERSION. Поскольку API C NumPy 1.19 совпадал с API версии 1.16, полученные программы будут совместимы с NumPy 1.16 с точки зрения API C. В будущих выпусках, не ограниченных исправлением ошибок, это значение будет повышаться. По-прежнему можно компилировать с более старой версией NumPy и запускать с более новой.

Подробнее см. Для авторов пакетов, зависящих от NumPy.

(gh-23528)

Новые возможности #

np.einsum теперь принимает массивы с dtype object#

Для массивов с dtype object эта ветвь кода вызывает операторы Python, как это делают np.dot и np.matmul.

(gh-18053)

Добавлена поддержка умножения матриц на месте#

Теперь можно выполнять матричное умножение на месте оператором @=.

>>> import numpy as np

>>> a = np.arange(6).reshape(3, 2)
>>> print(a)
[[0 1]
 [2 3]
 [4 5]]

>>> b = np.ones((2, 2), dtype=int)
>>> a @= b
>>> print(a)
[[1 1]
 [5 5]
 [9 9]]

(gh-21120)

Добавлена переменная среды NPY_ENABLE_CPU_FEATURES #

Теперь во время выполнения можно включить лишь часть возможностей процессора, поддержка которых включена в сборку, через переменную среды NPY_ENABLE_CPU_FEATURES. Они не должны входить в базовый набор, поскольку его наличие предполагается всегда. Попытка включить возможность, которую процессор не поддерживает или для которой NumPy не была собрана, вызывает ошибку.

(gh-22137)

В NumPy появилось пространство имён np.exceptions#

В NumPy появилось отдельное пространство имён для большинства исключений и предупреждений. Они пока остаются и в основном пространстве, хотя в будущем могут постепенно переноситься. Это упрощает их поиск и добавление новых исключений.

(gh-22644)

Функции np.linalg возвращают именованные кортежи#

Функции np.linalg, возвращающие кортежи, теперь возвращают именованные кортежи. Это функции eig(), eigh(), qr(), slogdet() и svd(). Если при определённых именованных аргументах, например svd(compute_uv=False), эти функции возвращают объекты, не являющиеся кортежами, тип результата не меняется.

(gh-22786)

Строковые функции np.char совместимы с пользовательскими dtype по NEP 42#

Пользовательские dtype, представляющие строки Unicode или байтовые строки, теперь можно передавать строковым функциям np.char.

(gh-22863)

Экземпляры строковых dtype можно создавать из абстрактных классов строковых dtype#

Теперь можно создавать экземпляр строкового dtype с заданным размером без строкового имени типа. Например, type(np.dtype('U'))(8) создаёт dtype, эквивалентный np.dtype('U8'). Это особенно полезно для универсального кода, работающего с классами строковых типов данных.

(gh-22963)

Добавлена поддержка компилятора Fujitsu C/C++#

Добавлена поддержка компилятора Fujitsu. Для сборки с компилятором Fujitsu запустите:

python setup.py build -c fujitsu

SSL2 теперь поддерживается #

Добавлена поддержка SSL2. SSL2 - это библиотека, обеспечивающая OpenBLAS совместимые функции GEMM. Для включения SSL2 необходимо редактировать site.cfg и строить с помощью компилятора Fujitsu. См. site.cfg.example.

(gh-22982)

Улучшения#

NDArrayOperatorsMixin явно задаёт отсутствие __slots__#

В классе NDArrayOperatorsMixin теперь явно заданы пустые __slots__, благодаря чему его подклассы могут пользоваться этим механизмом Python.

(gh-23113)

Исправление возведения комплексного нуля в степень#

np.power теперь возвращает другой результат для 0^{non-zero} с комплексными числами. Значение определено только тогда, когда вещественная часть показателя степени больше нуля. Раньше возвращался NaN, если мнимая часть не была строго равна нулю. Результат равен 0+0j или 0-0j.

(gh-18535)

Новое исключение DTypePromotionError#

В NumPy добавлен DTypePromotionError для случаев, когда два dtype нельзя повысить до общего типа. Например:

np.result_type("M8[s]", np.complex128)

вызывает это новое исключение.

( gh-22707 )

np.show_config использует информацию от Meson #

Сведения о сборке и системе теперь включают информацию из Meson. У np.show_config появился необязательный параметр mode для настройки вывода.

(gh-22769)

Исправлена np.ma.diff, не сохранявшая маску при вызове с аргументами prepend/append.#

Вызов np.ma.diff с аргументами prepend и/или append теперь возвращает MaskedArray с сохранением входной маски.

Ранее был возвращен MaskedArray без маски.

( gh-22776 )

Исправлена обработка ошибок C API NumPy в Cython#

У многих функций NumPy на C, объявленных для использования в Cython, отсутствовали правильные указания об ошибках, например except -1 или except *. Теперь они добавлены.

(gh-22997)

Возможность непосредственно создавать дочерние генераторы случайных чисел#

numpy.random.Generator.spawn теперь позволяет напрямую создавать новые независимые дочерние генераторы с помощью механизма numpy.random.SeedSequence.spawn. numpy.random.BitGenerator.spawn делает то же самое для базового генератора битов.

Кроме того, numpy.random.BitGenerator.seed_seq теперь предоставляет прямой доступ к последовательности инициализации, использованной для генератора битов. Это позволяет, например:

seed = 0x2e09b90939db40c400f8f22dae617151
rng = np.random.default_rng(seed)
child_rng1, child_rng2 = rng.spawn(2)

# safely use rng, child_rng1, and child_rng2
Комментарии к примеру на русском
  • Безопасно используем rng, child_rng1 и child_rng2

Раньше это было трудно сделать, не передав SeedSequence в явном виде. Для получения дополнительной информации см. numpy.random.SeedSequence.

(gh-23195)

numpy.logspace теперь поддерживает нескалярный аргумент base#

Аргумент base функции numpy.logspace теперь может быть объектом, подобным массиву, если его форма совместима для трансляции с аргументами start и stop.

(gh-23275)

np.ma.dot() теперь поддерживает массивы с числом измерений, отличным от двух#

Ранее np.ma.dot() работал, только если и a, и b были двумерными. Теперь он работает и с массивами другой размерности, как np.dot().

(gh-23322)

Явный вывод ключей файла .npz в repr#

NpzFile показывает ключи загруженного файла .npz при печати.

>>> npzfile = np.load('arr.npz')

NpzFile 'arr.npz' with keys arr_0, arr_1, arr_2, arr_3, arr_4...

Классы DType теперь доступны в np.dtypes#

Новый модуль numpy.dtypes предоставляет классы DType; в дальнейшем в нём будут появляться и другие средства работы с dtype. Большинству пользователей не требуется обращаться к этим классам напрямую.

(gh-23358)

Удаление метаданных dtype перед сохранением в .npy или .npz#

В настоящее время файл *.npy, содержащий таблицу с dtype с метаданными, невозможно прочесть обратно. Теперь np.save и np.savez перед сохранением опускают метаданные.

(gh-23371)

numpy.lib.recfunctions.structured_to_unstructured возвращает представления в большем числе случаев#

structured_to_unstructured теперь возвращает представление, если шаг между полями постоянен. Ранее промежутки между полями или обратный порядок поля приводили к созданию копии. Изменение касается только ndarray, memmap и recarray. Для всех остальных подклассов массивов поведение не меняется.

( gh-23652 )

Знаковые и беззнаковые целые числа всегда сравниваются корректно#

При смешивании uint64 и int64 NumPy обычно повышает оба типа до float64. Такое поведение спорно и особенно сбивает с толку при сравнениях == и <=: результат может быть неверным, а преобразование незаметно, поскольку возвращается логическое значение. Теперь NumPy даёт правильные результаты таких сравнений, избегая приведения к float.

( gh-23713 )

Ускорена работа np.argsort на процессорах с поддержкой AVX-512#

32-разрядный и 64-разрядный алгоритм быстрой сортировки для np.argsort набирают до 6-кратного ускорения на процессорах, поддерживающих набор команд AVX-512.

На процессорах с набором инструкций AVX-512 quicksort для 16-битных и 64-битных типов данных ускорена до 15 и 9 раз соответственно.

Благодарим корпорацию Intel за финансирование этой работы.

Механизм __array_function__ теперь работает значительно быстрее#

Накладные расходы большинства функций NumPy уменьшены, особенно при использовании именованных аргументов. Это существенно ускоряет многие простые вызовы функций.

(gh-23020)

ufunc.at может быть намного быстрее #

Общая реализация ufunc.at может работать до 9 раз быстрее. Условия такого ускорения:

  • операнды выровнены

  • без приведения типов

Для универсальных функций с подходящими индексированными циклами и одномерными аргументами, удовлетворяющими указанным выше условиям, ufunc.at может работать до 60 раз быстрее — это дополнительное ускорение в 7 раз. Подходящие индексированные циклы добавлены в add, subtract, multiply, floor_divide, maximum, minimum, fmax и fmin.

Внутренняя логика похожа на логику, используемую для обычных уфункций, которые также имеют быстрые пути.

Благодарим группу D. E. Shaw за финансирование этой работы.

Изменения#

np.r_[] и np.c_[] с определенными скалярными значениями #

В редких случаях, главным образом при использовании np.r_ со скалярами, результаты могут отличаться. Основные возможные изменения показаны ниже:

>>> np.r_[np.arange(5, dtype=np.uint8), -1].dtype
int16  # rather than the default integer (int64 or int32)
>>> np.r_[np.arange(5, dtype=np.int8), 255]
array([  0,   1,   2,   3,   4, 255], dtype=int16)
Комментарии к примеру на русском
  • Вместо целочисленного типа по умолчанию int64 или int32

А второй пример возвращал:

array([ 0,  1,  2,  3,  4, -1], dtype=int8)

Первый случай связан с целочисленным скаляром со знаком и беззнаковым целочисленным массивом. Второй — с тем, что 255 не помещается в int8, а NumPy сейчас учитывает конкретные значения, чтобы операция работала. В будущем второй пример изменится из-за NEP 50: вместо результата будет ошибка.

( gh-22539 )

Большинство функций NumPy обёрнуты в вызываемые объекты на C#

Для ускорения диспетчеризации __array_function__ большинство функций NumPy теперь обёрнуты в вызываемые объекты на C и формально не являются функциями Python или методами C. Внешне они по-прежнему ведут себя как функции Python; изменение должно лишь повысить производительность и удобство использования, в частности сократить трассировки ошибок. Однако сообщите разработчикам NumPy, если из-за этого изменения ваша программа работает некорректно.

(gh-23020)

Использование стандартной библиотеки C++#

Сборки NumPy теперь зависят от стандартной библиотеки C++, поскольку расширение numpy.core._multiarray_umath компонуется компоновщиком C++.

(gh-23601)
