Примечания к выпуску NumPy 2.0.0#

NumPy 2.0.0 — первый основной выпуск с 2006 года. Он стал результатом 11 месяцев разработки после предыдущего функционального выпуска: 212 участников подготовили 1078 запросов на изменения. Выпуск содержит много новых возможностей и изменения как Python API, так и C API.

Этот мажорный выпуск содержит изменения, несовместимые с обычным минорным выпуском: нарушение ABI, новые правила повышения типов и изменения API, которые могли не сопровождаться предупреждениями об устаревании в 1.26.x. Помимо этих примечаний, для перехода на NumPy 2.0 полезны следующие документы:

  • Руководство по переходу на NumPy 2.0

  • Рекомендации для NumPy 2.0 в разделе Для авторов пакетов, зависящих от NumPy

Основные изменения#

Основные моменты этого выпуска включают:

  • Новые возможности:

    • Новый тип данных для строк переменной длины StringDType и новое пространство имён numpy.strings с высокопроизводительными универсальными функциями для строковых операций,

    • Поддержка float32 и longdouble во всех функциях numpy.fft.

    • Поддержка стандарта Array API в основном пространстве имён numpy.

  • Повышение производительности:

    • Функции сортировки (sort, argsort, partition, argpartition) ускорены с помощью библиотек Intel x86-simd-sort и Google Highway; в зависимости от оборудования ускорение может быть значительным,

    • поддержка macOS Accelerate и двоичные wheel-пакеты для macOS >=14, значительно ускоряющие операции линейной алгебры в macOS и имеющие примерно втрое меньший размер,

    • Операции со строками фиксированной длины в numpy.char ускорены благодаря реализации универсальных функций, поддерживающих как строки фиксированной длины, так и StringDType,

    • Новый API трассировки и анализа opt_func_info для определения доступных аппаратно-зависимых вычислительных ядер и выбора вызываемых реализаций.

    • numpy.save теперь использует протокол pickle версии 4 при сохранении массивов с dtype object. Это позволяет сохранять объекты pickle размером более 4 ГБ и примерно на 5% ускоряет сохранение больших массивов.

  • Улучшения API Python:

    • Чёткое разделение публичного и внутреннего API, новая структура модулей; каждая публичная функция теперь доступна в одном месте;

    • Удалено множество нерекомендуемых функций и псевдонимов, что должно упростить изучение и использование NumPy. Число объектов в основном пространстве имён уменьшилось примерно на 10%, а в numpy.lib — на 80%,

    • Канонические имена dtype и новая функция интроспекции isdtype,

  • Улучшения C API:

    • Новый публичный C API для создания пользовательских dtype,

    • Удалены многие устаревшие функции и макросы, а закрытые внутренние детали скрыты для облегчения дальнейшего расширения,

    • Новые, более простые в использовании функции инициализации: PyArray_ImportNumPyAPI и PyUFunc_ImportUFuncAPI.

  • Улучшенное поведение:

    • Принятие NEP 50 изменило правила продвижения типов. Это устраняет многие неожиданные результаты: ранее продвижение часто зависело от значений входных массивов, а не только от их dtype. Подробности см. в NEP и руководстве по переходу на NumPy 2.0: это изменение может поменять типы выходных данных и снизить точность результатов операций со смешанными dtype.

    • Целочисленный тип по умолчанию в Windows теперь int64 вместо int32, как и на других платформах,

    • Максимальное количество измерений массива изменено с 32 на 64.

  • Документация:

    • Навигация по справочнику значительно улучшена; также появилась документация по структуре модулей NumPy,

    • Документация по сборке из исходного кода полностью переписана,

Кроме того, внесено множество внутренних изменений NumPy, в том числе продолжен перенос кода с C на C++, что облегчит дальнейшее развитие и сопровождение NumPy.

Принцип «бесплатных обедов не бывает» означает, что за улучшения API и поведения, а также большую расширяемость в будущем приходится платить. Эта цена такова:

  1. Обратная совместимость. В API Python и C внесено много изменений, нарушающих совместимость. В большинстве случаев понятные сообщения об ошибках объясняют, как адаптировать код. Однако для некоторых изменений поведения такое сообщение выдать невозможно. Все эти случаи описаны ниже в разделах об устаревших возможностях и совместимости, а также в руководстве по миграции на NumPy 2.0.

    Обратите внимание, что есть режим ruff для автоматического исправления многих вещей в коде Python.

  2. В ABI NumPy внесены несовместимые изменения. Поэтому двоичные пакеты, использующие C API NumPy и собранные с версией NumPy 1.xx, не работают с NumPy 2.0. При импорте возникает ImportError с сообщением о двоичной несовместимости.

    Можно собрать двоичные файлы с NumPy 2.0, которые во время выполнения будут работать и с NumPy 2.0, и с 1.x. Подробнее см. в разделе Рекомендации для NumPy 2.0.

    Всем пакетам, зависящим от ABI NumPy, рекомендуется выпустить новую версию, собранную с NumPy 2.0, и проверить её работу как с 2.0, так и с 1.26. Чтобы избежать проблем у пользователей, лучше сделать это между выпуском 2.0.0rc1 (ABI которого будет стабилен) и окончательным выпуском 2.0.0.

Версии Python, поддерживаемые этим выпуском: 3.9-3.12.

__array_prepare__ удалён#

При обычных вызовах универсальные функции вызывали __array_prepare__ перед вычислениями (это не относилось к обобщённым универсальным функциям, свёрткам и т. п.). Эта функция также вызывалась вместо __array_wrap__ для результатов некоторых функций линейной алгебры.

Теперь он удалён. Если вы его используете, перейдите на __array_ufunc__ или воспользуйтесь __array_wrap__, который всегда вызывается с контекстом, хотя только после заполнения массива результата. В этих путях выполнения в __array_wrap__ теперь передаётся массив базового класса, а не подкласса.

(gh-25105)

Устаревающие возможности#

  • np.compat объявлен устаревшим, поскольку Python 2 больше не поддерживается.

  • numpy.int8 и аналогичные классы больше не поддерживают преобразование целых чисел Python вне диапазона типа в целочисленные массивы. Например, преобразование 255 в int8 больше не возвращает -1. Границы типов можно проверить с помощью numpy.iinfo(dtype): например, np.iinfo(np.uint16) возвращает min = 0 и max = 65535.

    np.array(value).astype(dtype) даст желаемый результат.

  • np.safe_eval устарел. Вместо этого следует использовать ast.literal_eval.

    (gh-23830)

  • np.recfromcsv, np.recfromtxt, np.disp, np.get_array_wrap, np.maximum_sctype, np.deprecate и np.deprecate_with_doc объявлены устаревшими.

    (gh-24154)

  • np.trapz объявлена устаревшей. Вместо неё используйте np.trapezoid или функцию из scipy.integrate.

  • np.in1d объявлена устаревшей. Используйте np.isin.

  • Псевдоним np.row_stack объявлен устаревшим. Используйте np.vstack напрямую.

    (gh-24445)

  • В __array_wrap__ теперь передаётся arr, context, return_scalar; поддержка реализаций, не принимающих все три аргумента, объявлена устаревшей. Сигнатура должна быть __array_wrap__(self, arr, context=None, return_scalar=False)

    (gh-25409)

  • Использование массивов двумерных векторов в np.cross устарело. Вместо них используйте массивы трёхмерных векторов.

    (gh-24818)

  • Псевдоним np.dtype("a") для np.dtype(np.bytes_) объявлен устаревшим. Вместо него используйте псевдоним np.dtype("S").

    ( gh-24854 )

  • Использование аргументов ключевых слов x и y с функциями assert_array_equal и assert_array_almost_equal устарело. Вместо этого передайте первые два аргумента как позиционные аргументы.

    (gh-24978)

numpy.fft: объявление устаревшими n-мерных преобразований со значениями None в аргументах#

В соответствии со стандартом Array API использование fftn, ifftn, rfftn, irfftn, fft2, ifft2, rfft2 или irfft2 с параметром s, отличным от None, и параметром axes, равным None, объявлено устаревшим. Чтобы сохранить прежнее поведение для массива с k измерениями, передайте в axes последовательность [0, …, k-1].

Кроме того, передавать в s массив со значениями None теперь не рекомендуется: это объявлено устаревшим, поскольку и документация NumPy, и стандарт Array API определяют параметр как последовательность целых чисел. Для стандартного поведения соответствующего одномерного преобразования передайте значение по умолчанию его параметра n. Чтобы использовать стандартное поведение для всех осей, аргумент s можно опустить.

(gh-25495)

np.linalg.lstsq теперь использует новое значение rcond по умолчанию#

lstsq теперь использует значение rcond, равное машинной точности, умноженной на max(M, N). Раньше использовалась только машинная точность, а FutureWarning предупреждал о предстоящем изменении. Прежнее поведение по-прежнему можно получить, передав rcond=-1.

Поскольку фактическое использование этих типов почти всегда соответствует size_t/Py_ssize_t, теперь именно так они определены в C. Ранее использовались intptr_t и uintptr_t, что часто было не вполне корректно. Подавляющее большинство машин это не затрагивает: размеры этих типов различаются лишь на крайне редких платформах.

Однако это означает, что:

  • Указатели теперь не обязательно помещаются в массив типа intp. Однако символьные коды p и P по-прежнему можно использовать.

  • Создание массивов intptr_t или uintptr_t в C остается возможным кроссплатформенным способом через PyArray_DescrFromType('p').

  • Введены новые символьные коды nN.

  • Теперь функции C API Python корректно используются при разборе аргументов типа npy_intp.

numpy.fft.helper стал внутренним модулем#

numpy.fft.helper переименован в numpy.fft._helper, чтобы подчеркнуть его внутренний статус. Ко всем экспортируемым им публичным функциям следует обращаться через numpy.fft.

Ось за пределами допустимого диапазона не эквивалентна axis=None#

В некоторых случаях axis=32, а для concatenate — любое большое значение оси, было эквивалентно axis=None. За исключением concatenate, такое поведение было объявлено устаревшим. Теперь любое значение оси за допустимыми границами вызывает ошибку; используйте axis=None.

(gh-25149)

Новое значение именованного аргумента copy конструкторов array и asarray#

Теперь numpy.array и numpy.asarray поддерживают три значения параметра copy:

  • None - копия будет сделана только в случае необходимости.

  • True — Всегда делать копию.

  • False — копия не создаётся. Если она необходима, возникает ValueError.

Значение False изменилось, поскольку теперь возникает исключение, если требуется копия.

( gh-25168 )

Специальный метод __array__ теперь принимает именованный аргумент copy.#

NumPy передаёт copy специальному методу __array__, когда его значение отличается от стандартного (например, при вызове np.asarray(some_object, copy=False)). Сейчас, если это вызывает ошибку из-за неожиданного именованного аргумента, NumPy выводит предупреждение и повторяет вызов без аргумента copy. Объекты с протоколом __array__ должны принимать именованный аргумент copy с тем же смыслом, что и при передаче в numpy.array или numpy.asarray.

( gh-25168 )

Упорядочение инициализации numpy.dtype строками с запятыми#

Интерпретация строк с запятыми немного изменилась: завершающая запятая теперь всегда создаёт структурированный dtype. Раньше np.dtype("i") и np.dtype("i,") считались одинаковыми, а теперь np.dtype("i,") создаёт структурированный dtype с одним полем. Это аналогично np.dtype("i,i") с двумя полями и согласуется с ожидаемым поведением кортежей.

Задание формы подмассива одним числом в скобках, как в np.dtype("(2)i,"), также объявлено устаревшим. Вместо этого используйте np.dtype("(2,)i") или np.dtype("2i"). В дальнейшем число в скобках будет вызывать исключение, как уже происходит при инициализации без запятой, например np.dtype("(2)i").

(gh-25434)

Изменение вычисления знака комплексного числа#

В соответствии со стандартом Array API знак комплексного числа теперь вычисляется как z / |z|. Раньше использовалось менее логичное правило: возвращался знак действительной части, а если она была равна нулю — знак мнимой части. Как и для действительных чисел, при z==0 возвращается ноль.

(gh-25441)

Типы результатов функций, ранее возвращавших список массивов#

Функции, ранее возвращавшие список массивов ndarray, теперь возвращают кортеж. Единообразное использование кортежей для последовательностей массивов упрощает поддержку этих функций JIT-компиляторами, например Numba, а иногда и статическими анализаторами типов. Изменены функции atleast_1d, atleast_2d, atleast_3d, broadcast_arrays, meshgrid, ogrid, histogramdd.

Форма np.unique return_inverse для многомерных входных данных#

Когда многомерные входные данные передаются в np.unique с помощью return_inverse=True, выходные данные unique_inverse теперь имеют такую форму, что входные данные можно реконструировать напрямую с помощью np.take(unique, unique_inverse), когда axis=None, и np.take_along_axis(unique, unique_inverse, axis=axis) в противном случае.

Примечание

Это изменение отменено в версии 2.0.1, кроме случая axis=None. Правильное восстановление всегда выполняется как np.take(unique, unique_inverse, axis=axis). Если требуется поддержка версии 2.0.0, добавьте в код unique_inverse.reshape(-1).

any и all возвращают логические значения для массивов объектов#

Функции и методы any и all теперь возвращают булевы значения и для объектных массивов. Раньше они выполняли свёртку, поведение которой соответствовало операторам Python or и and, возвращающим один из аргументов. Чтобы получить прежнее поведение, используйте np.logical_or.reduce и np.logical_and.reduce.

np.can_cast нельзя вызывать для int, float или complex Python#

np.can_cast больше нельзя вызывать с экземплярами int, float или complex Python. Согласно NEP 50, результат can_cast не должен зависеть от переданного значения. Но для скаляров Python допустимость приведения по правилам "same_kind" или "safe" может зависеть от контекста и значения, поэтому такая поддержка пока не реализована. В некоторых случаях потребуется отдельная ветвь обработки: if type(obj) in (int, float, complex): ....
