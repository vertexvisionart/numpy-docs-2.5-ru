Историческая справка: страница описывает NumPy 2.1.0. Слова «сейчас», «раньше» и «будет» относятся ко времени этого выпуска; описанное поведение может отличаться от NumPy 2.5.

Примечания к выпуску NumPy 2.1.0#

NumPy 2.1.0 поддерживает предстоящий Python 3.13 и прекращает поддержку Python 3.9. Помимо обычных исправлений и обновления поддержки Python, этот выпуск возвращает проект к привычному графику выпусков после продолжительной разработки 2.0. Основные изменения:

  • Поддержка стандарта array-api 2023.12.

  • Поддержка Python 3.13.

  • Предварительная поддержка Python 3.13 без GIL.

В этом выпуске поддерживаются версии Python 3.10–3.13.

Новые функции #

Новая функция numpy.unstack#

Добавлена функция np.unstack(array, axis=...), разбивающая массив вдоль оси на кортеж массивов. Она обратна numpy.stack.

(gh-26579)

Устаревающие возможности#

  • Именованный аргумент fix_imports функции numpy.save объявлен устаревшим. Начиная с NumPy 1.17, numpy.save использует протокол pickle, больше не поддерживающий Python 2, и игнорирует аргумент fix_imports. Этот аргумент оставался только для обратной совместимости, а теперь объявлен устаревшим.

    (gh-26452)

  • Передача нецелочисленных данных первым аргументом bincount объявлена устаревшей: такие данные неявно приводятся к целым числам без предупреждения о потере точности.

    (gh-27076)

Окончательно удалённые устаревшие возможности#

  • Скалары и 0D-массивы запрещены для numpy.nonzero и numpy.ndarray.nonzero.

    ( gh-26268 )

  • Внутренняя функция set_string_function удалена, а PyArray_SetStringFunction заменена заглушкой.

    (gh-26611)

Изменения C API#

Символы API теперь скрыты, но настраиваемы #

Теперь NumPy по умолчанию скрывает добавляемые им символы, обеспечивающие доступ ко всему API NumPy. Поэтому по умолчанию больше нельзя динамически получать API NumPy из другой библиотеки; в Windows это было невозможно и раньше.

Если возникают ошибки компоновки, связанные с PyArray_API или PyArray_RUNTIME_VERSION, можно определить NPY_API_SYMBOL_ATTRIBUTE, чтобы отказаться от этого изменения.

Если проблема возникает из-за того, что заголовочный файл сторонней библиотеки включает NumPy, добавьте #include "numpy/ndarrayobject.h" перед включением этого заголовочного файла и самостоятельно импортируйте NumPy согласно including-the-c-api.

( gh-26103 )

Из npy_3kcompat.h удалено много средств совместимости#

Из npy_3kcompat.h удалены многие устаревшие средства совместимости и вспомогательные функции. Если они вам нужны, включите предыдущую версию этого файла в исходный код своего проекта.

(gh-26842)

Новое поле PyUFuncObject process_core_dims_func #

Поле process_core_dims_func добавлено в структуру PyUFuncObject. Для обобщённых ufunc оно может указывать на функцию типа PyUFunc_ProcessCoreDimsFunc, вызываемую при вызове ufunc. Это позволяет проверять дополнительные ограничения основных измерений и задавать размеры основных выходных измерений, если они ещё не заданы.

(gh-26908)

Новые возможности #

Предварительная поддержка CPython 3.13 без GIL#

CPython 3.13 будет доступен в виде экспериментальной сборки без GIL (free-threaded). Подробнее об этом см. https://py-free-threading.github.io, PEP 703 и примечания к выпуску CPython 3.13.

NumPy 2.1 предварительно поддерживает сборку CPython 3.13 без GIL. Это стало возможным после устранения ряда проблем потокобезопасности в коде NumPy на C. Ранее для кэшей и другого состояния времени выполнения использовалось много глобальных статических переменных C. Теперь код либо переработан для отказа от глобального состояния, либо использует состояние, локальное для потока, либо защищает доступ блокировками.

Поддержка Python без GIL не означает, что NumPy потокобезопасен. Совместный доступ к ndarray только для чтения должен быть безопасным. Но NumPy предоставляет общее изменяемое состояние, а в сам объект массива не добавлены блокировки для последовательного доступа к нему. Если один массив изменяется из нескольких потоков, пользовательский код должен предотвращать гонки. Одновременное изменение массива действительно может аварийно завершить NumPy, например при параллельном вызове ufunc и метода resize. Пока наша рекомендация — не делать этого. В будущем мы хотели бы предоставить более строгие гарантии.

Особого внимания требуют объектные массивы: раньше GIL блокировал доступ к ним, а в сборке без GIL этой защиты больше нет. Подробнее об объектных массивах в свободнопоточной сборке см. задачу #27199.

Если вас интересует Python без GIL, например для переноса вычислений с нескольких процессов на потоки Python, приглашаем вас тестировать и экспериментировать.

Если вы подозреваете проблему в NumPy, создайте задачу, предварительно проверив, воспроизводится ли она в обычной сборке CPython 3.13 с GIL. Многие ошибки многопоточности возникают и в коде, освобождающем GIL; отключение GIL лишь облегчает их проявление.

(gh-26157)

  • numpy.reshape и numpy.ndarray.reshape теперь поддерживают аргументы shape и copy.

    (gh-26292)

  • NumPy теперь поддерживает DLPack v1; поддержка более ранних версий в будущем будет объявлена устаревшей.

    ( gh-26501 )

  • numpy.asanyarray теперь поддерживает аргументы copy и device, как numpy.asarray.

    (gh-26580)

  • numpy.printoptions, numpy.get_printoptions и numpy.set_printoptions теперь поддерживают новый параметр override_repr для настройки поведения repr(array).

    (gh-26611)

  • Добавлены numpy.cumulative_sum и numpy.cumulative_prod — совместимые с Array API альтернативы numpy.cumsum и numpy.cumprod. Новые функции могут включать в результат фиксированное начальное значение: ноль для sum и единицу для prod.

    ( gh-26724 )

  • numpy.clip теперь поддерживает именованные аргументы max и min, предназначенные для замены a_min и a_max. Кроме того, вызовы np.clip(a) и np.clip(a, None, None) теперь возвращают копию входного массива вместо возникновения ошибки.

    ( gh-26724 )

  • numpy.astype теперь поддерживает аргумент device.

    ( gh-26724 )

f2py может генерировать расширения C, совместимые с Python без GIL#

Передайте --freethreading-compatible инструменту командной строки f2py, чтобы создать расширение C, помеченное как совместимое с интерпретатором CPython без GIL (free threading). Это предотвращает повторное включение GIL при импорте расширения. f2py не проверяет потокобезопасность кода Fortran, поэтому перед установкой этой отметки необходимо самостоятельно убедиться, что код Fortran, для которого создаётся обёртка, потокобезопасен.

( gh-26981 )

Улучшения#

histogram при автоматическом выборе интервалов для целочисленных данных теперь возвращает ширину интервалов не меньше 1#

Для целочисленных входных данных интервалы шириной меньше 1 создают лишние пустые интервалы. Теперь этого не происходит при вычислении числа интервалов одним из алгоритмов histogram_bin_edges.

( gh-12150 )

Параметр типа формы ndarray теперь ковариантен и ограничен tuple[int, ...]#

Статическая типизация ndarray развивается уже давно; это изменение продолжает работу. Это обобщённый тип с параметрами для формы и типа данных. Раньше параметр типа формы мог иметь любое значение. Теперь он ограничен кортежем целых чисел, что соответствует поведению ndarray.shape. Кроме того, этот параметр стал ковариантным вместо инвариантного. Изменение относится и к подтипам ndarray, например numpy.ma.MaskedArray. Подробнее см. документацию по типизации.

( gh-26081 )

np.quantile с методом closest_observation выбирает ближайшую порядковую статистику с чётным индексом#

В пограничных случаях выбор ближайшей порядковой статистики теперь разрешает равенство расстояний в пользу чётного индекса вместо нечётного. Реализация NumPy теперь соответствует другим эталонным реализациям.

(gh-26656)

lapack_lite теперь потокобезопасен#

NumPy предоставляет минимальную, низкопроизводительную реализацию LAPACK под названием lapack_lite. Она используется, если при сборке не обнаружена системная библиотека BLAS/LAPACK.

Раньше lapack_lite не был потокобезопасным. В одном потоке проблем не возникало, но параллельные операции линейной алгебры могли из-за гонок данных вызывать ошибки, неверные результаты или ошибки сегментации.

Добавлена глобальная блокировка, которая обеспечивает последовательный доступ к lapack_lite из нескольких потоков.

( gh-26750 )

Менеджер контекста numpy.printoptions теперь безопасен при использовании в потоках и асинхронных задачах#

В предыдущих версиях NumPy параметры вывода задавались сочетанием глобальных переменных Python и C. После рефакторинга состояние хранится в объекте Python ContextVar, благодаря чему менеджер контекста безопасен при использовании в потоках и асинхронных задачах.

(gh-26846)

Аннотации типов для numpy.polynomial#

Начиная с выпуска 2.1 функции и вспомогательные классы numpy.polynomial и его подпакетов снабжены аннотациями типов PEP 484.

(gh-26897)

Улучшены аннотации типов numpy.dtypes#

Аннотации типов numpy.dtypes теперь точнее отражают поведение во время выполнения: псевдонимы типов numpy.dtype заменены специализированными dtype подтипами, а отсутствовавшие аннотации numpy.dtypes.StringDType добавлены.

(gh-27008)

Улучшения производительности и изменения #

  • numpy.save теперь использует протокол pickle версии 4 при сохранении массивов с dtype object. Это позволяет сохранять объекты pickle размером более 4 ГБ и примерно на 5% ускоряет сохранение больших массивов.

    (gh-26388)

  • OpenBLAS для x86_64 и i686 собирается с меньшим числом вычислительных ядер. Тестирование выявило пять групп производительности вокруг ядер PRESCOTT NEHALEM SANDYBRIDGE HASWELL SKYLAKEX.

    (gh-27147)

  • OpenBLAS для Windows компонуется без quadmath, что упрощает лицензирование

    (gh-27147)

  • Из-за регресса в OpenBLAS в Windows улучшения производительности при использовании нескольких потоков для OpenBLAS 0.3.26 были отменены.

    (gh-27147)

ma.cov и ma.corrcoef теперь значительно быстрее #

Внутренняя функция переработана вместе с ma.cov и ma.corrcoef. Теперь они работают значительно быстрее, особенно для больших замаскированных массивов.

(gh-26285)

Изменения#

  • Поскольку numpy.vecdot теперь является универсальной функцией, её сигнатура стала менее точной из-за ограничений файла описаний типов для универсальных функций.

    (gh-26313)

  • numpy.floor, numpy.ceil и numpy.trunc теперь не приводят входные массивы целочисленного и логического типов к типу с плавающей точкой.

    (gh-26766)

ma.corrcoef может привести к несколько иному результату #

Ранее ma.corrcoef вычислял стандартные отклонения отдельно для каждой пары переменных по их парным наблюдениям. Этот подход изменён: стандартные отклонения используются для нормирования ковариации, оцениваемой через ma.cov, а эта функция не отбирает наблюдения попарно, поэтому прежний расчёт был излишним. Теперь для нормирования используется более подходящее стандартное отклонение каждой переменной. Это значительно сокращает время выполнения, но даёт немного другие оценки коэффициентов корреляции, если наблюдения пары переменных не совпадают. Во всех остальных случаях оценки остаются прежними; в частности, для массива с маской без замаскированных значений получается та же корреляционная матрица, что и у corrcoef.

(gh-26285)

Исправления безопасности приведения типов в copyto и full#

copyto теперь корректно следует NEP 50, в том числе при определении безопасности приведения типов. Приведения целого Python к целому NumPy и float Python к float NumPy считаются «safe», даже если присваивание может завершиться ошибкой или возможна потеря точности. Поэтому следующие примеры немного меняются:

  • np.copyto(int8_arr, 1000) ранее выполнял приведение типов по правилу unsafe/same-kind

    целого числа Python. Теперь всегда возникает исключение; для небезопасного приведения нужно передать массив или скаляр NumPy.

  • np.copyto(uint8_arr, 1000, casting="safe") вызовет OverflowError вместо TypeError, связанной с приведением типов по правилу same-kind.

  • np.copyto(float32_arr, 1e300, casting="safe") переполнится до inf, поскольку float32 не вмещает 1e300, вместо выдачи TypeError.

Кроме того, при присваивании скаляров NumPy (или нульмерных массивов) учитывается только dtype, поэтому следующий код ведёт себя иначе:

  • np.copyto(float32_arr, np.float64(3.0), casting="safe") вызывает исключение.

  • np.coptyo(int8_arr, np.int64(100), casting="safe") вызывает ошибку. Раньше NumPy проверял, помещается ли значение 100 в int8_arr. Примечание переводчика: в примере оригинала имя np.coptyo содержит опечатку; правильно np.copyto. Именно np.copyto в этом примере вызывает TypeError при casting="safe".

Это приводит поведение copyto, full и full_like в соответствие с правильным поведением NumPy 2.

( gh-27091 )
