Историческая справка: страница описывает NumPy 2.4.0. Слова «сейчас», «раньше» и «будет» относятся ко времени этого выпуска; описанное поведение может отличаться от NumPy 2.5.

Примечания к выпуску NumPy 2.4.0#

NumPy 2.4.0 продолжает улучшать поддержку Python без GIL (free-threaded), реализацию пользовательских dtype и аннотации. Также удалено много ранее устаревших возможностей и исправлены ошибки.

Этот выпуск поддерживает версии Python 3.11–3.14.

Основные изменения#

Помимо аннотаций и именованного аргумента same_value, основные изменения версии 2.4 интересны прежде всего разработчикам зависимых проектов. Они должны упростить реализацию новых пользовательских dtype.

  • Многочисленные улучшения аннотаций типов, в частности получение сведений о сигнатурах во время выполнения.

  • Для аргумента casting добавлено значение 'same_value' для приведения типов с сохранением значений.

  • Новая функция PyUFunc_AddLoopsFromSpec позволяет добавлять пользовательские циклы сортировки через API ArrayMethod.

  • Новый протокол __numpy_dtype__.

Устаревающие возможности#

Установка атрибута strides устарела #

Присваивание атрибуту strides объявлено устаревшим: изменение массива небезопасно при совместном использовании, особенно несколькими потоками. Вместо этого создайте новое представление без копирования:

  • np.lib.stride_tricks.strided_window_view, если применимо,

  • np.lib.stride_tricks.as_strided для общего случая,

  • или конструктор np.ndarray (buffer является исходным массивом) для облегченной версии.

( gh-28925 )

Передача аргумента out в np.maximum, np.minimum по позиции объявлена устаревшей#

Передача выходного массива out в numpy.maximum и numpy.minimum позиционным аргументом объявлена устаревшей. Например, np.maximum(a, b, c) выдаст предупреждение об устаревании, поскольку c трактуется как выходной буфер, а не как третий входной аргумент.

Всегда передавайте выходной массив как именованный аргумент, например np.maximum(a, b, out=c). Это проясняет назначение аргумента и упрощает аннотации типов.

(gh-29052)

Параметр align= в np.dtype() должен иметь логическое значение#

При создании dtype выдаётся VisibleDeprecationWarning, если align= не является булевым значением. Это прежде всего предотвращает случайную передачу флага выравнивания подмассива там, где он не действует, например np.dtype("f8", 3) вместо np.dtype(("f8", 3)). Настоятельно рекомендуется всегда передавать align= как именованный аргумент.

(gh-29301)

Утилиты управления проверками утверждений и предупреждениями объявлены устаревшими#

np.testing.assert_warns и np.testing.suppress_warnings устарели. Вместо этого используйте warnings.catch_warnings, warnings.filterwarnings, pytest.warns или pytest.filterwarnings.

(gh-29550)

np.fix готовится к объявлению устаревшей#

Функция numpy.fix будет объявлена устаревшей в будущем выпуске. Вместо неё рекомендуется numpy.trunc, которая так же отбрасывает дробную часть числа. Средства статической проверки типов уже могут предупреждать об использовании numpy.fix.

( gh-30168 )

Изменение ndarray.shape на месте готовится к объявлению устаревшим#

В будущем прямое присваивание атрибуту ndarray.shape будет объявлено устаревшим. Вместо изменения формы на месте рекомендуется использовать функцию numpy.reshape. Статические анализаторы типов уже могут выдавать предупреждение при присваивании атрибуту ndarray.shape.

Примечания о совместимости#

  • Модули расширения NumPy на C начали использовать многофазную инициализацию, определённую в PEP 489. Добавлена явная проверка, что каждый такой модуль импортируется только один раз в процессе Python. В результате удаление numpy из sys.modules и повторный импорт теперь завершаются ошибкой ImportError. Это и раньше было небезопасно и могло приводить к неожиданным побочным эффектам, хотя ошибка не вызывалась.

    (gh-29030)

  • numpy.round теперь всегда возвращает копию. Раньше он возвращал представление целочисленных входных данных для decimals >= 0 и копию во всех остальных случаях. Это изменение приводит round в соответствие с ceil, floor и trunc.

    (gh-29137)

  • Средства проверки типов больше не допускают вызовы numpy.arange с именованным аргументом start. Это изменение внесено для совместимости со стандартом Array API. Во время выполнения по-прежнему можно вызывать numpy.arange с именованным аргументом start.

    ( gh-30147 )

  • Макрос NPY_ALIGNMENT_REQUIRED удалён. Он был определён в файле npy_cpu.h и потому мог считаться частично публичным. На современных компиляторах и оборудовании выравнивание требуется почти всегда, поэтому NumPy больше не использует этот макрос. Вероятно, его почти никто не использует, но для проверки можно выполнить компиляцию с флагом -Wundef или его аналогом.

    ( gh-29094 )

Изменения C API#

В перечисление NPY_SORTKIND добавлены новые значения#

Это представляет интерес, если вы используете PyArray_Sort или PyArray_ArgSort. Мы изменили семантику старых имен в перечислении NPY_SORTKIND и добавили новые. Изменения обратно совместимы, и перекомпиляция не требуется. Новые имена, представляющие интерес:

  • NPY_SORT_DEFAULT — сортировка по умолчанию (то же значение, что у NPY_QUICKSORT)

  • NPY_SORT_STABLE — сортировка должна быть устойчивой (то же значение, что у NPY_MERGESORT)

  • NPY_SORT_DESCENDING – сортировка должна быть по убыванию

Семантическое изменение заключается в том, что NPY_HEAPSORT при использовании отображается в NPY_QUICKSORT. Обратите внимание, что NPY_SORT_DESCENDING еще не реализован.

(gh-29642)

Новый слот NPY_DT_get_constant для получения констант DType#

В API DType добавлен слот NPY_DT_get_constant, позволяющий реализациям dtype предоставлять константы, например машинные пределы и специальные значения. Функция слота имеет следующую сигнатуру:

int get_constant(PyArray_Descr *descr, int constant_id, void *ptr)

Возвращает 1 при успехе, 0, если константа недоступна, и -1 при ошибке. Функция всегда вызывается с удерживаемым GIL и может записывать данные в невыровненную память.

Целые константы (отмеченные битом 1 << 16) возвращают значения npy_intp, в то время как константы с плавающей запятой возвращают значения родного типа dtype.

Реализация этого механизма позволяет пользовательским DType предоставлять значения numpy.finfo.

(gh-29836)

В C API добавлена вспомогательная функция PyUFunc_AddLoopsFromSpecs.#

Позволяет за один вызов добавить несколько циклов ufunc по их спецификациям с помощью массива структур PyUFunc_LoopSlot, завершающегося NULL. Позволяет регистрировать циклы сортировки и косвенной сортировки через новый API ArrayMethod.

(gh-29900)

(gh-29423)

Параметр ndmax для numpy.array#

Опция ndmax теперь доступна для numpy.array. Она явно ограничивает максимальное количество измерений, созданных из вложенных последовательностей.

Это особенно полезно при создании массивов объектов, подобных спискам, с dtype=object. По умолчанию NumPy рекурсивно проходит все уровни вложенности, создавая массив с максимально возможным числом измерений. Но если вложенные структуры нужно сохранить как объекты, такое поведение нежелательно. Параметр ndmax позволяет явно ограничить глубину рекурсии.

# Default behavior: Creates a 2D array
>>> a = np.array([[1, 2], [3, 4]], dtype=object)
>>> a
array([[1, 2],
       [3, 4]], dtype=object)
>>> a.shape
(2, 2)

# With ndmax=1: Creates a 1D array
>>> b = np.array([[1, 2], [3, 4]], dtype=object, ndmax=1)
>>> b
array([list([1, 2]), list([3, 4])], dtype=object)
>>> b.shape
(2,)
Комментарии к примеру на русском
  • По умолчанию создаётся двумерный массив
  • При ndmax=1 создаётся одномерный массив

( gh-29569 )

Предупреждение при использовании where без out#

Вызов универсальной функции с маской where, но без позиционного или именованного аргумента out, теперь выдаёт предупреждение. Пользователи часто ожидают определённых значений в позициях результата, где маска равна False, хотя универсальная функция эти позиции не заполняет. Предупреждение можно подавить, указав out=None.

( gh-29813 )

Сортировка и получение индексов сортировки для DType поддерживают API ArrayMethod#

Пользовательские dtype теперь могут реализовать собственную сортировку и получение индексов сортировки через API ArrayMethod. Этот механизм можно использовать вместо слотов PyArray_ArrFuncs, которые в будущем могут быть объявлены устаревшими.

Методы сортировки и получения индексов сортировки регистрируются передачей реализующих их спецификаций ArrayMethod новой функции PyUFunc_AddLoopsFromSpecs. Подробности см. в документации API ArrayMethod.

(gh-29900)

Новый протокол __numpy_dtype__#

NumPy теперь имеет новый протокол __numpy_dtype__. NumPy будет проверять этот атрибут при преобразовании в NumPy dtype через np.dtype(obj) или любой аргумент dtype=.

Разработчикам зависимых проектов рекомендуется реализовать этот протокол для всех объектов, подобных dtype, которые раньше могли предоставлять атрибут .dtype, возвращающий dtype NumPy. В будущем мы планируем объявить .dtype устаревшим, чтобы объекты, подобные массивам и имеющие атрибут .dtype, не интерпретировались как dtype. При желании можно реализовать __numpy_dtype__, чтобы предупреждение или ошибка возникали раньше: при наличии этого метода .dtype игнорируется.

(gh-30179)

Улучшения#

Исправлены граничные случаи индексации flatiter#

Объект flatiter теперь использует ту же логику подготовки индексов, что и ndarray. Это обеспечивает согласованное поведение и устраняет несколько ошибок, при которых недопустимые индексы принимались или интерпретировались неправильно.

Основные исправления и улучшения:

  • Более строгая валидация индекса

    • Логические индексы, не являющиеся массивами, например arr.flat[[True, True]], ошибочно обрабатывались как arr.flat[np.array([1, 1], dtype=int)]. Теперь они вызывают ошибку индексации. В будущем индексы, соответствующие форме итератора, предположительно не будут вызывать ошибку и будут обрабатываться как обычные логические индексы. Для такого поведения уже сейчас используйте np.asarray(<index>).

    • Индексы с плавающей точкой, не являющиеся массивами, также приводились к целым числам и ошибочно обрабатывались как arr.flat[np.array([1.0, 1.0], dtype=int)]. Теперь это поведение объявлено устаревшим и будет удалено в будущей версии.

    • Нульмерные логические индексы, такие как arr.flat[True], также объявлены устаревшими и будут удалены в будущей версии.

  • Единообразные типы ошибок:

    Некоторые недопустимые индексы flatiter, ранее вызывавшие ValueError, теперь корректно вызывают IndexError, как и в случае ndarray.

  • Улучшенные сообщения об ошибках:

    Сообщение об ошибке для неподдерживаемых операций с индексами теперь содержит более подробную информацию, включая явный список допустимых типов индексов вместо общего IndexError: unsupported index operation .

(gh-28590)

Улучшена обработка ошибок в np.quantile#

np.quantile теперь вызывает исключение, если:

  • Все веса равны нулю

  • Хотя бы один вес — np.nan.

  • Хотя бы один вес — np.inf.

(gh-28595)

Усовершенствованное сообщение об ошибке для assert_array_compare #

Сообщение об ошибке от assert_array_compare, используемой в таких функциях, как assert_allclose, assert_array_less и других, теперь также содержит индексы элементов, для которых проверка не прошла.

( gh-29112 )

Вывод сведений о единице измерения в __repr__ для datetime64("NaT")#

Для объекта datetime64 со значением “Not a Time” (NaT) метод __repr__ теперь включает единицу времени типа datetime64. Это соответствует поведению объекта timedelta64.

(gh-29396)

Повышение производительности для скалярных вычислений #

Вычисления на скалярах ускорены примерно в 6 раз для ufunc с одним входом, например np.sin(scalar). Отставание от аналогов из math сократилось с 19 до 3 раз; скорость для массивов не изменилась.

( gh-29819 )

Рефакторинг numpy.finfo#

Класс numpy.finfo полностью переработан: теперь константы с плавающей точкой берутся непосредственно из макросов компилятора C, а не определяются во время выполнения. Это повышает точность и переносимость; также исправлены вычисления нескольких атрибутов:

  • Константы eps, min, max, smallest_normal и smallest_subnormal теперь получаются непосредственно из стандартных макросов C (FLT_EPSILON, DBL_MIN и др.), что обеспечивает правильные значения для платформы.

  • Устаревший механизм обнаружения во время выполнения MachAr был удален.

  • Производные атрибуты исправлены в соответствии со стандартными определениями: machep и negep теперь используют int(log2(eps)); nexp учитывает все битовые комбинации показателя степени; nmant исключает неявный бит; minexp соответствует определению стандарта C.

  • Константы longdouble, в частности smallest_normal, теперь соответствуют определениям стандарта C для соответствующей платформы.

  • Добавлена специальная обработка формата IBM double-double на PowerPC.

  • В test_finfo.py добавлен набор тестов, проверяющий все свойства finfo по ожидаемым характеристикам машинной арифметики для float16, float32 и float64.

(gh-29836)

В numpy.trim_zeros теперь поддерживается несколько осей#

Аргумент axis функции numpy.trim_zeros теперь принимает последовательность. Например, np.trim_zeros(x, axis=(0, 1)) обрезает нули многомерного массива x по осям 0 и 1. Это исправляет проблему gh‑29945; изменение реализовано в запросе gh‑29947.

(gh-29947)

Поддержка интроспекции сигнатур во время выполнения значительно улучшена #

Многие функции, классы и методы NumPy, которые раньше вызывали ValueError при передаче в inspect.signature(), теперь предоставляют содержательные сигнатуры. Это улучшает проверку типов во время выполнения, автодополнение в IDE, создание документации и анализ объектов во время выполнения во всём API NumPy.

Всего обновлено более трёхсот классов и функций, включая основные классы ndarray, generic, dtype, ufunc, broadcast, nditer и другие; большинство методов ndarray и скалярных типов; конструкторы массивов (array, empty, arange, fromiter и другие); все ufuncs; а также многие часто используемые функции, в том числе dot, concat, where, bincount и can_cast.

(gh-30208)

Улучшения производительности и изменения #

Повышена производительность np.unique для строковых типов данных#

Алгоритм поиска уникальных значений на основе хеширования ускоряет обработку больших строковых массивов на порядок. Во внутреннем тесте примерно на миллиарде строковых элементов np.unique с хешированием завершился примерно за 33,5 секунды, а метод на основе сортировки — за 498 секунд: при поиске уникальных строк без сортировки результата ускорение составило около 15 раз. Это значительно сокращает время поиска уникальных значений в очень больших строковых наборах данных.

(gh-28767)

Переработка np.ndindex с использованием itertools.product#

Функция numpy.ndindex теперь использует itertools.product внутри, что существенно ускоряет обход больших пространств индексов при сохранении поведения и интерфейса. Например, в тесте производительности NumPy ndindex для массива формы (50, 60, 90) достигнуто ускорение в 5.2 раза.

( gh-29165 )

Ускорение np.unique для комплексных типов данных#

Алгоритм выделения уникальных элементов на основе хеширования теперь поддерживает и комплексные dtype, заметно повышая производительность.

В наших тестах на массивах complex128 с 200 000 элементами хеш-подход был примерно на 1,4-1,5× быстрее, чем исходный уровень на основе сортировки, когда было 20% уникальных значений, и примерно на 5× быстрее, когда было 0,2% уникальных значений.

(gh-29537)

Изменения#

  • Умножение строки на целое число теперь вызывает OverflowError вместо MemoryError, если длина получаемой строки превышает представимый предел. Это соответствует поведению Python.

    (gh-29060)

  • Улучшена точность np.quantile и np.percentile для 16- и 32-битных входных данных с плавающей запятой.

    (gh-29105)

unique_values для типов строк может возвращать несортированные данные #

np.unique теперь поддерживает удаление повторов в строковых типах данных с помощью хеширования. Алгоритм хеш-таблицы теперь применяется к байтовым строкам (‘S’), строкам Unicode (‘U’) и экспериментальному строковому типу (‘T’, StringDType). Поэтому np.unique() для массива строк использует более быстрый алгоритм поиска уникальных значений на основе хеширования. Он не гарантирует сортировку результата. Этот алгоритм также работает с массивами StringDType, содержащими None (пропущенные значения), если задано equal_nan=True, то есть пропуски считаются равными.

(gh-28767)

Управление возможностями CPU x86, выбираемыми диспетчеризацией#

ВАЖНО: значение cpu-baseline по умолчанию для x86 повышено до микроархитектуры x86-64-v2. Для поддержки более старых процессоров при сборке можно задать none, однако SIMD-оптимизации для процессоров, выпущенных до 2009 года, больше не сопровождаются.

В NumPy возможности процессоров x86 объединены в группы по микроархитектурам вместо использования отдельных признаков. Это соответствует стандартам дистрибутивов Linux и требованиям Google Highway.

Ключевые изменения:

  • Отдельные возможности x86 заменены уровнями микроархитектуры: X86_V2, X86_V3 и X86_V4

  • Базовый уровень поднят до X86_V2.

  • Улучшено поведение оператора -: теперь правильно исключаются последующие возможности, подразумевающие исключённую

  • Для сохранения обратной совместимости в Meson добавлены перенаправления удалённых имён возможностей

  • Удалены обходные решения для совместимости с компиляторами, частично поддерживающими возможности процессора (например, AVX512 без операций с масками)

  • Удалены устаревшие возможности AMD (XOP, FMA4) и прекращена поддержка Intel Xeon Phi

Исправлена ошибка в matmul для именованного аргумента out с массивом, не расположенным непрерывно в памяти#

В некоторых случаях, когда out не был непрерывно расположен в памяти, np.matmul вызывал повреждение памяти или срабатывание assert на уровне C. Ошибка появилась в v2.3.0 и исправлена в v2.3.1.

Изменено поведение __array_interface__ с указателем NULL#

Интерфейс массива теперь принимает указатели NULL (при этом NumPy сам выделяет фиктивный участок памяти). Раньше они ошибочно приводили к выполнению недокументированной ветви обработки скаляров. Если вам действительно требовалось такое поведение, его пока можно воспроизвести через предусмотренную для скаляров ветвь, вообще не указывая поле data.

( gh-29338 )

unique_values для комплексных dtype может возвращать неотсортированные данные#

np.unique теперь поддерживает удаление повторов с помощью хеширования для комплексных dtype. Алгоритм на основе хеш-таблицы распространён на все комплексные типы (c), включая варианты расширенной точности. Он быстрее извлекает уникальные значения, но не гарантирует их сортировку.

(gh-29537)

Сортировка kind='heapsort' теперь соответствует kind='quicksort'#

Скорее всего, вы не заметите изменения. Однако если изменится время выполнения или порядок индексов при неустойчивой сортировке argsort, вероятная причина — в нём. Сообщите нам о снижении производительности. А если она повысилась, поздравьте нас :)

(gh-29642)

numpy.typing.DTypeLike больше не принимает None #

Псевдоним типа numpy.typing.DTypeLike больше не принимает None. Вместо

dtype: DTypeLike = None

Теперь она должна быть

dtype: DTypeLike | None = None

Вместо этого.

Если существующий проект уже их использует, лучше применять тот же набор инструментов компиляции; в Windows on Arm это clang-cl.
