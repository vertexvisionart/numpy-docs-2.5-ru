Примечания к выпуску NumPy 2.5.0#

NumPy 2.5.0 — переходный выпуск. Он прекращает поддержку Python 3.11, завершая использование distutils, и удаляет множество возможностей, объявленных устаревшими в серии 2.0.x. Также улучшена работа без GIL и добавлена сортировка по убыванию для соответствия стандарту Array API. Выполнен значительный объём подготовки к Python 3.15, поддержка которого начнётся с первого кандидата на выпуск.

Этот выпуск поддерживает версии Python 3.12–3.14.

Основные изменения#

  • Distutils удалён,

  • Завершены периоды устаревания многих возможностей, см. ниже,

  • Множество новых объявлений об устаревании, см. ниже,

  • Многочисленные улучшения статической типизации,

  • Улучшена поддержка многопоточности без GIL (free threading),

  • Поддержка сортировки по убыванию.

Другие дополнения перечислены ниже в разделе «Новые возможности».

Устаревающие возможности#

  • numpy.char.chararray объявлен устаревшим. Вместо него используйте ndarray со строковым или байтовым dtype.

    ( gh-30605 )

  • numpy.take теперь корректно проверяет, можно ли привести результат к переданному out=out по правилу same_kind. Если проверка не проходит, выдаётся DeprecationWarning. Ранее take ошибочно проверяла возможность приведения out к типу результата — в обратном направлении. Объявление этого поведения устаревшим также затрагивает compress и, возможно, другие функции. В будущих версиях NumPy проверка приведения может стать ещё строже.

    ( gh-30615 )

  • Функции numpy.char.[as]array объявлены устаревшими. Вместо них используйте numpy.[as]array со строковым или байтовым типом данных.

    (gh-30802)

  • Присваивание атрибуту dtype объявлено устаревшим: изменение массива небезопасно, если к нему есть совместный доступ, особенно из нескольких потоков. Вместо этого можно создать представление с новым dtype с помощью array.view(dtype=new_dtype).

    (gh-29244)

  • Присваивание атрибуту shape объявлено устаревшим: изменение массива небезопасно при совместном использовании, особенно несколькими потоками. Вместо этого создайте новое представление через np.reshape или np.ndarray.reshape. Например: x = np.arange(15); x = np.reshape(x, (3, 5)). Чтобы гарантировать отсутствие копирования данных, используйте np.reshape(..., copy=False).

    Хотя задавать форму массива напрямую не рекомендуется, в случаях, когда это трудно обойти, например в __array_finalize__, можно использовать внутренний метод np.ndarray._set_shape.

    (gh-29536)

  • Использование единицы generic в numpy.timedelta64 объявлено устаревшим, поскольку оно может приводить к неожиданному поведению, например к нетранзитивным сравнениям. Подробнее см. gh-28287. Вместо этого при создании объекта явно задавайте единицу измерения, например 's' (секунды) или 'D' (дни), для numpy.timedelta64. Из-за этого изменения операции, неявно использующие единицу generic, также объявлены устаревшими. Например:

    arr = np.array([1, 2, 3], dtype="m8[s]")

# `1` is implicitly converted to generic timedelta64
arr + 1
    Комментарии к примеру на русском
    • `1` неявно преобразуется в timedelta64 без конкретной единицы времени

    (gh-29619)

  • Изменение размера массива NumPy на месте объявлено устаревшим: изменять общий массив небезопасно, особенно при доступе из нескольких потоков. Вместо этого можно создать массив нужного размера через np.resize.

    (gh-30181)

  • numpy.fix устарел, вместо него используйте numpy.trunc. Это быстрее и соответствует стандарту Array API. Обе функции предоставляют одинаковую функциональность: округление элементов массива в сторону нуля.

    (gh-30644)

  • numpy.ma.round_ объявлена устаревшей. Вместо неё можно использовать numpy.ma.round.

    (gh-30738)

  • numpy.typename объявлен устаревшим, поскольку возвращаемые им имена устарели и были несогласованными. Вместо него можно использовать numpy.dtype.name.

    (gh-30774)

  • Нецелочисленные входные значения для numpy.triu_indices и numpy.tril_indices объявлены устаревшими. То же относится к нецелочисленным значениям параметров M, k и N функции numpy.tri, а также параметра k функций numpy.tril_indices_from и numpy.triu_indices_from.

    (gh-30869)

  • Устаревшие возможности пользовательского свойства dtype и __array_finalize__.

    Ранее arr.view(dtype=new_dtype) также вызывал arr.dtype = new_dtype для подклассов, то есть присваивал значение атрибуту. Теперь этот способ объявлен устаревшим, а поведение уточнено, поэтому обновить код стоит даже тем подклассам, для которых DeprecationWarning не выдаётся.

    Подкласс с логикой, зависящей от dtype, например с проверкой dtype в __array_finalize__ или свойством dtype, теперь должен:

    • Задайте _set_dtype = None: тогда arr.view(dtype=new_dtype) вызовет __array_finalize__ с новым dtype, что гарантирует выполнение всех проверок из __array_finalize__.

    • Для быстрого исправления можно определить _set_dtype как функцию, вызывающую ndarray._set_dtype(), чтобы избежать DeprecationWarnings. В будущих версиях возможен переход к варианту _set_dtype = None.

    По возможности следуйте NumPy и запрещайте пользователям изменять dtype, поскольку такая возможность объявлена устаревшей. ndarray._set_dtype() может требоваться для некоторых схем завершения создания подклассов; в остальных случаях его следует избегать.

    ( gh-31293 )

Примечания о совместимости#

linalg.eig и linalg.eigvals теперь всегда возвращают комплексные массивы#

Раньше возвращаемые значения зависели от того, оказались ли собственные значения на вещественной оси, что для произвольной несимметричной матрицы не гарантируется.

Это изменение делает результат единообразным, устраняя зависимость от значения. Для прежнего поведения выполните:

w = eigvals(a)
if np.any(w.imag == 0):  # this is what NumPy used to do
    w = w.real
Комментарии к примеру на русском
  • Так NumPy работал раньше

Если матрица симметричная или эрмитова, используйте eigh и eigvalsh вместо eig и eigvals. Эти функции гарантированно возвращают действительные значения. Типичный пример — ковариационные матрицы, симметричные и положительно определённые по построению.

(gh-30411)

Поддержка MSVC#

NumPy теперь требует минимальной версии набора инструментов MSVC 19.35 на платформах Windows. Это соответствует Visual Studio 2022 версии 17.5 Preview 2 или новее.

(gh-30489)

Поддержка Cython #

Для сборки с заголовочными файлами Cython из NumPy, подключаемыми через cimport numpy, теперь требуется Cython 3.0 или новее. При попытке собрать зависящий от них проект с Cython 0.29 или более ранней версией появится сообщение примерно следующего вида:

Error compiling Cython file:
------------------------------------------------------------
...
# versions.
#
# See __init__.cython-30.pxd for the real Cython header
#

DEF err = int('Build aborted: the NumPy Cython headers require Cython 3.0.0 or newer.')
  ------------------------------------------------------------

  /path/to/site-packages/numpy/__init__.pxd:11:13: Error in compile-time expression:
  ValueError: invalid literal for int() with base 10:
  'Build aborted: the NumPy Cython headers require Cython 3.0.0 or newer.'
Комментарии к примеру на русском
  • Версии.
  • Настоящий заголовок Cython см. в __init__.cython-30.pxd

Обратите внимание, что недействительное целое число не является ошибкой в NumPy - мы намеренно генерируем эту ошибку, чтобы избежать более неясной ошибки позже в сборке, когда старая версия Cython пытается использовать функцию Cython, которая не была доступна в старой версии Cython.

(gh-30770)

numpy.where больше не усекает целые числа Python #

Раньше целое число Python в аргументе x или y функции numpy.where, выходящее за диапазон выходного типа, усекалось без предупреждения. Теперь вместо этого вызывается OverflowError.

Это изменение также относится к базовой функции C API PyArray_Where.

(gh-30803)

Изменение распределителя памяти по умолчанию#

NumPy теперь использует PyMem_RawMalloc и PyMem_RawFree в качестве распределителя памяти по умолчанию вместо непосредственно системных malloc и free.

( gh-30846 )

from_dlpack возбуждает BufferError вместо RuntimeError#

np.from_dlpack теперь вызывает BufferError вместо RuntimeError, если входной тензор DLPack имеет неподдерживаемое устройство или dtype либо превышает максимальное число измерений. Это согласуется со спецификациями DLPack и Array API, рекомендующими BufferError для данных, которые невозможно импортировать.

( gh-30937 )

Исправления генератора биномиальных выборок BTPE#

Исправлены две независимые ошибки в ряде Стирлинга на этапе принятия или отклонения кандидата алгоритма BTPE, используемого numpy.random.Generator.binomial:

  • Третий и четвёртый члены погрешности складывались вместо вычитания. Эта ошибка знака унаследована из раздела 5.3 исходной статьи Kachitvichyanukul и Schmeiser 1988 года, в которой ошибочно складываются все четыре члена.

  • В старшем коэффициенте с самого начала реализации была опечатка с перестановкой цифр: 13680 вместо 13860.

В результате Generator.binomial и Generator.multinomial (последний использует binomial внутри) теперь могут возвращать иные выборки при том же начальном значении.

Устаревшие numpy.random.RandomState.binomial и numpy.random.RandomState.multinomial не затронуты: они сохраняют исходное, некорректное поведение, чтобы прежние последовательности оставались воспроизводимыми.

(gh-31238)

Арифметика datetime64/timedelta64 вызывает исключение при переполнении#

Сложение, вычитание и умножение на целое число значений datetime64 и timedelta64 теперь вызывают OverflowError, если результат выходит за диапазон int64 или совпадает со специальным значением NaT. Раньше переполнение незаметно приводило к циклическому переходу через границу диапазона, часто давая значение, неотличимое от NaT. Это согласуется с проверкой переполнения, уже выполняемой при приведении типов с изменением единиц времени.

( gh-31378 )

Изменения C API#

  • Теперь методы ArrayMethod "real" и "imag" можно зарегистрировать через PyUFunc_AddLoopsFromSpecs. Они будут использоваться для imag и real. Обычно следует задать *view_offset в их функции resolve_descriptors, чтобы атрибуты массива могли возвращать представления.

    (gh-30984)

  • Новые макросы PyDataType_TYPE, PyDataType_KIND, PyDataType_BYTEORDER и PyDataType_TYPEOBJ для доступа к C API. Вместе с другими макросами, добавленными для перехода NumPy 2.0, они позволяют получать доступ к полям структур PyArray_Descr без прямого доступа к полю.

    ( gh-30994 )

  • NumPy теперь поддерживает стабильный ABI для Python со свободной многопоточностью, описанный в PEP 803.

    (gh-31091)

  • PyArray_DescrFromScalar теперь возвращает полный дескриптор dtype для скаляров пользовательских параметрических типов данных, включая все параметры dtype. Ранее параметры отбрасывались без предупреждения, что могло приводить к неверным результатам операций вроде astype над скалярными объектами. Теперь функция передаёт обработку discover_descr_from_pyobject, которая корректно работает с параметрическими типами данных.

    (gh-31067)

Новые возможности #

  • Теперь пользовательские типы данных можно регистрировать для экспорта и импорта DLPack через numpy.dtypes.register_dlpack_dtype. Авторам таких типов следует пользоваться этой возможностью осторожно.

    (gh-31256)

Определения пакетов Pixi #

Добавлены описания пакетов Pixi для разных вариантов сборки NumPy из исходников. Их можно использовать в рабочих пространствах Pixi зависимых проектов через возможность pixi-build.

Определения как для сборок default, так и для сборок с инструментированием AddressSanitizer (asan) находятся в исходном коде в каталоге pixi-packages/.

Поддерживаются платформы linux-64 и osx-arm64.

(gh-30381)

numpy.ndarray теперь поддерживает структурное сопоставление с образцом#

Для numpy.ndarray и его подклассов теперь установлен флаг Py_TPFLAGS_SEQUENCE, что позволяет применять структурное сопоставление с образцом (PEP 634) с помощью конструкций match/case. Это также позволяет Cython оптимизировать целочисленную индексацию. Подробнее см. :ref:arrays.ndarray.pattern-matching.

(gh-30653)

В пакет polynomial добавлены функции вычисления значений в N измерениях#

Добавлены функции polyvalnd, chebvalnd, legvalnd, hermvalnd, hermevalnd и lagvalnd для вычисления значений многочленов произвольного числа переменных, аналогичные существующим двумерным и трёхмерным функциям.

( gh-30857 )

Новый именованный аргумент descending для numpy.sort и numpy.argsort#

Теперь можно передавать именованный аргумент descending=True в numpy.sort и numpy.argsort, чтобы сортировать массивы по убыванию и получать соответствующие индексы сортировки. Значения NaN, если они есть, помещаются в конец массива при обоих направлениях сортировки. Возможность доступна для всех встроенных типов данных, кроме void, object и generic. SIMD-оптимизации пока не применяются к сортировке по убыванию, поэтому она может работать медленнее.

( gh-31345 )

Улучшения#

Для f2py улучшено поведение intent(inplace). Раньше, если тип данных или порядок входного массива не соответствовал требованиям, массив изменялся на месте: менялся dtype, а данные заменялись исправленной копией. Теперь исправленная копия хранится отдельно и после передачи в подпрограмму Fortran и возможного изменения в ней копируется обратно во входной массив. Поэтому существующие представления и срезы исходного массива больше не рискуют указывать на освобождённую память. Цена — дополнительные расходы на обратное копирование в конце вызова. Примечание переводчика: в оригинале ошибочно сказано «во входную подпрограмму»; имеется в виду входной массив.

Проблема могла возникнуть, например, если раньше вместо ожидаемого массива double передавался целочисленный: обратная запись в целочисленный массив, скорее всего, давала неверные результаты. Чтобы этого избежать, intent(inplace) теперь допускает только массивы с типом, эквивалентным используемому процедурой Fortran, то есть с тем же dtype.kind. Например, процедура, ожидающая double, может принять float, но для целочисленных данных вызовет ошибку.

(gh-29929)

В модулях f2py массивы allocatable теперь видны в dir()#

Переменные модулей с выделяемой памятью (allocatable), для которых f2py создаёт обёртки, теперь отображаются в выводе dir(), что соответствует возможности обращения к ним по имени.

(gh-30965)

Улучшения производительности и изменения #

Повышена производительность numpy.searchsorted#

Реализация двоичного поиска на C++, используемая в numpy.searchsorted, теперь значительно быстрее при поиске нескольких ключей. Шаги двоичного поиска выполняются пакетно для всех ключей, что позволяет лучше использовать локальность данных в кэше и внеочередное выполнение инструкций. Измерения показывают ускорение до 20 раз для сотен тысяч ключей, тогда как поиск одного ключа по скорости сопоставим с прежними версиями.

(gh-30517)

Улучшено масштабирование универсальных функций при свободной многопоточности#

Универсальные функции NumPy теперь значительно лучше масштабируются в сборках CPython без GIL благодаря следующим оптимизациям:

  • Таблица диспетчеризации без блокировок: теперь таблица ufunc реализована как конкурентная хеш-таблица без блокировок, поэтому несколько потоков могут вызывать ufunc без конкуренции за блокировку.

  • Бессмертные общие объекты: некоторые совместно используемые объекты, например глобальные обработчики памяти, сделаны бессмертными. Это уменьшает конкуренцию потоков при изменении счётчиков ссылок.

  • Оптимизированное выделение памяти: NumPy теперь использует PyMem_RawMalloc и PyMem_RawFree для выделения памяти. В Python 3.15 и новее это задействует mimalloc и значительно снижает накладные расходы в многопоточных задачах.

( gh-30846 )

Ускорены свёртки небольших и средних массивов с непрерывным расположением в памяти#

numpy.sum, numpy.prod, numpy.any, numpy.all и другие свёртки с нейтральным элементом теперь используют ускоренный алгоритм, если входной массив непрерывно расположен в памяти, выровнен и не имеет объектного типа, а свёртка выполняется по всем осям (axis=None) без дополнительных специальных аргументов. Для небольших массивов типичное ускорение составляет около 1,3 раза; для numpy.any / numpy.all на непрерывно расположенных в памяти логических массивах оно может достигать 1,9 раза.

(gh-31274)

Улучшения и изменения аннотаций типов#

Улучшения типизации numpy.linalg и предварительная поддержка типизации формы#

Типы входных и выходных данных функций numpy.linalg теперь указаны точнее. Несколько функций также получили предварительную поддержку типизации форм с сохранением обратной совместимости. Например, тип результата numpy.linalg.matmul теперь зависит от типов форм входных массивов. Если формы неизвестны во время проверки типов, используется прежний совместимый тип результата. Из-за ограничений системы типов Python и существующих средств проверки типов учесть все ситуации невозможно; часто типизация форм реализована только для наиболее распространённых случаев с небольшим числом измерений.

(gh-30480)

Аннотации типов numpy.ma#

Модуль numpy.ma теперь полностью покрыт аннотациями типов, включая массивы с маской, маски, различные функции и методы. Таким образом, все подмодули NumPy имеют стопроцентное покрытие аннотациями типов.

( gh-30566 )

Поддержка аннотаций форм во многих функциях и методах#

Многие функции и методы теперь имеют аннотации возвращаемого типа, учитывающие форму массива. Средства проверки типов могут выводить число измерений результата распространённых операций. Например, np.linspace(0, 1) теперь имеет тип одномерного массива float64, а np.sum(x, keepdims=True) — столько же измерений, сколько x.

Это охватывает функции numpy.linalg, функции создания массивов (например, asarray, from{buffer,string,file,iter,regex}), функции создания последовательностей (linspace, logspace, geomspace), функции и методы агрегирования (sum, mean, std, var, min, max, all, any и т. д.), сортировку (sort, argsort, argpartition), накопительные операции (cumsum, cumprod и т. д.), операции над множествами (unique_values, intersect1d, union1d и т. д.) и другие функции, включая nonzero, transpose, diagonal, atleast_{1,2,3}d, clip, round, inner, bincount и fft.fftfreq. В рамках этой работы некоторые из них также получили более точные аннотации dtype возвращаемых значений.

Типизация форм массивов ещё разрабатывается, поэтому охват пока неполный. Из-за ограничений системы типов Python и существующих средств проверки типов она часто реализована только для наиболее распространённых случаев с небольшим числом измерений.

(gh-31172)

Улучшения типизации numpy.fft и предварительная поддержка типизации формы#

Функции numpy.fft теперь поддерживают dtype, отличные от float64/complex128, и получили предварительную поддержку аннотаций формы. Например, возвращаемый тип numpy.fft.fft теперь зависит от типов форм входных массивов. Если формы неизвестны при проверке типов, используется прежний обратно совместимый тип результата.

(gh-31226)

Изменения#

При копировании структурированных массивов теперь используется memcpy для типов данных с непрерывным расположением полей в памяти#

При копировании структурированных массивов с одинаковыми dtype теперь используется memcpy вместо переноса по отдельным полям, если поля dtype расположены непрерывно в памяти, без промежутков. Новый флаг dtype NPY_NOT_TRIVIALLY_COPYABLE устанавливается для структурированных типов с промежутками в памяти, например созданных с явными offsets или индексацией по нескольким полям. Более медленное копирование по полям по-прежнему используется только для таких типов.

Это означает, что байты заполнения в структурированных типах данных с непрерывным расположением полей (например, созданных без явного указания offsets) теперь могут копироваться при memcpy, тогда как раньше они оставались нетронутыми. Это может повлиять на код, который рассчитывает на сохранение байтов заполнения при копировании структурированных массивов.

(gh-29270)

numpy.ctypeslib.as_ctypes теперь не поддерживает скалярные типы #

Функция numpy.ctypeslib.as_ctypes теперь принимает только numpy.ndarray. Передача скалярного значения, например numpy.int32(5), вызывает TypeError. Это изменение устраняет проблему gh-30354 и обеспечивает неизменяемость скалярных значений NumPy. Прежнее поведение опиралось на недокументированное неявное создание временных массивов и не было чётко определено. Для преобразования скаляра в ctypes сначала преобразуйте его в массив, например через numpy.asarray, и только затем передайте в numpy.ctypeslib.as_ctypes.

(gh-30538)

Изменения __array_interface__ для скаляров#

Теперь скаляры предоставляют __array_interface__ напрямую, вместо включения копии массива в поле __ref. Поэтому они экспортируются только для чтения, тогда как раньше разрешали запись. Путь через __ref не был документирован и применялся непоследовательно даже в самом NumPy.

(gh-30538)

meshgrid теперь всегда возвращает кортеж#

Ранее np.meshgrid возвращала список, если sparse было истинным, а copy — ложным. Теперь она всегда возвращает кортеж независимо от аргументов.

(gh-30707)

numpy.triu_indices теперь принимает unsigned integers (беззнаковые целые числа)#

Ранее numpy.triu_indices в некоторых случаях выдавала ошибку при передаче unsigned integers в качестве аргументов. Теперь такие аргументы принимаются во всех случаях.

(gh-30869)

Тип данных object в .real, .imag и связанных функциях#

Для объектных массивов атрибуты .real и .imag теперь ведут себя иначе, возвращая поэлементно getattr(element, "real", element) или getattr(element, "imag", 0). Кроме того, оба результата теперь доступны только для чтения, чтобы предотвратить изменения на месте, которые могли бы не иметь эффекта.

Это изменение также затрагивает np.isreal(), который использует arr.imag.

Раньше .imag всегда возвращал 0, а .real — исходный массив без изменений. Теперь для комплексных объектов Python возвращаются правильные значения. Однако возможны неожиданные результаты, например если element.real() — метод, а не свойство.

(gh-30984)

Внутренние выделения памяти NumPy теперь используют PyMem_RawMalloc #

Внутренние выделения памяти NumPy теперь используют PyMem_RawMalloc вместо malloc и могут отслеживаться tracemalloc.

(gh-31503)
