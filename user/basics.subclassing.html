Наследование от ndarray#

Введение#

Создать подкласс ndarray сравнительно просто, но есть особенности, которых нет у многих других объектов Python. На этой странице объясняются механизм создания таких подклассов и его последствия для реализации подкласса.

Массивы ndarray и создание объектов#

Создание подкласса ndarray осложняется тем фактом, что новые экземпляры классов ndarray могут создаваться тремя разными способами. Это:

  1. Явный вызов конструктора, например MySubClass(params). Это обычный способ создания экземпляра в Python.

  2. Преобразование через представление: получение представления существующего ndarray как экземпляра заданного подкласса.

  3. Создание по шаблону — создание нового экземпляра на основе экземпляра-шаблона. Примеры: получение срезов массива-подкласса, создание возвращаемых объектов универсальными функциями и копирование массивов. Подробнее см. в разделе «Создание по шаблону»

Последние два способа характерны именно для ndarray: они нужны, в частности, для получения срезов массива. Дополнительные сложности при создании подклассов ndarray связаны с механизмами NumPy, которые поддерживают эти два способа создания экземпляров.

Когда использовать наследование#

Помимо сложности самого создания подклассов массивов NumPy, есть риск неожиданного поведения: некоторые функции преобразуют экземпляр подкласса в объект базового класса и «забывают» связанную с подклассом дополнительную информацию. Поэтому использование методов и функций NumPy, которые вы явно не тестировали с вашим подклассом, может давать неожиданные результаты.

По сравнению с другими способами взаимодействия создание подклассов может быть полезно тем, что многие возможности будут «просто работать».

Таким образом, создание подкласса бывает удобным подходом, а долгое время часто было единственным доступным. Теперь у NumPy есть дополнительные протоколы совместимости, описанные в разделе «Взаимодействие с NumPy». Во многих случаях они лучше подходят для задачи либо дополняют использование подклассов.

Создание подкласса может быть уместно, если:

  • вы меньше заботитесь о сопровождаемости кода и других пользователях: подкласс быстрее реализовать, а дополнительную совместимость можно добавлять по мере необходимости. При небольшом числе пользователей возможные неожиданности не столь существенны.

  • Вы не считаете проблемой, если сведения, специфичные для подкласса, будут незаметно проигнорированы или потеряны. Например, у np.memmap потеря сведений о том, что данные отображены из файла в память, не приводит к неверному результату вычисления. Пример подкласса, который иногда вызывает путаницу, — маскированные массивы NumPy. При их появлении наследование было единственным способом реализации; сегодня мы, возможно, постарались бы обойтись протоколами совместимости без создания подкласса.

Авторам подклассов также стоит изучить раздел Взаимодействие с NumPy, чтобы поддержать более сложные сценарии использования или обойти неожиданное поведение.

astropy.units.Quantity и xarray — примеры объектов, подобных массивам и хорошо взаимодействующих с NumPy. Quantity из Astropy использует комбинированный подход: и наследование, и протоколы взаимодействия.

Преобразование через представление#

Преобразование через представление — стандартный механизм ndarray: из массива любого подкласса получают представление в виде экземпляра другого, явно указанного подкласса:

>>> import numpy as np
>>> # create a completely useless ndarray subclass
>>> class C(np.ndarray): pass
>>> # create a standard ndarray
>>> arr = np.zeros((3,))
>>> # take a view of it, as our useless subclass
>>> c_arr = arr.view(C)
>>> type(c_arr)
<class '__main__.C'>

  • Создаём обычный ndarray
  • Получаем его представление в виде нашего бесполезного подкласса

Создание нового объекта по шаблону#

Новый экземпляр подкласса ndarray может возникнуть и по механизму, очень похожему на преобразование через представление: NumPy создаёт его по существующему экземпляру-шаблону. Самый очевидный пример — получение среза массива, принадлежащего подклассу. Например:

>>> v = c_arr[1:]
>>> type(v) # the view is of type 'C'
<class '__main__.C'>
>>> v is c_arr # but it's a new instance
False
Комментарии к примеру на русском
  • Представление имеет тип C
  • Но это новый экземпляр

Срез — представление исходных данных c_arr. Получая представление ndarray, мы создаём новый ndarray того же класса, указывающий на исходные данные.

Такие представления нужны и в других операциях с ndarray: при копировании массивов (c_arr.copy()), создании выходных массивов универсальных функций (см. также __array_wrap__ для универсальных и других функций) и в методах свёртки, например c_arr.mean().

Связь создания представления с приведением типа и создания объекта по шаблону#

Оба способа используют один механизм. Мы различаем их, поскольку аргументы ваших методов будут разными. При преобразовании через представление новый экземпляр вашего типа массива создаётся из массива, который может относиться к любому подклассу ndarray. При создании по шаблону новый экземпляр вашего класса создаётся по уже существующему экземпляру того же класса. Это позволяет, например, перенести атрибуты, специфичные для вашего подкласса.

Последствия для реализации подклассов#

При создании подкласса ndarray нужно учитывать не только явное создание массива своего типа, но и приведение типа через представление и создание нового объекта по шаблону. NumPy предоставляет для этого специальный механизм, из-за которого создание подклассов немного отличается от обычного.

В механизме поддержки представлений и создания новых объектов по шаблону в подклассах ndarray есть два аспекта.

Первая особенность: основная работа по инициализации объекта выполняется методом ndarray.__new__, а не более привычным __init__. Вторая — метод __array_finalize__: он позволяет подклассу завершить настройку после создания представления или нового экземпляра по шаблону.

Краткое введение в __new__ и __init__ в Python#

__new__ — стандартный метод Python, который при наличии вызывается до __init__ при создании экземпляра класса. Подробнее см. документацию Python по __new__.

Например, рассмотрим следующий код Python:

>>> class C:
...     def __new__(cls, *args):
...         print('Cls in __new__:', cls)
...         print('Args in __new__:', args)
...         # The `object` type __new__ method takes a single argument.
...         return object.__new__(cls)
...     def __init__(self, *args):
...         print('type(self) in __init__:', type(self))
...         print('Args in __init__:', args)
Комментарии к примеру на русском
  • Метод __new__ типа `object` принимает один аргумент.

это означает, что мы получаем:

>>> c = C('hello')
Cls in __new__: <class '__main__.C'>
Args in __new__: ('hello',)
type(self) in __init__: <class '__main__.C'>
Args in __init__: ('hello',)

При вызове C('hello') метод __new__ получает первым аргументом сам класс, а следующим — переданную строку 'hello'. После вызова __new__ Python обычно (см. ниже) вызывает наш метод __init__. Первым аргументом ему передаётся результат __new__ — уже экземпляр класса, — а затем аргументы, указанные при вызове.

Как видно, объект можно инициализировать в методе __new__, в методе __init__ или в обоих. У ndarray нет собственного метода __init__: вся инициализация выполняется в __new__.

Зачем использовать __new__, а не обычный __init__? Потому что в некоторых случаях, как в случае с ndarray, мы хотим иметь возможность возвращать объект какого-то другого класса. Учтите следующее:

class D(C):
    def __new__(cls, *args):
        print('D cls is:', cls)
        print('D args in __new__:', args)
        return C.__new__(C, *args)

    def __init__(self, *args):
        # we never get here
        print('In D __init__')
Комментарии к примеру на русском
  • Сюда выполнение не дойдёт

Это означает следующее:

>>> obj = D('hello')
D cls is: <class 'D'>
D args in __new__: ('hello',)
Cls in __new__: <class 'C'>
Args in __new__: ('hello',)
>>> type(obj)
<class 'C'>

Определение C осталось прежним, но для D метод __new__ возвращает экземпляр класса C вместо D. При этом метод __init__ класса D не вызывается. В общем случае, когда метод __new__ возвращает объект другого класса, метод __init__ класса, в котором он определён, не вызывается.

Именно так подклассы ndarray могут возвращать представления с сохранением своего типа. При создании представления стандартный механизм ndarray создаёт новый объект ndarray примерно следующим образом:

obj = ndarray.__new__(subtype, shape, ...

Здесь subtype — подкласс. Поэтому возвращаемое представление принадлежит этому подклассу, а не классу ndarray.

Это решает задачу возврата представлений того же типа, но создаёт новую проблему. Внутренние механизмы ndarray могут устанавливать класс таким способом в стандартных методах создания представлений, однако метод __new__ класса ndarray ничего не знает о действиях нашего собственного метода __new__ по установке атрибутов и т. д. Почему бы тогда не вызвать obj = subdtype.__new__(...? Потому что у нашего метода __new__ может быть другая сигнатура вызова.

Роль __array_finalize__#

__array_finalize__ — это механизм, который предоставляет numpy, позволяющий подклассам обрабатывать различные способы создания новых экземпляров.

Напомним три способа появления экземпляра подкласса:

  1. Явный вызов конструктора: obj = MySubClass(params). При этом в обычном порядке вызываются MySubClass.__new__, затем MySubClass.__init__, если он определён.

  2. Приведение через представление

  3. Создание по шаблону

Наш метод MySubClass.__new__ вызывается только при явном вызове конструктора, поэтому нельзя полагаться на MySubClass.__new__ или MySubClass.__init__ при создании представления с приведением к подклассу или нового объекта по шаблону. Оказывается, MySubClass.__array_finalize__ действительно вызывается при всех трёх способах создания объекта, поэтому именно в нём обычно выполняются необходимые служебные действия.

  • При явном вызове конструктора наш подкласс должен создать новый экземпляр ndarray собственного класса. На практике для этого нужно вызвать ndarray.__new__(MySubClass,...), использовать учитывающий иерархию классов вызов super().__new__(cls, ...) либо создать представление существующего массива с приведением к подклассу (см. ниже).

  • При приведении к представлению и создании по шаблону на уровне C вызывается эквивалент ndarray.__new__(MySubClass,....

Аргументы, которые получает __array_finalize__, отличаются для трех методов создания экземпляров выше.

Следующий код позволяет нам просмотреть последовательности вызовов и аргументы:

import numpy as np

class C(np.ndarray):
    def __new__(cls, *args, **kwargs):
        print('In __new__ with class %s' % cls)
        return super().__new__(cls, *args, **kwargs)

    def __init__(self, *args, **kwargs):
        # in practice you probably will not need or want an __init__
        # method for your subclass
        print('In __init__ with class %s' % self.__class__)

    def __array_finalize__(self, obj):
        print('In array_finalize:')
        print('   self type is %s' % type(self))
        print('   obj type is %s' % type(obj))

Сигнатура __array_finalize__:

def __array_finalize__(self, obj):

Видно, что вызов super, направленный в ndarray.__new__, передаёт методу __array_finalize__ новый объект нашего класса (self) и объект, из которого получено представление (obj). Как показывает приведённый выше вывод, self всегда является новым экземпляром нашего подкласса, а тип obj зависит от способа создания экземпляра:

  • При явном вызове конструктора obj равен None.

  • При преобразовании через представление obj может быть экземпляром любого подкласса ndarray, включая наш собственный.

  • При создании по шаблону obj — другой экземпляр нашего подкласса, который можно использовать для настройки нового экземпляра self.

Поскольку __array_finalize__ — единственный метод, вызываемый при любом способе создания нового экземпляра, в нём удобно, в частности, задавать значения по умолчанию для новых атрибутов объекта.

Пример поможет прояснить это.

Простой пример - добавление дополнительного атрибута к ndarray #

import numpy as np

class InfoArray(np.ndarray):

    def __new__(subtype, shape, dtype=np.float64, buffer=None, offset=0,
                strides=None, order=None, info=None):
        # Create the ndarray instance of our type, given the usual
        # ndarray input arguments.  This will call the standard
        # ndarray constructor, but return an object of our type.
        # It also triggers a call to InfoArray.__array_finalize__
        obj = super().__new__(subtype, shape, dtype,
                              buffer, offset, strides, order)
        # set the new 'info' attribute to the value passed
        obj.info = info
        # Finally, we must return the newly created object:
        return obj

    def __array_finalize__(self, obj):
        # ``self`` is a new object resulting from
        # ndarray.__new__(InfoArray, ...), therefore it only has
        # attributes that the ndarray.__new__ constructor gave it -
        # i.e. those of a standard ndarray.
        #
        # We could have got to the ndarray.__new__ call in 3 ways:
        # From an explicit constructor - e.g. InfoArray():
        #    obj is None
        #    (we're in the middle of the InfoArray.__new__
        #    constructor, and self.info will be set when we return to
        #    InfoArray.__new__)
        if obj is None: return
        # From view casting - e.g arr.view(InfoArray):
        #    obj is arr
        #    (type(obj) can be InfoArray)
        # From new-from-template - e.g infoarr[:3]
        #    type(obj) is InfoArray
        #
        # Note that it is here, rather than in the __new__ method,
        # that we set the default value for 'info', because this
        # method sees all creation of default objects - with the
        # InfoArray.__new__ constructor, but also with
        # arr.view(InfoArray).
        self.info = getattr(obj, 'info', None)
        # We do not need to return anything

Этот класс не очень удобен: у него тот же конструктор, что у базового ndarray, которому нужно передавать буферы, форму и другие параметры. Вероятно, удобнее иметь конструктор, принимающий готовый ndarray, полученный обычным вызовом NumPy np.array, и возвращающий объект нашего класса.

Чуть более реалистичный пример - атрибут добавлен к существующему массиву #

Следующий класс принимает уже существующий обычный ndarray, создаёт его представление нашего типа и добавляет атрибут.

import numpy as np

class RealisticInfoArray(np.ndarray):

    def __new__(cls, input_array, info=None):
        # Input array is an already formed ndarray instance
        # We first cast to be our class type
        obj = np.asarray(input_array).view(cls)
        # add the new attribute to the created instance
        obj.info = info
        # Finally, we must return the newly created object:
        return obj

    def __array_finalize__(self, obj):
        # see InfoArray.__array_finalize__ for comments
        if obj is None: return
        self.info = getattr(obj, 'info', None)

  • Входной массив — уже созданный экземпляр ndarray
  • Сначала приводим его к типу нашего класса
  • Добавляем новому экземпляру атрибут
  • Наконец, нужно вернуть созданный объект:
  • Пояснения см. в InfoArray.__array_finalize__

Итак:

>>> arr = np.arange(5)
>>> obj = RealisticInfoArray(arr, info='information')
>>> type(obj)
<class 'RealisticInfoArray'>
>>> obj.info
'information'
>>> v = obj[1:]
>>> type(v)
<class 'RealisticInfoArray'>
>>> v.info

__array_ufunc__ для универсальных функций#

Подкласс может изменить обработку универсальных функций NumPy, переопределив стандартный метод ndarray.__array_ufunc__. Он вызывается вместо обычной обработки ufunc и должен вернуть результат операции либо NotImplemented, если запрошенная операция не реализована.

Сигнатура __array_ufunc__:

def __array_ufunc__(self, ufunc, method, *inputs, **kwargs):

  • ufunc — объект вызванной универсальной функции.

  • method — строка, указывающая способ вызова универсальной функции: "__call__" означает прямой вызов; иначе указывается один из её методов: "reduce", "accumulate", "reduceat", "outer" или "at".

  • inputs — кортеж входных аргументов ufunc

  • kwargs содержит необязательные и именованные аргументы, переданные функции, в том числе аргументы out, которые всегда находятся в кортеже.

Типичная реализация преобразует все входные и выходные объекты собственного класса, передаёт аргументы суперклассу через super(), а затем при необходимости преобразует результаты обратно и возвращает их. Ниже приведён пример из теста test_ufunc_override_with_super в файле _core/tests/test_umath.py.

input numpy as np

class A(np.ndarray):
    def __array_ufunc__(self, ufunc, method, *inputs, out=None, **kwargs):
        args = []
        in_no = []
        for i, input_ in enumerate(inputs):
            if isinstance(input_, A):
                in_no.append(i)
                args.append(input_.view(np.ndarray))
            else:
                args.append(input_)

        outputs = out
        out_no = []
        if outputs:
            out_args = []
            for j, output in enumerate(outputs):
                if isinstance(output, A):
                    out_no.append(j)
                    out_args.append(output.view(np.ndarray))
                else:
                    out_args.append(output)
            kwargs['out'] = tuple(out_args)
        else:
            outputs = (None,) * ufunc.nout

        info = {}
        if in_no:
            info['inputs'] = in_no
        if out_no:
            info['outputs'] = out_no

        results = super().__array_ufunc__(ufunc, method, *args, **kwargs)
        if results is NotImplemented:
            return NotImplemented

        if method == 'at':
            if isinstance(inputs[0], A):
                inputs[0].info = info
            return

        if ufunc.nout == 1:
            results = (results,)

        results = tuple((np.asarray(result).view(A)
                         if output is None else output)
                        for result, output in zip(results, outputs))
        if results and isinstance(results[0], A):
            results[0].info = info

        return results[0] if len(results) == 1 else results

Итак, этот класс не делает ничего особенного: он преобразует свои экземпляры в обычный ndarray (иначе возникла бы бесконечная рекурсия!) и добавляет словарь info со сведениями о том, какие входные и выходные значения были преобразованы. Поэтому, например:

>>> a = np.arange(5.).view(A)
>>> b = np.sin(a)
>>> b.info
{'inputs': [0]}
>>> b = np.sin(np.arange(5.), out=(a,))
>>> b.info
{'outputs': [0]}
>>> a = np.arange(5.).view(A)
>>> b = np.ones(1).view(A)
>>> c = a + b
>>> c.info
{'inputs': [0, 1]}
>>> a += b
>>> a.info
{'inputs': [0, 1], 'outputs': [0]}

Другой подход — использовать getattr(ufunc, methods)(*inputs, **kwargs) вместо вызова super. В этом примере результат будет тем же, но при наличии у другого операнда метода __array_ufunc__ поведение различается. Пусть вычисляется np.add(a, b), где b — экземпляр другого класса B с переопределением. Если, как в примере, использовать super, метод ndarray.__array_ufunc__ обнаружит переопределение у b и не сможет самостоятельно вычислить результат. Он вернёт NotImplemented, как и наш класс A. Затем управление перейдёт к b, который либо умеет работать с нашим классом и вернёт результат, либо вернёт NotImplemented, что приведёт к TypeError.

Если заменить вызов super на getattr(ufunc, method), фактически получится np.add(a.view(np.ndarray), b). Снова вызывается B.__array_ufunc__, но теперь другой аргумент — ndarray. Вероятно, метод умеет его обрабатывать и вернёт новый экземпляр B. Наш демонстрационный класс это не поддерживает, однако такой подход может быть лучшим вариантом, например для повторной реализации MaskedArray через __array_ufunc__.

В заключение: если классу подходит использование super, этот подход упрощает построение иерархий классов. Предположим, другой наш класс B тоже использует super в реализации __array_ufunc__, а мы создали класс C, наследующий от обоих, то есть class C(A, B) (для простоты без собственного переопределения __array_ufunc__). Тогда вызов любой универсальной функции для экземпляра C передаётся A.__array_ufunc__; вызов super в A переходит в B.__array_ufunc__, а вызов super в B — в ndarray.__array_ufunc__. Это позволяет A и B работать совместно.

__array_wrap__ для ufunc и других функций#

До NumPy 1.13 поведение универсальных функций настраивалось только через __array_wrap__ и __array_prepare__ (последний теперь удалён). Они позволяли изменить тип результата, но, в отличие от __array_ufunc__, не позволяли менять входные данные. В перспективе планируется объявить их устаревшими, однако __array_wrap__ используется и другими функциями и методами NumPy, например squeeze, поэтому пока необходим для сохранения всей функциональности.

По смыслу __array_wrap__ завершает обработку результата: позволяет подклассу задать тип возвращаемого значения и обновить атрибуты и метаданные. Рассмотрим пример. Вернёмся к простому подклассу, изменив его имя и добавив вывод диагностических сообщений:

import numpy as np

class MySubClass(np.ndarray):

    def __new__(cls, input_array, info=None):
        obj = np.asarray(input_array).view(cls)
        obj.info = info
        return obj

    def __array_finalize__(self, obj):
        print('In __array_finalize__:')
        print('   self is %s' % repr(self))
        print('   obj is %s' % repr(obj))
        if obj is None: return
        self.info = getattr(obj, 'info', None)

    def __array_wrap__(self, out_arr, context=None, return_scalar=False):
        print('In __array_wrap__:')
        print('   self is %s' % repr(self))
        print('   arr is %s' % repr(out_arr))
        # then just call the parent
        return super().__array_wrap__(self, out_arr, context, return_scalar)
Комментарии к примеру на русском
  • Затем просто вызываем родительский метод

Вызовем ufunc для экземпляра нового класса массива:

>>> obj = MySubClass(np.arange(5), info='spam')
In __array_finalize__:
   self is MySubClass([0, 1, 2, 3, 4])
   obj is array([0, 1, 2, 3, 4])
>>> arr2 = np.arange(5)+1
>>> ret = np.add(arr2, obj)
In __array_wrap__:
   self is MySubClass([0, 1, 2, 3, 4])
   arr is array([1, 3, 5, 7, 9])
In __array_finalize__:
   self is MySubClass([1, 3, 5, 7, 9])
   obj is MySubClass([0, 1, 2, 3, 4])
>>> ret
MySubClass([1, 3, 5, 7, 9])
>>> ret.info
'spam'

Универсальная функция (np.add) вызвала метод __array_wrap__, передав аргументами self в качестве obj и out_arr — результат сложения типа ndarray. Затем стандартная реализация __array_wrap__ (ndarray.__array_wrap__) привела результат к классу MySubClass и вызвала __array_finalize__ — отсюда копирование атрибута info. Всё это произошло на уровне C.

Но здесь можно выполнить любые нужные действия:

class SillySubClass(np.ndarray):

    def __array_wrap__(self, arr, context=None, return_scalar=False):
        return 'I lost your data'

>>> arr1 = np.arange(5)
>>> obj = arr1.view(SillySubClass)
>>> arr2 = np.arange(5)
>>> ret = np.multiply(obj, arr2)
>>> ret
'I lost your data'

Определив для подкласса собственный метод __array_wrap__, можно изменить результат ufunc. Метод __array_wrap__ принимает self, затем результат ufunc или другой функции NumPy и необязательный параметр context. Универсальные функции передают в нём кортеж из трёх элементов, а другие функции NumPy обычно его не передают. Примечание переводчика: описание состава кортежа в оригинале неточно. В NumPy 2.5 это объект ufunc, кортеж её аргументов и индекс выходного результата (0, 1 и т. д.), а не имя функции и её «область определения». Также современная сигнатура включает необязательный аргумент return_scalar. Хотя, как показано выше, возможны и другие варианты, __array_wrap__ должен возвращать экземпляр своего класса; пример реализации есть у маскированных массивов. В __array_wrap__ всегда передаётся массив NumPy: он может быть экземпляром подкласса, обычно класса вызывающего объекта, но это необязательно.

Дополнительные тонкости: собственные методы __del__ и ndarray.base#

Одна из задач ndarray — отслеживать владение памятью массивов и их представлений. Предположим, мы создали ndarray arr и срез v = arr[1:]. Оба объекта обращаются к одной памяти. NumPy отслеживает происхождение данных массива или представления через атрибут base:

>>> # A normal ndarray, that owns its own data
>>> arr = np.zeros((4,))
>>> # In this case, base is None
>>> arr.base is None
True
>>> # We take a view
>>> v1 = arr[1:]
>>> # base now points to the array that it derived from
>>> v1.base is arr
True
>>> # Take a view of a view
>>> v2 = v1[1:]
>>> # base points to the original array that it was derived from
>>> v2.base is arr
True
Комментарии к примеру на русском
  • Обычный ndarray, владеющий своими данными
  • В этом случае base равен None
  • Получаем представление
  • Теперь base указывает на исходный массив
  • Получаем представление представления
  • base указывает на первоначальный исходный массив

Обычно, если массив владеет своей памятью, как arr в этом примере, arr.base равен None. У этого правила есть исключения; подробнее см. в книге о NumPy.

Атрибут base полезен для определения того, есть ли у нас представление или исходный массив. Это, в свою очередь, может быть полезно, если нам нужно знать, следует ли выполнять какую-либо конкретную очистку при удалении массива подкласса. Например, мы можем захотеть выполнить очистку только в том случае, если удален исходный массив, но не представления. Для примера того, как это может работать, взгляните на класс memmap в numpy._core.

Подклассы и совместимость с зависимыми проектами#

При создании подкласса ndarray или объекта, имитирующего интерфейс ndarray, вы сами определяете степень совместимости своего API с NumPy. Для удобства многие функции NumPy, имеющие одноимённый метод ndarray, например sum, mean, take и reshape, сначала проверяют наличие такого метода у первого аргумента. Если метод есть, вызывается он, а не преобразование аргументов в массив NumPy.

Например, чтобы ваш подкласс или объект, поддерживающий нужный интерфейс (duck type), был совместим с функцией NumPy sum, сигнатура его метода sum должна быть следующей:

def sum(self, axis=None, dtype=None, out=None, keepdims=False):
...

Это та же сигнатура, что у np.sum. Поэтому при вызове np.sum для объекта NumPy вызовет его собственный метод sum и передаст перечисленные в сигнатуре аргументы. Ошибок не возникнет, поскольку сигнатуры полностью совместимы.

Однако если изменить эту сигнатуру, например так:

def sum(self, axis=None, dtype=None):
...

Этот объект больше не совместим с np.sum, поскольку если вы вызовете np.sum, он передаст неожиданные аргументы out и keepdims, что приведет к возникновению ошибки TypeError.

Чтобы сохранить совместимость с NumPy и будущими версиями, в которых могут появиться новые именованные аргументы, не перечисляя все аргументы NumPy явно, включите **kwargs в сигнатуру своей функции. Например:

def sum(self, axis=None, dtype=None, **unused_kwargs):
...

Этот объект снова совместим с np.sum, поскольку все лишние аргументы (то есть именованные аргументы, отличные от axis и dtype) помещаются в параметр **unused_kwargs.
